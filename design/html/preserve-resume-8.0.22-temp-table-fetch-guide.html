用户临时表与待 FETCH 结果
如何跨主继续使用

Preserve Trx 在完整命令边界保存用户临时表和服务端尚未取完的游标结果，经 standby transfer 提前送到物理备机。PS statement 由系统内部已有链路在源端序列化并发送给 receiver。备机在线升主、SQL RESUME 接管事务和资源后，回放 PS，再显式关联原来的 cursor，业务继续 DML 和 FETCH。

    01 / OVERVIEW先用一个会话理解这项能力

    换的是后端连接和主节点；临时表中的数据、事务效果，以及已生成结果的下一行，必须接得上。

    一个业务 session 已有临时表 tmp_cart，在事务中修改了临时表和普通 InnoDB 表，又执行一个带服务端 cursor 的查询。查询结果已经物化，共 1,000 行。客户端完成前 100 行的 FETCH 后，系统开始 DRAIN。

    用户能观察到什么

    前端连接保持；后续 FETCH 读到剩余结果。未提交的临时表 DML 随恢复事务继续受 COMMIT、ROLLBACK 和受支持的 SAVEPOINT 语义约束。

    两类资源分别保存什么

    临时表的定义、数据和恢复所需 undo；已物化 cursor 的列元数据、行文件、结果代次与消费位置。事务、锁、ReadView、binlog 等仍沿用既有 Preserve 管线。

    先区分三种结论：代码已实现表示本仓库有相应处理；集成合同表示依赖系统内物理复制／PS／proxy 模块的既有协作机制；运行证据仅覆盖所列版本、场景及端点。本文始终分别说明。

    02 / BACKGROUND临时表、结果集和 cursor 是不同的对象

    对象是什么／在哪里本能力如何对待
    用户临时表用户通过 CREATE TEMPORARY TABLE 建立，挂在 session 的临时表集合。通常活到 DROP 或 session 销毁。保存受支持的 InnoDB 表及事务恢复状态。
    查询内部临时表执行器为排序、分组、物化等建立的中间对象，通常随当前命令清理。不迁移执行中的整个执行器；只保留跨命令存活的 cursor 结果语义。
    Prepared statement（PS）预处理语句对象，位于 session 的 statement map，可反复 EXECUTE。PS 本体通过系统内部已有链路在源端序列化、传给 receiver，再在 RESUME 后回放。本临时资源模块不重复实现这条链路。
    服务端 cursor 及其物化结果Classic 二进制协议以只读 cursor 标志 EXECUTE 后，结果由服务端持有，通过后续 COM_STMT_FETCH 分批返回。保存行内容、列信息、代次和位置，回放 PS 后显式挂接。
    普通 SELECT 的客户端缓冲服务端已发送，数据尚在网络、驱动或应用缓冲中。驱动也可能把本地取行方法叫 fetch。不是本能力新增迁移的服务端 cursor；前端连接与原有协议处理负责交付。

    三条原生语义先分清

    • 临时表属于 session。同名临时表可由不同 session 分别持有；COMMIT 不会因为名字里有“临时”就删除它。
    • 表的存在与表内 DML 不同。CREATE／DROP TEMPORARY TABLE 的存在性不因普通 ROLLBACK 自动撤销；受支持的 InnoDB 表内 DML 按事务回滚。因此保存点、DROP 后同名重建和 undo 不能只看表名。
    • 驱动的 fetch 方法不一定发 FETCH 命令。本文保留的是以 Classic 只读 cursor 标志执行 PS 后，通过 COM_STMT_FETCH 请求的服务端结果。文本 SQL PREPARE／EXECUTE 不自动等价于这个协议模式。

    为什么不能只保存“表文件”

    用户临时表需要 SQL 层定义与 InnoDB 对象相互对应。数据页中还包含表、索引、空间、行版本和 undo 等关系。仅把源文件复制到新主，会同时遇到定义缺失、回滚链不完整和 ID 冲突。临时表未参与普通持久表那套完整 redo 恢复语义，也不能假定物理复制自然带来了所有 session 私有状态。

    为什么不必重建原来的结果临时表形态

    MySQL 的物化 cursor 可以依赖内存或落盘的内部结果表。恢复目标是保留结果值、类型、顺序和读取位置，不是在新主重放查询计划。当前实现封存结果文件，receiver 提前建立 decoder／发送对象，恢复后由独立 cursor 读取文件。因此执行器内部临时表与用户临时表走不同的资源通路。

    一个 FETCH 的真实含义

    若客户端与 proxy 的前端连接真正断开，这个逻辑会话的连续性合同随之结束。新建会话通常需要重新执行查询，得到新的结果并从头读取；本能力不承诺跨前端断连找回客户端尚未消费的缓冲。

    源码核对：原生对象与协议语义
    • sql_class.h：THD::temporary_tables、PS map。
    • sql_cursor.cc：物化 cursor 的结果表、open／fetch／close。
    • protocol_classic.cc：COM_STMT_FETCH 解包与行数；sql_prepare.cc：EXECUTE／RESET／CLOSE 生命周期。
    • sql_parse.cc：COMMIT／ROLLBACK 与 RELEASE；mysql_client_test.cc：test_bug12243 的 COMMIT 后 FETCH。不能把被禁用的旧断言当成当前通用规则。
    • sp_rcontext.cc：存储程序 cursor 向局部变量取值，不等同于 Classic 客户端 FETCH。

    03 / SEMANTICS保存的边界与各方责任

    保存点必须位于完整命令边界。正在执行的命令先走完；只有既有超时策略可以结束等待，不能在语句中间搬走执行现场。

    必须保持的事实为何重要
    临时表定义、DATA、undo 与事务锚点属于同一有效边界避免数据已经更新，而回滚链或字典仍是旧版本。
    结果身份包含恢复身份、源 statement ID、最终 generation同一 PS 可多次 EXECUTE；相同 ID 也可能经历 CLOSE 和重建。
    列信息、结果值、顺序、下一读取位置及 EOF 语义一致避免重复行、遗漏行、类型变化或错误复活已结束结果。
    final 清单精确选择仍然存活的资源历史传输过的结果不一定仍属于最终会话。
    业务放行前，恢复、回放、必要关联与 CLOSE 补发完成避免客户端访问部分恢复的 session。
    参与方职责不由本资源层重新实现的内容
    本工程资源模块TEMP 和 cursor 结果捕获、校验、传输、receiver 准备、owner 交接和显式关联。不生成新的 PS 本体迁移体系。
    既有 Preserve 核心DRAIN、事务／锁／ReadView／binlog 恢复、token、final 和升主接点。不新增物理升主阶段。
    物理复制工程系统内部已有 session 上下文转移；源端序列化 PS statement 并发送给 receiver；SQL RESUME 后回放 PS，保持原 ID 与权威记录映射；独占接管目标 session。该完整工程源码未在本地逐项核验，不等于系统缺少这些能力。
    proxy通过既有特殊错误码协调后端切换，保留前端；按合同补发 CLOSE，并在恢复失败时结束逻辑会话。不要求客户端修改，也不增加通用业务命令重放协议。

    层次主要文件／模块负责什么
    编排与最终接管preserve_trx、preserve_trx_drain、preserve_trx_standby_phase2_scheduler命令边界、阶段、事务与资源的共同收敛，SQL RESUME。
    TEMP 源端preserve_trx_temp_table、temp_prebuild、temp_undo_prebuild、temp_pretransfer、temp_delta目录和历史、页捕获、预构建、增量依赖。
    TEMP 目标端temp_receiver、temp_import、temp_restore、temp_id_contract；InnoDB trx0temp_preserve_*原生资源分配、转换、校验、SQL 对象安装和 undo 恢复。
    结果源端preserve_trx_cursor_capture、preserve_trx_cursor、cursor_file、result_manifest、result_pretransfer、result_transfer封存文件、选择有效结果代、保存位置及最终清单。
    结果目标端cursor_decode、result_cursor、result_restore提前解码准备，RESUME owner，PS 回放后挂接。
    共同传输／准备preserve_trx_transfer、receiver_prepare、receiver_candidates、receiver_retired、resource协议、候选索引、现有 worker、额度、取消及最后使用者管理。
    在线升主preserve_trx_promotion、preserve_trx_promotion_prepared、InnoDB 既有 Preserve hooks在固定升主接点采用已准备资源。

    共享 MySQL 文件只保留必要接点：例如 sql_prepare.cc 的 cursor 生命周期、sql_cursor.cc 的轻量结果身份与捕获输入、网络首包头的安全读等待钩子、protocol_classic.cc 的发送绑定。捕获与恢复接点按功能／内部状态门控，大段资源算法集中在专用文件中。临时 ID namespace 是独立启动策略：启用后即使 Preserve 关闭仍影响分配，不能把所有接点一概描述为 OFF 时完全无行为差异。

    源码导航

    完整源码分工；receiver_prepare；temp_receiver；result_restore。表内模块名省略共同的 sql/ 路径和 .cc/.h 后缀，实际文件以索引为准。

    05 / END TO END从持续业务到新主再次 FETCH

    源端“捕获完成”、传输“收到 ACK”、receiver“准备完成”和 epoch“READY”是四件事。流水线要让数据规模相关工作尽量在 Phase1 完成，最终切换只处理不可避免的尾差和安装。

    Phase1 到 T0：先守住原有事务边界

    本节展示当前 bounded dependency 流水路线：进入最终切换前，沿用既有 stop purge → pipeline cutoff → 发布 T0 → dependency readiness 收敛 → closing 的顺序。在 stop purge 后、cutoff 前，对已登记目标进行最后一轮有限结果采样，仍受原 Phase1 截止期约束，不扩展新 cohort 或重开首次门槛。此处检查的是结果资源；系统已有 PS 序列化／回放链路保持自己的职责。该条件路线不泛化为所有 DRAIN 模式的无条件执行序列。

    pipeline cutoff 等待相关作业、ordinary outstanding 和 operation permits 收敛，不要求全部业务事务提交。T0 后仍可能有需要保留的存活事务；这正是 Preserve 的目标。

    final 与 READY：固定的是“这一次恢复究竟用什么”

    final 选择确切的临时表版本和仍开放的结果代，带上结果读取位置。目标复用身份与依赖匹配的预准备对象；缺失或不兼容的部分必须补齐。结果 cursor 仍在 READY 前完整准备。TEMP 在最终输入校验、目标 ID/dictionary 与私有 undo 准备后可 READY；剩余页处理和 pwrite、flush、close 由原 receiver worker 继续。SQL RESUME 仅等待本 session 完成，不执行批量复制和转换。

    源码核对：阶段与完成点
    • preserve_trx.cc、preserve_trx_drain.cc：DRAIN 和 RESUME 主链。
    • preserve_trx_transfer.cc：COMMIT 接受、final ACK 与后续绑定／READY 发布；receiver_prepare：已有 worker 中的候选准备。
    • result_pretransfer、temp_pretransfer：持续预传与 final 的衔接。

    06 / TEMP TABLES临时表：数据能读，事务也必须能回滚

    BASE 和 DELTA：少搬变化，但仍证明完整性

    BASE 给出确定的基础镜像。后续 DELTA 说明相对基础依赖的页面和元数据变化，final 选择能还原同一最终状态的依赖集合。连续捕获利用页版本等信息跳过已知未变部分；不能只比较文件长度、只抓新追加页，或者用无 redo 临时空间的 LSN 当作完整变化证明。

    undo 是最容易误判的部分。继续 UPDATE、回滚到保存点、回滚和页复用，可能修改已有 undo 页、链、偏移及锚点。必须跟随真实 owner 和历史关系捕获，而不是把 undo 当作只追加的日志。receiver 在原生 no-redo undo slots 中保留 undo_no，并转换 table ID、前驱 roll pointer 和 LOB 空间引用；恢复时接回同一 owner 事务，并保持保存点要求的序号下界。这不是重放 SQL 行日志或照搬源 undo 地址。“SELECT 正确”也不能证明 ROLLBACK 正确。

    当前稀疏 BASE 表示可省略实际全零的 4 KiB 块，保留逻辑完整大小和逻辑摘要；传输表示还有自身校验。收益不足可回退到原始表示。它减少无用字节，不允许省略非零页，也不把完整性校验变成可选项。

    目标节点已有临时表：靠原生分配与统一映射隔离

    当前协商合同使用进程本地高位临时 table ID 范围，索引仍采用原生 32 位 ID。源 index ID 可以保留在新分配、独占的目标空间内。因此既不能写成“所有源 ID 原样保留”，也不能写成“所有 ID 都全局改号”。空间、表、undo 及行／LOB／FSEG 等关联由同一导入计划处理。

    数据量相关的页面转换、复制和准备尽量在 Phase1 完成。E128 允许 TEMP 最终尾部在 READY 后继续；SQL RESUME 等待本 session 的真实完成，不能读取半成品。实际物理 replay／在线升主期间，目标临时池、undo 和 ID 分配器是否保持这些资源的生命周期，是完整物理复制系统集成时必须核验的合同；关闭 redo 不是其证明。

    AUTO_INCREMENT 取原生的 next counter，不能通过 MAX(id)+1 猜测；无显式主键的表还要保留隐藏 DB_ROW_ID 并保证后续分配下界。DDL 的表名也不是稳定身份：DROP 后同名重建必须区分 table ID／generation，避免旧 undo 误接新表。

    SQL 能力与历史不是一句“支持 DDL”

    场景当前边界
    InnoDB 临时表 DML、AUTO_INCREMENT、BLOB／JSON、生成列当前有相应保存／导入路径；类型、索引和行格式仍受实际字典及页校验约束，不承诺任意非法／未知布局。
    已记录的 CREATE、确认的 DROP、SAVEPOINT／RELEASE／ROLLBACK TO有历史与恢复处理；表目录和 undo 必须与所选边界一致。
    TRUNCATE／ALTER／RENAME 等历史不能统称任意临时 DDL 序列可迁移。具体动作需结合原生命令的隐式提交、历史清理及捕获 gate 判断；不兼容的保留历史会拒绝。
    仅临时表事务／混合事务／结果存在但没有引擎事务按真实恢复依据选择 TEMP_UNDO、REDO_RESURRECTION、READ_CONTEXT 或 NONE；SQL 事务活动状态另行判断，不能只凭一个引擎分支推断 session 没有事务。
    源码核对：TEMP 目录、undo、ID 与增量
    • temp_table.cc：候选 gate、DD、历史；temp_history.cc：DDL／保存点记录。
    • temp_delta.cc、temp_undo_prebuild.cc：增量与 undo 预构建。
    • temp_id_contract.h：OPEN／ACK 合同与其证据边界；trx0temp_preserve_id.cc：本地 ID。
    • trx0temp_preserve_import.cc、trx0temp_preserve_undo.cc、temp_receiver.cc：导入与目标转换。

    07 / RETAINED RESULTSFETCH 保存的是结果，不是再次执行查询的配方

    同一次 EXECUTE 生成的物化结果已经确定。后续 FETCH 主要改变读取位置；重新 EXECUTE 则产生新的结果代。

    源端怎么找到 PS 对应的 cursor

    cursor 本来就由源 PS 持有。捕获记录它所属的源 statement ID、结果 generation、列／文件描述和位置。没有开放 cursor 时，计数可跳过 PS map；存在 cursor 时，每轮发现和 final 仍要扫描 map、筛选与校验；续段按 statement ID 查找并核对同一活 artifact。这里没有重新解析每条 SQL 来猜它“可能有结果”，也不能宣传任意 PS 数量下整个捕获都是 O(1)。

    SQL 字符串相同不代表同一个 PS；PS ID 相同也不证明跨生命周期仍是同一个对象。generation 表示结果代次，不是 PS 生命周期编号。恢复关联必须取系统既有 PS 链路的权威回放记录中的同一源 PS，而不是按 SQL 文本或目标分配顺序猜测。

    边界命令如何影响结果

    命令／事件结果状态迁移应做什么
    正数 FETCH，未读完同代内容不变，消费位置前进。复用封存内容，在最终边界保存正确位置。
    FETCH 恰好取完最后一行可能仍报告 CURSOR_EXISTS，尚未探测下一行。允许保存“行数已取完但仍开放”的状态；下一正数 FETCH 返回 EOF。
    FETCH 请求超过剩余行数探测 EOF，发 LAST_ROW_SENT 并关闭 cursor。不得在 final 复活已关闭结果。
    FETCH 0不推进，也不额外探测 EOF。保持原位置与开放状态。
    RESET关闭当前 cursor，PS 本体仍在。旧结果不再关联；后续 PS 生命周期仍走原生规则。
    再次 EXECUTE旧结果关闭；可能建立新结果代。仅保留最终有效代，不能接上旧代位置。
    CLOSE销毁 PS；协议无响应包。保留静默语义，按 proxy CLOSE 补发合同处理切换边界。
    普通 COMMIT／ROLLBACK结束事务不必然关闭现有物化 cursor。以实际 open／位置有效性判定；RELEASE 或断连另按 session 清理。
    网络发送失败／位置失效无法证明完整批次成功边界。不能把不确定位置当成有效快照，不能宣称无条件恰好一次交付。

    物化以后，即使源查询依赖的表继续变化，结果仍是生成时的那一份。即使查询用过用户临时表，cursor 恢复也不再执行 SELECT；临时表恢复为后续 DML 服务，结果文件恢复为后续 FETCH 服务。

    捕获从 DRAIN Phase1 开始。DRAIN 前只保留源 ID、原输出字符集、位置有效性及空引用，不分配迁移缓冲或写文件。Phase1 新 EXECUTE 在原生结果表成功插入后，将完整行编码到有界内存环，既有 worker 同时发送；行回调不取互斥锁、不写文件、不等待网络。环满、超大行或可选分配不足时继续原生查询，随后回退至安全扫描。

    存量结果和回退结果由既有 worker 在安全命令读等待区短时借用业务 session，分段扫描物化结果；每段恢复原生 FETCH 书签、诊断区和 TLS 后归还。stop purge 后、T0 前关闭新 producer admission，补齐已注册 owner 的宣告并沿原期限完成有限采样；final 在 freeze/detach 前补齐必要尾部。两条路径复用值格式、预算、worker 和最终选择。首轮完成、文件发送完与 receiver PREPARED 分别确认。

    源码核对：位置、代次与 EOF
    • result_pretransfer.cc：开放 cursor 计数和 PS map 捕获；result_transfer.cc：final 选择，完整批次要求 fetch_count == fetch_limit。
    • cursor_file.cc、result_manifest.cc：不可变文件与最终描述。
    • result_cursor.cc：factory 定位、FETCH 循环、位置失效和 EOF；sql_prepare.cc：RESET／EXECUTE／CLOSE。

    08 / RESTORE & ATTACH先采用资源，再把 cursor 交给回放后的 PS

    在线升主只扩展三个既有接点

    接点准确入口
    升主前置preserved_trx_prepare_before_trx_sys_init_for_physical_promotion()
    InnoDB 事务链初始化trx_lists_init_at_db_start() 中已有 Preserve 接口
    采用 epochpreserved_trx_adopt_ready_epoch_for_physical_promotion()
    SQL 恢复入口Sql_cmd_resume_preserved_transaction::execute()

    SQL RESUME 交接的是 owner

    receiver 已准备的事务、TEMP 和结果集合由既有 lease／journal 管理。RESUME 将它们交给目标业务 THD，不创建 PS，不重放 SELECT。TEMP 安装仍包含逐表注册、打开 SQL 对象和小型分配；结果集合暂存为待关联 owner。不能把 RESUME 描述为绝对零成本的指针交换。

    控制连接与执行上下文要分开：proxy 通过新主上的独立控制连接发起接管，物理复制工程用既有机制在目标业务 session 完成 RESUME。当前 strict RESUME 内部要求正确的目标执行上下文；本文不把 cursor attach 的跨 THD 合同扩大成“SQL RESUME 可直接用任意控制 THD 替代业务 THD”。回放完成后，下面的关联接口明确允许 current_thd != target_thd，且不切换 TLS。

    给物理复制工程的显式接口

    enum class Preserve_cursor_attach_status {
  ATTACHED, NO_CURSOR, ALREADY_ATTACHED, ERROR
};

Preserve_cursor_attach_status preserve_trx_attach_cursor_after_ps_replay(
    THD *target_thd,
    uint32_t source_statement_id,
    Prepared_statement *target_ps);
    1. 取权威映射。从刚完成的同一条 PS 回放记录取得源 statement ID 和 target_ps；保持原 ID，PS 已进入目标 map。记录须属于此次恢复的同一逻辑 session，不能跨恢复轮次复用。
    2. 校验实际对象。调用方和目标均有效、未 killed；目标有有效结果 owner；PS 的 THD、ID 与 map 中对象一致。
    3. 查已认证 final 清单。按源 ID 查找选中的结果，只能用该条目的 generation、文件身份与最终位置。找不到条目是 NO_CURSOR；缺少恢复 owner 是 ERROR。
    4. 先 bind，再移交。目标没有冲突活 cursor；先完成可能失败的小型协议缓冲准备，再把 cursor 移到目标 PS 并减少 pending。
    5. 完成所有必要关联和 CLOSE 补发后放行。不能因为 SQL RESUME 已成功，就让业务访问只恢复了一部分的 session。
    返回值含义及调用方处理
    ATTACHED对应 cursor 已移交，之后按保存位置 FETCH。
    NO_CURSOR有效恢复的 final 结果清单不含该源 ID；不修改目标 PS，也不检查其现有 cursor 冲突。可继续回放，不表示已证明目标没有 cursor。
    ALREADY_ATTACHED同一存活 PS 仍持有同一开放结果身份；重复调用不重置位置。
    ERROR上下文、对象、身份、活 cursor 冲突或绑定失败；停止业务放行并清理失败的恢复会话。

    pending 归零后仍保留小型最终条目记录，用于识别合法重复调用。EOF、RESET、再次 EXECUTE 或 CLOSE 后，旧结果不能重新挂回去。接口不会仅凭相同裸指针判定相同结果，也无法凭 ID 证明 PS 回放模块回放了正确 SQL；这项对应关系由权威回放记录保证。

    仍有 pending cursor 时拒绝再次 Preserve；即使 pending 已归零，非空 Ready owner 的 entries 仍在，不能在同一 THD 上直接叠加另一轮 RESUME，需按既有 reset／cleanup 释放旧 owner。这里只指会话资源生命周期，不增加 RESET DRAIN 行为。重复 attach 的幂等性不等于整轮迁移可任意重复；连续迁移仍属 V06 独立集成验收。

    关联时不重新读整份文件、不重复计算结果摘要；但协议 bitmap 缓冲仍可能分配，失败必须保持原所有权。目标原生 cursor 若已关闭，不重复 close；其后续原生生命周期仍保留。

    源码核对：四个入口与三参 API
    • preserve_trx_promotion.cc：prepare／adopt；trx0trx.cc：trx_lists_init_at_db_start()。
    • preserve_trx.cc：Sql_cmd_resume_preserved_transaction::execute() 与 strict target 上下文 gate。
    • result_restore.h、result_restore.cc：owner／journal／接口及返回值；result_cursor.cc：Protocol_binary::bind_preserved()。
    • 回放与接口完整合同；安装成本边界。

    09 / SCENARIOS把设计放回真实使用场景

    场景保存与恢复验收重点
    仅用户临时表持续 DML目录＋DATA＋必要 undo；恢复后继续 DML 和事务操作。行值、主／次索引、AUTO_INCREMENT、保存点与回滚一致。
    仅开放 cursor，已 FETCH 部分结果独立结果文件＋最终消费位置；PS 由已有链路回放后关联。原 ID 对应正确，内容顺序不变，无重复／遗漏。
    临时表与 cursor 同时存在两条资源线在同一最终会话边界汇合。TEMP 后续更新不改写已物化结果，二者生命周期独立。
    一个 session 有多个 cursor逐源 PS ID 选择各自 generation 和位置。不能串游标，不能共享错误的 decoder 位置。
    cursor 已取完但 EOF 尚未探测保留开放状态和末尾位置。下一正数 FETCH 只完成 EOF，不重复最后一行。
    业务中反复 EXECUTE／RESET／CLOSE淘汰旧代；final 仅选当前有效结果。迟到 worker 不复活资源；换代副本仍计入额度。
    receiver 正在使用临时表新资源分配与保留规则隔离迁入空间。既有表和后续本地 CREATE 都不冲突；实际升主保活另验。
    所有事务已提交，survivor 为 0按既有零 token／session-only 分支收敛。0 survivor 本身不等于 DRAIN 失败；与 token abort／fail 分开统计。
    源端命令持续很久等待完整命令边界或既有超时处理。不能为追求 2 秒指标截断执行栈；量清业务等待与捕获尾部。
    RESUME 失败遵循不可回退边界和既有清理。proxy 关闭前后端、结束逻辑会话；不重试／不回池／不补发 CLOSE。

    CLOSE 无响应，为什么仍能完成切换

    补发交付不确定时不能释放业务；SQL RESUME 失败则前后端都断开，CLOSE 记录随该逻辑会话丢弃。本工程不增加跨端 close-event 通道，也不要求通用命令前缀回放。

    10 / OWNERSHIP & FAILURE并发正确性必须延续到最后一个使用者

    取消任务、记录完成、收到 ACK，都不代表文件和对象已经无人使用。资源回收必须跟随实际引用，状态发布必须再次核对身份。

    风险必须保持的规则
    异步捕获读到已经释放的表／文件边界捕获、pin／lease 与既有操作许可配合；借用对象不能逃逸其有效期。
    旧 ACK 清掉新变化N 的 ACK 只确认 N；不能清 N+1 的 dirty，也不能删除仍需重试的唯一文件。
    已取消／终结 token 被迟到 worker 再次入队发布时核对终态与拥有关系；取消后等待实际使用者退出再收回资源。
    final 与候选清理并发用所选索引与对象 pin 固定依赖，复用前核对 epoch／token／object／generation／摘要。
    预算看似释放，实际副本仍堆积处理中的、退休的及清理债务都跟真实资源生命周期记账，不用逻辑标记提前归零。
    跨 THD 关联时 PS 被销毁调用方的既有接管机制保活且独占；接口不接受悬空对象，不以 current_thd 相等充当锁。
    恢复了一半又重复 RESUME以既有 activation 状态机判定是否可回退，不凭某个局部 journal 尚未 commit 推断可重试。

    失败按阶段收敛

    1. 捕获／编码／传输失败：不发布虚假的最终成功。按既有 DRAIN、超时、取消或 token 失败策略处理；错误不能被当成“本来没有资源”。
    2. ACK 不确定：由既有请求身份、摘要和状态查询／重试策略判定，已知语义错误和网络不确定要分开。无法确认的恢复身份不能无条件释放 fence。
    3. receiver 准备失败：可选 Phase1 结果候选准备失败，可以由 final 对同一文件重新验证和准备。发布前必要校验或 cursor 准备仍失败的 token 不得 READY，可按既有 selection 规则排除；已发布 TEMP 的后台写入或依赖准备失败，记录本 token 的失败终态并拒绝其 SQL RESUME，不再改写已冻结的 epoch 选择。局部 token 失败与 epoch 全局失败分别处理。
    4. RESUME 激活前失败：仅在既有允许回退的边界内归还相同 owner；激活后走不可重试失败收尾。
    5. 回放／attach 失败：不放行业务，清理部分恢复的 session。bind 失败不覆盖现有目标 cursor，也不丢弃待关联结果。

    在线清理与启动垃圾清理各有职责

    在线资源释放依赖最后使用者、owner 析构和原生 session／PS 清理。进程重启时可以异步扫描清理本特性留下的垃圾工件，但这不等于恢复本地临时表，也不能代替在线内存、原生 undo 和活文件句柄的管理。新功能不增加 RESET DRAIN 分支。

    FETCH 到 EOF 会关闭 decoder／文件引用；PS 持有的小型 cursor／sender 对象可能延续到 RESET、再次 EXECUTE、CLOSE 或析构。额度应跟随这些对象的真实生命周期，不能声称 EOF 立即释放全部开销。

    源码核对：所有权与错误边界

    preserve_trx_resource.h、receiver_retired.cc、receiver_candidates.cc：租约、退休和候选；result_restore.cc：stage／commit／rollback／attach；temp_gc.cc：垃圾工件处理。具体失败路由沿用主状态机，不能用局部资源状态覆盖它。

    11 / PERFORMANCE目标是减少总工作，并让工作提早完成

    用户关注两个不同端点：严格 Phase2 约 2 秒和receiver ACK→READY 小于 500 ms。仅使源端捕获变快，或使 ACK 提前返回，并不能同时达成它们。Phase1 必须推进到 receiver 已处理足够充分。

    处理减少的成本不能夸大的部分
    同代结果封存复用FETCH 只推进位置，避免反复编码和传输相同行。重新 EXECUTE 的结果代不能盲目复用；有 cursor 时仍可能遍历 PS map。
    TEMP BASE＋DELTA／稀疏表示少传、少写未变页和全零块；复用兼容目标资源。逻辑长度扫描、摘要和关系校验仍可能存在，不是全流程 O(delta)。
    receiver 候选预准备把解码、页转换和原生资源准备前移。PREPARED 不是 READY，final 仍要准确消费和完成最终准备。
    固定 final 索引和 pin避免每批复制整条大记录和反复扫描无关历史对象。复用需验证身份、退休状态及最终依赖。
    有界批次＋既有 worker 并行缩短轮转间隔，让捕获、发送、目标准备重叠，控制并发副本。增加线程数不必然增加吞吐；共享锁、I/O 与内存仍可能瓶颈。
    结果批次先交付，再查准备状态避免首个结果的等待挡住后续文件进入流水线。查询失败要按真实错误处理，不能伪报已准备。
    去掉固定发送／receiver 限速与固定让步等待让已有流水线充分使用可用吞吐。预算、credit、backpressure、deadline 仍保留；人工故障限速仅用于指定测试。

    如何知道 receiver 真的跟上了

    Phase1 的 QUERY_RESOURCE_PREPARED 针对确切候选身份查询目标进度。尚未就绪的工作按既有调度的 not-before 方式重排，避免持 worker 睡眠；等待受 Phase1 期限约束。未确认时不能谎报 PREPARED，必要时由 final 路径继续收敛。请求接受 ACK 与候选 prepared 都不能代替 epoch READY。

    结果候选 prepared 可复用已校验 decoder；最终准备还要按 final 描述构造 cursor／sender、定位最终消费位置。TEMP 兼容代可以复用目标空间、undo 和私有 DATA writer；布局或 undo 历史不兼容时走重建／拒绝规则，不为提高复用率牺牲一致性。

    12 / SCOPE & INTEGRATION明确约束，避免把局部能力扩大成承诺

    边界规定
    运行模式本扩展针对 standby transfer → 物理备机在线升主 → SQL RESUME。local startup 恢复和新 RESET DRAIN 行为不在范围内。
    事务保存时机完整命令边界或既有超时；不迁移执行中 SELECT／CALL／存储程序的调用栈，不在多命令执行中任意切断。
    协议保留 Classic 服务端 cursor；不扩展 X Protocol 或打开中的 HANDLER 支持。
    用户 TEMP 引擎现网范围为 InnoDB。其他引擎不按此方案承诺。
    TEMP 类型与布局类型／字典／页／undo 必须通过当前 gate。TEMP GEOMETRY 不在当前列映射中；instant-column、加密、压缩／共享空间、不匹配字典、FULLTEXT／SPATIAL、多值 virtual undo 等不得泛称已支持。结果值编码采用独立规则，不能套用 TEMP 的类型排除表。
    会话上下文复用物理复制工程已实现的上下文转移，不新增通用 THD 变量迁移。局部测试比较须对齐上下文；不能将测试未对齐解释成现网缺能力。
    PS 本体与 LONG_DATAPS 本体由系统内部已有链路负责状态转移与回放。本临时资源层不重复建立 PS 迁移／重建及 LONG_DATA 拒绝子系统；本次表述修正不新增 LONG_DATA 支持承诺。cursor 关联必须使用原 ID 和权威回放记录。
    部署参数strict 在线升主合同要求两端 log_bin=ON、gtid_mode=ON。临时 ID namespace 需按一致拓扑合同启用；不能从 no-bin 测试通过推导其支持商业在线升主。
    源／目标协议兼容OPEN／ACK 协商能力及 ID 合同；未知格式、身份不符或不支持的关系不能静默降级。
    客户端连续性前端连接保持，后端由 proxy 重建；不承诺前端断连后的旧缓存恢复，不改变 FETCH 协议。
    目标资源保活READY 前准备的目标空间、undo、字典在实际物理 replay／升主中保持有效；必须在完整物理复制工程中核验。
    并发调用attach 全程由既有接管机制独占并保活目标 session；不支持并发业务／PS map 变动／清理。

    支持条件、预算与捕获时机

    采用已确认的内存预算、runtime profile 和 ID namespace 默认值；结果捕获已统一延后到 DRAIN Phase1，不再保留独立 enable 参数。显式启动参数或配置文件仍可覆盖这些默认值；历史压测结果保留当轮配置，不据此宣称新默认值已完成性能验收。

    配置／条件当前默认和含义
    rds_preserve_trx_memory_budget_bytes默认 2 GiB（2147483648 字节）；通用 heap lease 额度，不是启动预分配内存，也不改变 inflight 和结果文件额度。
    rds_preserve_trx_transfer_runtime_profile默认 PROMOTION_PREPARE；使用既有并发、分块和 binlog prefix 提前准备策略。源端 DRAIN 与 receiver epoch 分别冻结本机配置；修改全局值不会改写已冻结的策略。
    rds_preserve_trx_temp_table_enable默认 ON；控制受约束的用户 InnoDB TEMP 支持，仍须满足整体 Preserve 和模式要求。
    结果捕获时机Preserve ON、standby_transfer_save、Classic 协议下，在 DRAIN Phase1 自动启动；独立 capture_enable 参数已删除。DRAIN 前只记录轻量身份和安全读等待事实，不创建捕获文件。
    rds_preserve_trx_result_capture_max_bytes启动只读，默认 1 GiB；限制本实例活结果捕获文件的字节量。它不是可忽略的开销，也不等同于全部 Preserve 内存预算。
    rds_preserve_trx_temp_id_namespace启动只读，默认 ON；按拓扑一致性合同启用，见下文。

    DRAIN 前已存在的开放 cursor 也在 Phase1 采样范围内；无需在创建结果前提前编码。最后仍未封存的活结果在 freeze/detach 前由同一捕获核心补齐，失败按既有拒绝／清理处理。transfer、物理升主和 SQL RESUME 仍须满足各自合同；修改预算不能代替性能验收。

    临时 ID namespace 是启动配置合同

    rds_preserve_trx_temp_id_namespace 是启动只读配置，默认 ON。启用时临时 ID 命名空间规则即使在 Preserve 功能关闭时仍然有效；所有物理写入方必须遵守兼容的持久 ID 上限。不能运行中随意切换，也不能把一次成功 OPEN 当成整个物理复制生命周期已经验证。

    集成验收应检查四个交接面

    1. 物理升主接点：按现有 prepare → trx_lists hook → adopt 调用；验证目标原生 TEMP／undo 不被重新初始化或覆盖。
    2. 控制连接接管：已有机制保证目标 session 生存和独占，RESUME 执行上下文正确，attach 保持控制诊断与业务资源分离。
    3. PS 回放与关联：逐条权威映射，原 ID 不变；多 cursor、同 ID 重用和重复调用都不能接错结果。
    4. proxy 放行：必要关联完成、CLOSE 补发顺序正确；失败关闭逻辑会话，未知交付不释放业务。

    物理复制工程已经有在线升主与 session／PS 能力。PS statement 的源端序列化、向 receiver 传输及目标回放属于系统内部已有能力（按用户确认的工程事实）。本仓库尚未逐字段核查该完整工程，也未用真实全链路完成本轮验收；这是源码与运行证据边界，不是系统内外的划分，更不意味着需要重建这些机制。

    边界的源码与部署依据

    sys_vars.cc：rds_preserve_trx_temp_id_namespace；trx0temp_preserve_id.h：命名空间约束；trx0temp_preserve_source.cc、trx0temp_preserve_dict.cc：布局 gate；promotion.cc：严格升主资格。

    术语速查

    术语本文含义
    epoch / tokenepoch 是迁移批次；当前 standby token 取源 THD 连接 ID，标识该批次内恢复对象。它不是新业务连接 ID，也不能脱离 epoch／恢复身份使用。
    BASE / DELTA资源基础镜像与相对其依赖的变化；当前不指本临时资源模块中已移除的重复 PS 传输实现，也不替代系统已有的 PS 序列化协议。
    generation结果或资源代次，用来隔离换代；不能单独证明 PS 生命周期。
    sealed file / pin已封存的不可变文件／使实际资源在使用期间保持存活的引用。
    candidate prepared指定候选准备完成；仍须 final 选择、证明和发布。
    final ACK / READYreceiver 接受最终请求／所选 epoch 达到可采用状态；两个不同完成点。传输协议 COMMIT 不等于业务 SQL COMMIT。
    owner / journal / lease资源归属／分阶段安装与回退记录／绑定实际资源生命周期的持有凭据。
    strict Phase2 / EXACTT0 到 Phase2 结束／最后 eligible 命令 BODY 到 final ACK；互不替代。

    容易误解的五个问题

    删除重复 PS transfer 后，系统还会传输 PS 吗？

    会。系统内部已有链路仍在源端序列化 PS statement 并发送给 receiver，随后在 RESUME 后回放。本临时资源模块只承担 TEMP 和开放 cursor 结果，不再重复捕获和传输 PS 本体。PS 数量仍会影响既有链路的工作量，端到端验收需要计入其序列化、传输和回放成本。结果模块在没有开放 cursor 时可以快速跳过；有 cursor 时仍可能扫描 PS map。

    COMMIT 后是不是肯定不能 FETCH？

    不能这样概括。当前 Classic 物化 cursor 的是否开放、RESET／EXECUTE／CLOSE、EOF 和断连决定可用性。普通 COMMIT／ROLLBACK 不统一关闭全部物化 cursor；RELEASE 导致断连另算。

    只把 Phase1 拉长，就能保证 Phase2 很短吗？

    不能。要确认源捕获、传输、receiver 转换／准备都实际推进，而且业务产生的新代和尾差受控。延长时间不能消除串行等待、重复工作、处理能力不足或长命令本身。

    READY 后能否直接开始 FETCH？

    不能。还要经过既有升主、正确 session 上的 SQL RESUME、系统内部 PS 回放和必要 cursor 关联，以及约定的 CLOSE 补发。READY 只是资源可被采用的端点。

    新主已有临时表，会不会被迁入的源 space ID 覆盖？

    当前导入计划取得目标空间并保留身份；目标分配器跳过保留资源，既有表继续独立使用。整个物理复制期间这些目标资源的保活还需按完整系统集成合同验证，不能凭一次本地导入就宣布全链路证明。
