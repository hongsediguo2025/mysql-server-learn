RESET DRAIN：从 SQL 语句到内核恢复接口

以当前工作区源码为准，解释 RESET 会话如何发布取消、如何与 final ACK 竞争，以及原 DRAIN 线程如何把已经 preserve/detach 的事务安全地还给原连接。

控制模型协作式取消，不是异步强杀
执行恢复者原 DRAIN owner 线程

最终结果原 THD 重新持有 ACTIVE trx

1. 核心结论

RESET DRAIN 没有对应单一的 InnoDB reset API。它通过 attempt 终态 CAS 发布取消，由原 DRAIN 调用栈在安全检查点执行语义恢复。

一句话模型 RESET 会话负责“提出并等待撤销”；DRAIN owner 负责“真正撤销”；InnoDB 最终负责“重新挂载并激活事务”。

RESET 会话

检查权限和自身事务状态，执行 RUNNING → RESET_REQUESTED，取消 source sink，并等待所有目标事务重新 runnable。

DRAIN owner

在 phase1/phase2 检查点观察 reset；停止 admission、恢复已 detach token、清理 warmcopy 与 transfer 资源。

InnoDB 内核

将 preserved trx 重新关联原 THD，把状态改回 ACTIVE，再激活 redo/no-redo undo 状态。

3. SQL 入口与命令执行

3.1 Grammar 与命令码

语法规则把两个关键字映射为独立命令码，不创建专用 Sql_cmd 对象：

reset_drain_stmt:
  RESET_SYM DRAIN_SYM
  {
    Lex->sql_command = SQLCOM_RESET_DRAIN;
  }

mysql_execute_command() 将该命令和其他 Preserve 控制命令一起交给 preserve_trx_execute_command(thd)。

3.2 SQL executor 的前置条件

SQL executor 调用 preserve_trx_request_active_drain_reset(true)。参数 true 表示命令返回前要等待原事务重新 runnable，不能只发布一个异步请求就立即返回。

4. RESET 与 final ACK 的原子仲裁

RESET 和 shutdown handoff 竞争同一个 Preserve_trx_drain_attempt::terminal，从而给 ownership 转移建立唯一顺序。

RUNNING ──RESET──▶ RESET_REQUESTED   |   RUNNING ──FINAL_ACK──▶ SHUTDOWN_HANDOFF

RESET 先赢

  • CAS：RUNNING → RESET_REQUESTED。
  • manager 进入 RESET_CLEANUP。
  • 当前 source transfer sink 收到 request_cancel()。
  • final ACK arbiter 不能再取得 shutdown handoff。

final ACK 先赢

  • CAS：RUNNING → SHUTDOWN_HANDOFF。
  • source ownership 已跨过不可撤回边界。
  • 后来的 RESET 返回 ER_PRESERVE_TRX_RESET_TOO_LATE。
  • source 不再尝试撤回 receiver 已接管的状态。
为什么不能使用两个独立布尔值 若 reset 与 final ACK 分别写不同变量，两个线程可能都认为自己获胜。共享 terminal CAS 保证只存在一个最终所有者决定。

5. 谁执行真正的清理

RESET 会话不会遍历目标 THD，也不会直接调用事务恢复接口。它只做以下控制动作：

  1. 发布 RESET_REQUESTED。
  2. 把 manager 状态推进到 RESET_CLEANUP。
  3. 取消 source transfer sink。
  4. 等待 all_transactions_runnable 或 reset_failed。

真正清理发生在原 DRAIN 线程。该线程在 source epoch open、record/binlog streaming、manifest、WARMCOPY_CLOSING、target wait、phase2 catch-up、XID provenance 和 final metadata 等位置检查 reset_requested()。

6. Phase1 撤销路径

Phase1 尚未完成事务 detach，主要工作是停止 admission/streaming 并恢复 batch 状态，不需要执行完整的 preserved-record reattach。

finish_phase1_reset(stage)

  1. 终止 phase1 batch sender，停止继续排队和发送对象。
  2. 关闭 warmcopy admission，并关闭 lock warmcopy epoch。
  3. 清除目标 THD 的 generation 和 batch state。
  4. 标记原事务 runnable。
  5. abort drain participants，释放 source session、sink 和 provider。
  6. manager 从 RESET_CLEANUP 回到 IDLE。
结果 原连接继续持有原事务；原 DRAIN 命令返回 ER_PRESERVE_TRX_DRAIN_RESET，明确表示本次 drain 未进入 shutdown handoff。

7. Phase2 语义恢复路径

Phase2 可能已经把部分事务 preserve/detach。此时必须先恢复事务语义和 ownership，最后才能删除 artifact。

7.1 Batch 恢复顺序

  1. finish_phase2_reset() 停止 admission。
  2. 若尚无 detached token，只清 batch generation/state。
  3. 若已经 detached，调用 restore_preserved_batch_items_to_original_thds()。
  4. 按 preserve 的逆序恢复 token，降低部分发布场景下的所有权交错风险。
  5. 全部语义恢复成功后，才标记原事务 runnable。
  6. 随后清 snapshot、detached MDL context、XID provenance 和进程内 warmcopy 状态。

7.2 单 token 恢复内容

顺序恢复对象关键动作
1Preserved recordpreserved_trx_take_record(token) 取得唯一 ownership
2Session facts恢复隔离级别、事务访问模式、DML policy、last insert id、user vars 等
3Binlog cache优先重新激活 retained native cache；必要时导入已保存 payload
4MDL将 detached transactional MDL context 转回原 THD
5GTID恢复事务原来的 GTID ownership/state
6InnoDB trx重新挂回原 THD，并从 preserved/prepared 转回 ACTIVE
7Savepoints恢复事务保存点结构
8Undo state激活 redo 与 no-redo undo 状态

失败语义 如果语义 reattach 失败，代码不会把事务伪装成已经 runnable。DRAIN owner 设置 reset_failed 并返回 batch cleanup failure；RESET 等待者收到 unsupported/error，而不是错误地报告 reset 成功。

8. 最终落到哪些内核接口

RESET DRAIN 没有单一的“最后一个接口”；它最终落到事务、undo、lock warmcopy、binlog 和 MDL 五类恢复边界。

事务重新挂载

trx_preserve_reattach_preserved_to_original_thd(trx, thd)

  • 验证 magic XID 与 detached ownership。
  • 在 trx_sys_mutex 下将状态恢复为 ACTIVE。
  • 恢复 trx->mysql_thd。
  • 调用 replace_native_transaction_in_thd()。
  • 重新执行 server/handlerton 事务注册。

Undo 激活

trx_preserve_activate_reattached_in_original_thd(trx, thd)

  • 确认事务已 ACTIVE 且属于目标 THD。
  • 激活 redo rseg undo。
  • 激活 no-redo temp undo。
  • 必要时持久化 prepare-state 转换。

Lock warmcopy 关闭

lock_warmcopy_close_epoch() 将 active epoch 发布为 0，停止后续 warmcopy hook。

lock_warmcopy_record_store_clear_for_target() 清除目标的进程内 record store 与 journal 状态。

Server 层资源恢复

Binlog cache 通过 reactivate/import 路径恢复；detached MDL context 转回原 THD；GTID 和 savepoint 在事务激活前后按既定次序归还。

内核完成态 原客户端连接重新拥有同一个 InnoDB trx_t，事务状态为 ACTIVE，可以继续执行 DML，并最终 COMMIT 或 ROLLBACK。

9. Receiver 与网络边界

RESET DRAIN 是 source-local ownership 撤销，不是跨节点反向事务 当前协议没有 RESET frame。RESET 赢得仲裁后，source 取消 sink 并恢复原事务；receiver 已收到的 partial staging 由 receiver 自身 lifecycle、TTL 或未来 HA 策略处理。

10. 两个会话的返回语义

RESET 成功不是让两个命令都返回 OK。两个会话承担不同角色，因此返回结果不同：

RESET 会话

  • 赢得 reset：等待恢复完成后返回 OK。
  • 加入已有 reset：等待同一结果后返回 OK。
  • manager 已 IDLE：幂等返回 OK。
  • handoff 已完成：返回 ER_PRESERVE_TRX_RESET_TOO_LATE。

原 DRAIN 会话

  • 安全 unwind 成功：返回 ER_PRESERVE_TRX_DRAIN_RESET。
  • 语义恢复失败：返回 batch cleanup failure。
  • final ACK 先赢：继续原 shutdown handoff 路径。

这种分工让控制会话得到“撤销已完成”，同时让原执行者明确知道“DRAIN 没有正常完成”。

11. 当前能力范围

问题当前答案
是否是通用 KILL DRAIN？不是。它是受状态机约束的协作式 reset。
是否覆盖所有 local-carrier DRAIN？不是。当前 active attempt 在 standby-transfer streaming 路径创建。
是否向 receiver 发送撤销命令？不发送。receiver 生命周期独立处理 partial staging。
是否能跨过 final ACK 撤回？不能。shutdown handoff 是 source ownership 的不可撤回边界。
是否直接回滚用户事务？不是。正常 reset 是把事务恢复到原 THD 继续执行。
OFF/IDLE 下执行是否报错？manager IDLE 且无 active attempt 时幂等成功，不触发 Preserve 内核工作。
