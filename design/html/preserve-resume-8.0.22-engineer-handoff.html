1. 背景和来龙去脉

Preserve/Resume 的目标来自受控维护窗口：业务中存在未提交长事务，传统重启会迫使事务回滚，而普通 XA recovery 只能保留 prepared transaction，不足以还原完整 SQL session 语义。该特性选择把事务转换成 durable token，并保存恢复所需语义，重启后由用户显式 resume。

8.0.22 port 的特殊点是：源实现来自较新的 8.0 代码结构，而目标分支保留 8.0.22 的 XA、协议、parser、handler 和 InnoDB 组织方式。因此移植不是逐文件复制，而是对象级映射：SQL 命令、THD 状态、InnoDB trx、锁、MDL、binlog cache、临时表 sidecar 都要在 8.0.22 对应位置落地。

后续重点从“功能可保存/恢复”扩展到两件事：第一，降低对原生 8.0.22 热路径的侵入，保持 preserve_trx_enable=OFF 时原路径只剩轻量分支；第二，优化 batch drain phase 2 阻塞窗口，让大锁数 workload 目标接近 1 秒，同时功能上即使超过 1 秒也继续正确执行。

3. 关键算法与状态机

3.1 Preserve Kernel 算法

  1. 检查开关、权限、协议、显式事务、XA/复制/升级/force recovery。
  2. 导出 binlog state、read view、lock payload、MDL descriptors、savepoint、临时表 manifest。
  3. 把 token 映射为 magic XID，调用 prepare。
  4. 从 THD detach InnoDB transaction，使 prepared trx 由 preserve token 持有。
  5. 写 snapshot 和 sidecar，注册内存 record。
  6. 响应 token；响应失败或 cleanup 失败时按 durable point 语义处理。

3.2 Warmcopy 算法

Warmcopy 的核心思路是把大对象工作提前到 drain 第一阶段。binlog warmcopy 复制 transaction binlog cache prefix，phase 2 只补 tail。lock warmcopy 当前已有 record store、canonical compare、fallback、conversion freeze 等基础；要达到 1 秒目标，需要发展为 phase 1 authoritative mirror 和 external artifact。

5. 代码阅读路线

建议按“用户命令到 durable artifact，再到 InnoDB 对象”的顺序阅读，避免一开始陷入某个单文件细节。

用户命令从 PREPARE SHUTDOWN PRESERVE TRANSACTION、DRAIN TRANSACTIONS PRESERVE、RESUME PRESERVED TRANSACTION 和 SHOW PRESERVED TRANSACTIONS 开始追踪。参数入口重点关注 preserve_trx_enable、preserve_trx_warmcopy_max_total_bytes、preserve_trx_lock_warmcopy_enable、preserve_trx_parallel_preserve_threads。

  1. 先读 sql/sql_yacc.yy、include/my_sqlcommand.h、sql/sql_parse.cc，理解命令入口和 gate。
  2. 读 sql/preserve_trx.cc 中单事务 preserve、batch drain、resume、recovery 的主流程。
  3. 读 sql/preserve_trx_bundle.* 和 sql/preserve_trx_carrier*，理解 snapshot 格式和文件生命周期。
  4. 读 sql/binlog_warmcopy.*、sql/binlog.cc、sql/binlog_ostream.cc，理解 logged transaction cache 的保存和 warmcopy。
  5. 读 sql/preserve_trx_lock_warmcopy.*、storage/innobase/lock/lock0preserve.cc、lock0warmcopy.cc，理解锁 payload、fallback 和 conversion freeze。
  6. 读 storage/innobase/trx/trx0preserve.cc、read0read.cc，理解 trx claim、attach、read view、savepoint。
  7. 读 sql/preserve_trx_temp_table.*、trx0temp_preserve.cc，理解用户临时表 sidecar。
  8. 最后读 P_S、status、lint、MTR 和 NFR 脚本，理解发布证据和回归边界。

7. 约束、风险和后续工作

  • 低侵入原则：preserve_trx_enable=OFF 时原生路径应只留下轻量分支，不能有 payload 构造、文件 I/O、大扫描或错误语义变化。
  • All-or-live：同一 target 的 record/table/MDL/savepoint 不能混用不同时间点 payload。
  • Phase 2 1 秒：当前是目标路线；需要 phase 1 authoritative mirror、external lock artifact、bounded tail 和并行 target preserve。
  • Temp table：用户临时表恢复涉及 DD、dict、fil space、dirty page、no-redo undo，任何不完整形态都应 fail closed。
  • 复制集群：跨机 sidecar 同步、promotion 编排、GTID/位点协议、旧主隔离还需单独实现。
  • Release Gate：本地 preserve/resume 证据不等于全 MySQL release gate 关闭；最终仍需要 full all-suite 或发布负责人接受的等价证据。
