Preserve/Resume 8.0.22：已 Preserve 未提交事务为何不会被恢复回滚

目标：解释当前 preserve/resume 特性如何确保“已经成功 preserve 的未提交事务”在 mysqld 重启恢复阶段不会被普通 crash recovery rollback 掉。

结论：保障不是单靠 preserved_trx_recover_all() 调用得早，而是由 prepared 状态边界、preserve magic XID 隔离、rollback 线程状态过滤、ordinary XA recovery 排除 和 preserved_trx_recover_all() 的 token 配对/claim 共同完成。

源码基准：codex/user-temp-table-phase1-drain-resume，核查 HEAD 1b6f680d9890；路径为 /Users/a1234/project/mysql-server-8022-preserve-port。

一句话判断：普通 recovered active transaction 可以被 InnoDB recovery rollback 线程回滚；已经 preserve 成功的事务在重启后应处于 TRX_STATE_PREPARED，且携带 preserve magic XID，因此不会进入普通 rollback 线程和普通 XA recovery 的处理集合。随后 preserved_trx_recover_all() 根据 durable token 把它 claim 成 TRX_STATE_PRESERVED 并恢复锁、read view、MDL 等语义。

1. 问题边界

本文讨论的是已经 preserve 成功的未提交事务。这里的“成功”至少意味着：

  • 事务已经跨过 preserve 的 prepare 边界，InnoDB 中对应事务可在 crash recovery 后以 prepared 形态恢复。
  • 事务的 durable artifact 已发布到 preserve store，包括 snapshot metadata、必要的语义 payload、外部 blob/sidecar 描述等。
  • token 与 InnoDB prepared transaction 的 preserve magic XID 可以互相映射。

本文不讨论两类对象：

  • 普通未提交事务：它们在 crash recovery 后是 active recovered transaction，可以被 recovery rollback 线程回滚。
  • 保存失败或半成品 artifact：这类对象应由 preserve 失败处理、crash recovery 清理或 taint/rollback 逻辑处理，不应被当作可 resume 的 token。
容易误解的点：srv_start_threads() 在 innobase_post_recover() 前已经可能启动 trx_recovery_rollback_thread。所以不能把正确性解释成“rollback 线程完全没启动”。真正的正确性来自于 rollback 线程不会处理 TRX_STATE_PREPARED/TRX_STATE_PRESERVED，以及 preserve magic XID 不进入普通 XA recovery。

3. 第一层保护：prepared 状态边界

Preserve 的核心不是把普通 active transaction 留给 crash recovery，而是把它推到可恢复的 prepared 边界，并使用 preserve 专用 XID。重启时，InnoDB resurrect undo 的逻辑会把 prepared undo 恢复成 TRX_STATE_PREPARED。

if (undo->state == TRX_UNDO_PREPARED) {
  const bool preserve_magic_xid =
      trx_preserve_xid_is_magic_active(*trx->xid);

  if (srv_force_recovery == 0 || preserve_magic_xid) {
    trx->state = TRX_STATE_PREPARED;
    ++trx_sys->n_prepared_trx;
  }
}

源码位置：storage/innobase/trx/trx0trx.cc:814-833。

这层保护的含义是：

  • 已 preserve 事务在 InnoDB crash recovery 后不是普通 TRX_STATE_ACTIVE。
  • 普通 recovery rollback 线程主要处理需要 undo 的 active recovered transaction。
  • prepared transaction 的 commit/abort 决策必须由更高层明确给出；不能由 background rollback 线程擅自决定。

4. 第二层保护：recovery rollback 跳过 PREPARED/PRESERVED

srv_start_threads() 中如果发现需要 rollback 的 recovered transactions，会创建 trx_recovery_rollback_thread：

if (!bootstrap && srv_force_recovery < SRV_FORCE_NO_TRX_UNDO &&
    trx_sys_need_rollback()) {
  /* Rollback all recovered transactions that are
  not in committed nor in XA PREPARE state. */
  srv_threads.m_trx_recovery_rollback = os_thread_create(
      trx_recovery_rollback_thread_key, trx_recovery_rollback_thread);

  srv_threads.m_trx_recovery_rollback.start();
}

源码位置：storage/innobase/srv/srv0start.cc:2979-2986。

关键在 rollback 扫描逻辑。trx_rollback_or_clean_resurrected() 遇到 TRX_STATE_PREPARED 或 TRX_STATE_PRESERVED 时返回 FALSE，不做 rollback：

case TRX_STATE_PREPARED:
case TRX_STATE_PRESERVED:
  return (FALSE);

源码位置：storage/innobase/trx/trx0roll.cc:671-673。

同一文件还有直接说明：

/* Note: For XA recovered transactions, we rely on MySQL to
do rollback. They will be in TRX_STATE_PREPARED state. */

源码位置：storage/innobase/trx/trx0roll.cc:703-705。

因此：即使 recovery rollback 线程已经启动，只要 preserve 目标事务已经以 TRX_STATE_PREPARED resurrect，它就不会被该线程回滚。后续 preserved_trx_recover_all() claim 成 TRX_STATE_PRESERVED 后也同样被跳过。

5. 第三层保护：preserve magic XID 不走普通 XA recovery

如果只靠 prepared 状态，还要担心另一个问题：普通 XA recovery 会不会把这个 prepared transaction 当作普通 XA 事务接管，然后后续被普通 XA rollback/commit 处理？当前代码通过 preserve magic XID 做了隔离。

5.1 普通 XA recover 上报时排除 preserve magic XID

if (trx_state_eq(trx, TRX_STATE_PREPARED) &&
    !trx_preserve_xid_is_magic_active(*trx->xid)) {
  if (get_info_about_prepared_transaction(&txn_list[count], trx, mem_root))
    break;
  ...
}

源码位置：storage/innobase/trx/trx0trx.cc:3034-3036。

这表示 preserve magic XID 的 prepared transaction 不会被普通 XA recover 列表返回给 SQL 层。

5.2 普通 trx_get_trx_by_xid() 也拒绝 preserve magic XID

trx_t *trx_get_trx_by_xid(const XID *xid) {
  if (xid == nullptr || trx_preserve_xid_is_magic_active(*xid)) {
    return (nullptr);
  }
  ...
}

源码位置：storage/innobase/trx/trx0trx.cc:3102-3106。

这意味着普通 XA 路径不能用 XID 抢走 preserve transaction。preserve transaction 必须走 preserve 专用 claim 入口。

5.3 preserve token 与 XID 的映射

preserve token 会被编码进 XID 的 bqual 部分：

xid->set(PRESERVE_TRX_XID_FORMAT_ID, PRESERVE_TRX_XID_GTRID,
         PRESERVE_TRX_XID_GTRID_LENGTH, token,
         static_cast<long>(token_length));

源码位置：storage/innobase/trx/trx0preserve.cc:55-70。

这个映射关系让 preserved_trx_recover_all() 能从 durable token 找回对应的 InnoDB prepared transaction，同时又不会和普通 XA XID 混用。

6. 第四层保护：preserved_trx_recover_all() 配对并 claim

preserved_trx_recover_all() 是启动阶段恢复 preserve artifact 的统一入口。它做的不是“防止普通 rollback 线程回滚”这一件事，而是在普通 recovery 已经完成后，把 durable token 与 InnoDB prepared transaction 做一致性配对，并恢复事务语义。

6.1 扫描 durable token

const std::string dir = normalize_dir(preserve_trx_default_dir());
auto store = create_preserved_trx_default_store(dir);
...
Preserved_trx_carrier_listing listing;
if (store->list_tokens(&listing) != Preserve_snapshot_status::OK) {
  ...
}

源码位置：sql/preserve_trx.cc:8599-8619。

6.2 读取 snapshot，构造 XID，claim prepared transaction

XID xid;
if (preserve_trx_token_to_xid(token, &xid)) {
  return log_preserved_trx_recovery_failure(
      token, "failed to map durable transaction token to XID");
}

trx_t *trx = trx_preserve_claim_prepared(xid);

源码位置：sql/preserve_trx.cc:8162-8182。

trx_preserve_claim_prepared() 的要求非常窄：必须是 preserve magic XID、无 live owner THD、未被 claim、状态为 TRX_STATE_PREPARED，然后标记为 TRX_STATE_PRESERVED。

if (trx->mysql_thd == nullptr && !trx->preserve_trx_claimed &&
    trx_state_eq(trx, TRX_STATE_PREPARED) && xid.eq(trx->xid) &&
    trx_preserve_mark_preserved(trx) == DB_SUCCESS) {
  trx->preserve_trx_claimed = true;
  claimed = trx;
  break;
}

源码位置：storage/innobase/trx/trx0preserve.cc:258-276。

6.3 claim 后恢复语义对象

claim 成功后，恢复逻辑会导入事务隔离级别、read view、表锁、行锁、predicate locks、detached MDL context，并注册为可 resume 的 preserved record：

trx_preserve_set_isolation(trx, metadata.tx_isolation);
trx_preserve_import_read_view(trx, metadata.read_view_payload);
trx_preserve_import_table_locks(trx, metadata.table_locks_payload);
trx_preserve_import_record_locks(trx, metadata.record_locks_payload);
create_detached_mdl_context(metadata);

preserved_trx_add_record(metadata, trx, true,
                         Preserved_trx_lifecycle_state::PRESERVED,
                         std::move(bundle.blob_descriptors));

源码位置：sql/preserve_trx.cc:8233-8279。

这里的设计含义：已 preserve 事务不是只依赖 InnoDB prepared undo 存活。prepared undo 只保证未提交变更没有被普通 recovery rollback；真正能被用户继续 resume，还需要 durable snapshot 中的 SQL 层和锁语义被恢复到内存结构。

7. 孤儿 preserve prepared 为什么会被主动回滚

正确性还包括另一面：如果 InnoDB 里存在 preserve magic XID prepared transaction，但没有对应 durable snapshot token，不能把它默默保留下来。否则它既不能安全 resume，也可能永久占用锁和 undo。

preserved_trx_recover_all() 会先根据 durable listing 计算 snapshot_tokens，然后调用：

std::vector<std::string> retained_snapshot_tokens(snapshot_tokens.begin(),
                                                  snapshot_tokens.end());
uint32_t orphan_rollback_count = 0;
if (trx_preserve_rollback_prepared_without_snapshot(
        retained_snapshot_tokens, &orphan_rollback_count) != DB_SUCCESS) {
  ...
}

源码位置：sql/preserve_trx.cc:8673-8681。

底层判断逻辑是：候选事务必须是 detached、未 claim、TRX_STATE_PREPARED、preserve magic XID，并且 XID 中的 token 不在 durable snapshot token 集合里。只有这种“没有 snapshot 的 preserve prepared”才会被主动回滚。

if (candidate->mysql_thd == nullptr &&
    !candidate->preserve_trx_claimed &&
    trx_state_eq(candidate, TRX_STATE_PREPARED) &&
    candidate->xid != nullptr &&
    xid_is_preserve_magic(*candidate->xid) &&
    !trx_preserve_xid_token_in(*candidate->xid, snapshot_tokens)) {
  candidate->preserve_trx_claimed = true;
  trx = candidate;
  break;
}

源码位置：storage/innobase/trx/trx0preserve.cc:442-476。

这不是破坏 preserve 语义，而是 fail closed：有 durable snapshot 的 preserve transaction 被恢复；没有 durable snapshot 的 preserve prepared transaction 被视为孤儿并回滚，避免留下无法 resume 的半状态。

8. force recovery 和 read only 情况

8.1 innodb_force_recovery

当 srv_force_recovery > 0 时，preserved_trx_recover_all() 不会正常导入 snapshot，而是把发现的 preserved token 标记为 tainted 并保留文件，避免在不完整恢复能力下做危险 resume。

if (srv_force_recovery > 0) {
  ...
  LogErr(WARNING_LEVEL, ER_LOG_PRINTF_MSG,
         "PRESERVE: preserved transaction recovery is not supported while "
         "innodb_force_recovery is enabled; snapshot and binlog-cache "
         "files are retained and marked tainted");
  preserved_trx_mark_recovery_complete();
  return false;
}

源码位置：sql/preserve_trx.cc:8645-8670。

8.2 srv_read_only_mode

innobase_post_recover() 在 srv_read_only_mode 下不会调用 preserved_trx_recover_all()，只标记 recovery complete 后返回：

if (srv_read_only_mode) {
  purge_sys->state = PURGE_STATE_DISABLED;
  preserved_trx_mark_recovery_complete();
  return;
}

源码位置：storage/innobase/handler/ha_innodb.cc:3731-3734。

这对物理备机只读运行场景很关键：只读备机运行时不会通过当前本地 startup preserve recovery 路径导入本地 token。后续如果设计“物理备机在线升主时 adopt/fast resume”，应该是显式 promotion/adopt 入口，而不是让 read-only startup recovery 自动处理。

10. 实现/评审检查清单

后续改 preserve/resume、standby transfer 或 promotion adopt 逻辑时，必须保护下面这些边界：

  • 不要让 preserve magic XID 进入普通 XA recovery 列表。
  • 不要让普通 trx_get_trx_by_xid() 能拿到 preserve magic XID。
  • 不要让 recovery rollback 路径回滚 TRX_STATE_PREPARED 或 TRX_STATE_PRESERVED。
  • 不要把只有 InnoDB prepared trx、没有 durable snapshot 的对象暴露为可 resume token。
  • 不要在 claim 前删除 durable snapshot；claim 后的任何语义恢复失败都必须 rollback claimed preserve transaction 或 taint/fail closed。
  • 不要把物理备机接收保存路径塞进 preserved_trx_recover_all()；该入口是本地 startup recovery 路径。
  • 如果新增 promotion-side adopt，应显式复用 token-to-XID、store read、bundle decode、claim/import 这些底层能力，但保持入口独立，避免影响现有本地 preserve/resume 行为。

最终结论：已 preserve 未提交事务不会被普通 crash recovery rollback 掉，核心原因是它不再是普通 active recovered transaction，而是带 preserve magic XID 的 prepared transaction；普通 recovery rollback 跳过 prepared/preserved 状态，普通 XA recovery 又排除 preserve magic XID。preserved_trx_recover_all() 随后用 durable token 找回该 prepared trx，claim 成 preserved，并恢复事务语义。没有 durable token 匹配的 preserve prepared 则会被主动回滚，这是 fail closed 的清理行为。
