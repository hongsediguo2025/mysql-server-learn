1. 总体代码地图

Preserve/Resume 不是单个存储引擎接口，而是 SQL 命令、THD/session 状态、binlog cache、InnoDB 事务、锁、MDL、临时表、snapshot 文件和 P_S 观测共同构成的跨层能力。当前代码的核心分层如下：

2. SQL 命令入口与总开关

include/my_sqlcommand.h 新增 4 个命令枚举：SQLCOM_PREPARE_SHUTDOWN_PRESERVE、SQLCOM_DRAIN_TRANSACTIONS_PRESERVE、SQLCOM_RESUME_PRESERVED_TRX、SQLCOM_SHOW_PRESERVED_TRX。sql/sql_parse.cc 在 command flag 和 dispatch 中识别这些命令，并在 preserve/drain/resume/show 路径进入 preserve service。

这里的关键原则是：preserve_trx_enable=OFF 时，功能命令应被拒绝，而不是继续创建 token 或触发引擎 adapter。后续低侵入重构也应坚持这一点：非 preserve 场景只能保留必要的薄分支，不能把 snapshot、payload 或文件 I/O 泄漏到原生路径。

3. 单事务 preserve 代码链路

单事务 preserve 的任务是把当前 THD 上的事务从“活跃连接拥有”转换为“durable token 拥有”。代码层面可分成 eligibility、语义导出、prepare、detach、snapshot publish、in-memory record 注册几个阶段。

InnoDB 侧的关键函数在 storage/innobase/trx/trx0preserve.cc：trx_preserve_claim_prepared() 从 prepared XID 取得 trx，trx_preserve_detach_current_thd() 和 trx_preserve_attach_to_thd() 管理 THD 绑定，trx_preserve_activate_resumed() 把恢复后的 trx 放回可执行状态。read view 和 savepoint 分别通过 trx_preserve_export_read_view()、trx_preserve_import_read_view()、trx_preserve_export_savepoints()、trx_preserve_import_savepoints() 处理。

4. Batch drain 两阶段与 participant 模型

batch drain 的核心对象是 Preserve_trx_drain_orchestrator。它维护 participant 列表，并按顺序调用 open_phase1_participants()、close_phase1_participants()、ensure_phase1_ready()、phase2_preflight_participants()、finalize_participants() 或 abort/cleanup。当前已接入的典型 participant 包括 binlog warmcopy 和 lock warmcopy。

重要边界：phase 2 是用户可感知阻塞窗口，当前优化目标是把 full workload 下的 phase2_total_ms p95 收敛到约 1 秒，稍高于 1 秒时不改变功能语义。超过目标应标记 SLO miss 或走 fallback，但不应把可恢复事务变成 silent corruption。

5. Snapshot bundle 与 carrier 写入顺序

sql/preserve_trx_bundle.h 定义 Preserve_snapshot_metadata、TLV、external blob descriptor、decoded snapshot 等结构；sql/preserve_trx_bundle.cc 负责编码、认证、CRC 和解析。sql/preserve_trx_carrier.cc 的 Preserved_trx_store::write() 采用“外部对象先写或 adopt，authenticated snapshot descriptor 最后发布”的顺序。

这条顺序是恢复安全的关键：snapshot 是 token 可见性的事实源；在 snapshot 持久化前，外部 blob 只是 cleanup 候选；一旦 snapshot 写入可能已经开始，cleanup 失败不能静默丢失 prepared trx 的所有权，必须保留可观测记录。

6. Binlog warmcopy 代码解读

binlog warmcopy 的目标是把大事务 binlog cache 的存量复制提前到 batch phase 1。sql/preserve_trx_warmcopy.cc 中 WarmcopyDrainCoordinator 控制 epoch 状态：open_epoch() 发布 admission，publish_open_gate_before_enumeration() 和 reconcile_open_admission_sequence() 处理枚举边界，begin_closing() 停止 admission 并等待 participant ready，phase2_preflight() 负责最终尾部收敛。

sql/binlog_ostream.cc 是实际写入路径。Binlog_cache_storage::install_warmcopy_mirror_if_absent() 安装 mirror，write() 同时写原 cache 和 mirror lease，truncate() 同步 truncate generation，copy_range_to() 支持从 cache 拷贝指定区间。preserve_trx_warmcopy_max_total_bytes 是 warm external blob 的 epoch 总预算，不是等量堆内存预分配。

7. Lock warmcopy 代码解读

lock warmcopy 位于 SQL 协调层和 InnoDB 锁层之间。SQL 层 sql/preserve_trx_lock_warmcopy.cc 负责 policy、artifact、canonical compare、fallback 和状态计数；InnoDB 层 storage/innobase/lock/lock0warmcopy.cc 维护 record store、fence、seal 和 conversion freeze；传统 live export/import 仍在 storage/innobase/lock/lock0preserve.cc。

  • lock0warmcopy.cc 使用 64 个 record store partition，降低以 target 为 key 的全局大锁压力。
  • lock_warmcopy_record_store_fence_for_target()、lock_warmcopy_record_store_seal_for_target() 和 lock_warmcopy_record_store_seal_metadata_for_target() 是 phase 1 candidate 到 sealed artifact 的核心边界。
  • lock_warmcopy_trx_conversion_freeze()、lock_warmcopy_trx_conversion_thaw() 与 lock0lock.cc 中 implicit-to-explicit conversion 检查共同避免 seal 后其它会话把目标事务的 implicit lock 物化成遗漏的 explicit lock。
  • sql/preserve_trx_lock_warmcopy.cc 的 route 函数把 artifact invalid、final fence mismatch、predicate/spatial unsupported 收敛为 per-target all-or-live：fallback ON 丢弃该 target 全部 warmcopy artifact 后 live export，fallback OFF reject。

8. InnoDB 事务、锁、Read View、Savepoint 与临时表

InnoDB adapter 的职责是把存储引擎内部对象转成 snapshot 可验证 payload，并在 resume 时恢复到新的 THD 上。下图按对象列出主要导出/导入点。

临时表路径是最容易误判的部分。sql/preserve_trx_temp_table.cc 负责 SQL 层 manifest、resume policy、open/materialize；storage/innobase/trx/trx0temp_preserve.cc 处理 physical image、dict table register/unregister、fil space attach/detach、no-redo undo reconnect 和 native-owned adoption。native-adopted token 可以在 resume 后继续执行受支持的临时表 DML；旧 manifest、restored-only reconnect 或无法证明 ownership 的 no-redo undo resume 形态必须按 fail closed 处理，不应在文档或运维说明里描述成完全通用的临时表事务迁移。

9. Resume、startup recovery 与 expired-token cleanup

Resume 从 token 读取 snapshot，校验 identity、权限、状态和 payload，然后重建 THD/session 状态并 attach InnoDB trx。startup recovery 的目标不是自动继续业务，而是把磁盘 snapshot 转回可观测 record，使 operator 或后续编排能处理 token。expired-token cleanup 需要区分普通过期、已准备但 snapshot 不明确、cleanup 失败后仍需保留 ownership 的场景。

这里需要特别关注 session 语义：隔离级别、read only 访问模式、user variables、prepared statement 边界、权限和 account ownership 都属于 SQL 层恢复的一部分。恢复成功不是只把 InnoDB trx 挂回去，还要保证业务看到的事务语义与 preserve 前一致。

10. 可观测性、状态计数与测试入口

Preserve/Resume 的可观测性分三层：SQL 命令输出、P_S 表、内部状态计数。P_S 相关表位于 storage/perfschema/table_preserved_transactions.*，用户命令 SHOW PRESERVED TRANSACTIONS 提供面向运维的 token 视图。lock warmcopy 还提供 attempts、sealed_valid、sealed_invalid、fallback、strict_reject、final_fence_mismatch、conversion_freeze_waits 等计数。

11. 当前限制与实现风险

phase 2 约 1 秒目标：当前完整目标依赖 phase 1 authoritative mirror、external artifact、bounded final seal 和并行 target preserve。若仍在 quiesced 后扫描、排序、编码、写入大量锁对象，只能保证功能正确，不能宣称 full workload 的约 1 秒 SLO。

lock warmcopy family 边界：record/table/MDL/savepoint 等 family 必须保持同一 target 的 all-or-live 语义，不能只替换单个 family 形成混合时间点 snapshot。

R-tree/spatial predicate：当前不做 warmcopy 优化；fallback ON 走 live export/import，fallback OFF reject。

低侵入原则：preserve_trx_enable=OFF 时，原生 MySQL 路径不应执行 preserve payload、文件 I/O、大扫描、错误语义转换或长时间等待。
