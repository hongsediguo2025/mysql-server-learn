1. 观察模型

Preserve/Resume 没有一个单独的“总状态”可以回答所有问题。事务是否可恢复、一次 DRAIN 为什么慢、接收端是否已经 READY、promotion 是否满足 500ms，分别落在不同对象上。排障时应保持固定的证据顺序。

控制面参数、SQL 命令次数、当前拓扑角色。先确认观察的是哪条功能路径。
事务状态SHOW / P_S 中的本地 record、生命周期、sidecar 和最近错误。
运行指标最近一次、当前 gauge、进程累计和 monotonic 时间点必须分开解释。
结构化日志恢复 begin/end、drain metrics、participant、receiver、resume failure。
持久化对象snapshot、sidecar、marker、ledger 说明 durable 边界和清理债务。
代码写入点从状态注册找到 getter，再找到 store/fetch_add 和状态迁移。

本地事务平面

performance_schema.preserved_transactions 和 SHOW PRESERVED TRANSACTIONS 读取同一份内存 registry。它们展示本机已经注册的 preserved record，不扫描目录。

传输与升主平面

standby receiver registry 和 strict prepared registry 与本地 preserved record 分离。接收成功的 token 不会因此出现在本地事务视图，也不能直接执行普通 SQL RESUME。

持久化平面

preserve_trx_dir 保存 snapshot、sidecar 和 marker。文件能证明某个 durable 对象存在，但不能单独证明内存状态已注册或 promotion gate 已通过。

当前实现的四个观察边界

这些边界需要在诊断结论中写明
  • manager 的 IDLE、BATCH_DRAINING、WARMCOPY_CLOSING 等内部状态没有公开 P_S 表；只能通过事务状态、命令会话、日志和阶段指标间接判断。
  • strict prepared registry 只暴露 registered、prewarm pending、ready、adopting、adopted、tainted 六个聚合 gauge，没有逐 token 公共视图。
  • strict physical promotion gate 的 API 会返回 status、elapsed_us 和 message，但当前没有写入 Preserve_trx_promotion_gate_status_code；后者只对应旧 ready-cache gate。
  • Preserve_trx_transfer_receiver_strict_record_index_page_reads、...strict_ibuf_merges、...strict_target_local_redo_bytes 已注册 getter，但当前源码没有写入点。它们为 0 不能证明没有副作用。

SHOW PRESERVED TRANSACTIONS 与 performance_schema.preserved_transactions 共用 preserved_trx_snapshot()。查询会等待 startup recovery 完成，因此启动期间的查询延迟本身可能是恢复尚未结束，而不是 P_S 锁死。

PROCESS

可见全部行，并看到完整 token。生产采集应限制输出范围和访问权限。

RESUME_ANY_PRESERVED_TRANSACTION

可见全部行，但没有 PROCESS 时 token 仍脱敏。

普通 owner

3.1 生命周期状态

STATE含义诊断动作
DRAINING批量 DRAIN 尚持有事务所有权短暂状态；长期不变时检查 participant、token delivery 和批量收尾。
SNAPSHOTTING单事务 snapshot 已进入持久化/交付窗口短暂状态；关注 snapshot 写入、XID provenance 和注册失败。
PRESERVED本地稳定可恢复正常稳态；可执行 SQL RESUME，前提是权限和 sidecar 校验通过。
ADOPTED_FOR_PROMOTION已被 promotion 路径认领普通 SQL RESUME 不应抢占，等待 promotion resume core。
RESUMING某会话正在认领并恢复并发 RESUME 应被排除；失败后看是否回到可重试状态。
ROLLING_BACK显式回滚正在认领观察清理是否完成以及 artifacts 是否移除。
EXPIRED_ROLLBACK到期 reaper 正在回滚不要并发人工删除文件；等待终态或错误记录。
EXPIRED_CLEANUP_FAILED到期回滚/清理未完整收敛必须结合 LAST_ERROR、tainted/consume marker 和日志处理。
FAILED仅用于诊断的 observable record不代表可恢复；到 GC deadline 后会被移除。
不要把所有非 PRESERVED 状态都当故障DRAINING、SNAPSHOTTING、RESUMING、ROLLING_BACK 和 EXPIRED_ROLLBACK 都可能是正常短暂状态。判断异常需要“状态持续时间 + LAST_ERROR + 对应操作日志”三项同时成立。

4. 指标与度量

212 个状态量混合了四种口径。先确定口径，再解释数值。最常见的误判，是把进程累计值当成最近一次操作，或把 monotonic 时间点当成墙钟时间。

口径读法适合的度量不能做什么
当前 gauge某一时刻的队列、内存、worker、registry 数量定时采样，观察绝对值与持续时间不能用两次差值当吞吐量，状态可能上下波动。
最近一次最近一次 drain、resume、startup 或 gate 覆盖的结果操作结束后立即采集，并和 operation ID/日志对齐不能汇总多次操作，也不能说明历史 p99。
进程累计本次 mysqld 启动以来的 count、bytes、us用采样差值计算速率或单次增量进程重启后归零；也不要假设 FLUSH STATUS 会清理自定义 atomics。
monotonic 时间点同一进程 steady clock 的微秒值同一 mysqld 内两时间点相减不能跨进程、跨重启，不能直接和 NOW(6) 或日志时间相减。

累计增量 = value_after - value_before

平均速率 = 累计增量 / 采样间隔秒数

7. 500ms 升主怎么量

“小于 500ms”必须先定义时间边界。当前代码能提供 receiver、gate 和 resume core 的内部证据，但不能单独覆盖 HA 决策、VIP/路由切换和第一笔业务写。因此验收需要一条外部时间线和三段内部时间线。

T0：进入升主HA 已冻结 apply，取得预期 physical fence，开始 strict promotion gate。
T1：gate 完成prepared registry 认领完成，返回 strict gate status、elapsed_us、message。
T2：resume core 完成事务对象激活并进入可续接状态；观察 resume core latest/分布。
T3：服务可写mysqld/HA 解除写保护并发布服务状态。
T4：首笔写成功从业务连接发出探针并成功提交，作为用户可见 RTO 终点。

用户可见 RTO = T4 - T0，要求 < 500ms

内部分解 = gate + resume core + 可写发布 + 路由/连接 + 首写

每个剧本都从“先证明哪一层出了问题”开始。除非状态机和清理语义已经明确，不要用重启、改参数或删文件代替定位。

先看
preserve_trx_enable、当前账号 PROCESS/RESUME_ANY 权限、SHOW/P_S 是否正在等待 startup recovery。

9.3 差分原则

  • 累计量用前后差分；gauge 保存完整采样序列；latest 值和对应操作日志绑定。
  • 进程重启时另开一段时间序列，不能把重启前后累计值直接相减。
  • monotonic 时间点只在同一 mysqld 内计算；跨 source/receiver 使用墙钟或由同一协调器打点。
  • 若存在并发 DRAIN、transfer 或 promotion，必须用 epoch_id、operation_id 和时间窗口隔离，不能只按“最后一条日志”归因。
