MYSQL 8.0.22 · STARTUP RECOVERY

Preserve / Resume 启动恢复与原生代码差异

本文从 MySQL 8.0.22 原生启动与 XA 恢复链路出发，逐层说明 Preserve / Resume 在哪里复用原生能力、在哪里增加隔离钩子、如何通过认证 Resurrection Index 跳过 Undo body 扫描、在哪里扩展了 InnoDB 事务语义，以及启动恢复和真正 RESUME 之间的边界。

0. 核心结论

先把最容易混淆的问题说清楚：当前实现没有另起一套 mysqld 启动框架，也没有整体替换 MySQL 的 ha_recover()、ha_post_recover() 或 handlerton 事务绑定机制。它是在原生恢复骨架内，对特定 Preserve XID 做隔离，并在 InnoDB post_recover 回调中补齐事务语义。

问题原生 MySQL 8.0.22当前 Preserve / Resume判断
ha_recover() 是否被替换 遍历 handlerton，收集或裁决各引擎返回的 prepared XID。 SQL 层函数保持原样；InnoDB 的 recover 返回结果提前滤掉受保护的 Preserve XID。 复用原生改变输入集合

原生 XA 能否处理 Preserve XID prepared XID 可进入 XA recovery cache，并可通过 commit / rollback by XID 裁决。 经过“magic XID + 认证 provenance”判定后，从原生恢复列表隐藏，并拒绝通用 commit / rollback by XID。 命名空间隔离
启动后是否已经 RESUME 原生 XA 只恢复为 prepared XA。 启动恢复为 detached PRESERVED；用户执行 RESUME 后才恢复 session、binlog cache、GTID、临时表并绑定 THD。 两阶段恢复
trx_sys_init_at_db_start() 是否仍扫描 Undo 遍历 rseg 的 insert / update Undo list，建立 trx_t，并逐条扫描 Undo body 提取修改表 ID。 仍遍历 Undo list、读取 Undo header、建立 trx_t / rseg / Undo 链；认证 Index 命中时注入 exact table IDs，只跳过该事务的 Undo body record 扫描。未命中或 anchor 不一致时逐事务回退原生扫描。 原生对象构建保留热点 I/O 优化
Index 是否能提前把事务改成 PRESERVED 无 Index，也无 PRESERVED 状态。 不能。Index 只是认证优化提示；事务在 Undo resurrection 后始终保持 PREPARED，完整 bundle 通过校验后才在共享 recover/adopt 内核中 claim 为 PRESERVED。 禁止提前 claim
receiver 文件能否跨重启恢复 无 transfer receiver。 不能。receiver artifact 只属于接收它的 mysqld 进程；正常重启在 InnoDB 初始化前清理 transfer tree、standby-pending 和 promotion markers，清理失败则启动失败。 进程级所有权fail closed
一句话理解 InnoDB 原生 XA PREPARED undo 仍负责构建真实事务对象；认证 Resurrection Index 只消除可证明冗余的 Undo body 扫描；Preserve snapshot 是语义目录和所有权凭据；post_recover 把两者重新组合成 detached PRESERVED 事务；RESUME 才把它交给新的客户端连接继续执行。

2. 原生 MySQL 8.0.22 启动恢复基线

理解差异前，先固定原生顺序。MySQL 的存储引擎低层恢复并不是从 ha_recover() 才开始：InnoDB 在 builtin core storage engine 初始化阶段已经完成 redo / undo 扫描，并从 undo 中复活 prepared transaction；后面的 ha_recover() 是 SQL / TC 层面的 XA 收集和裁决。

原生 ha_recover() 通过 handlerton 的 recover 回调读取 prepared XID。外部 XA 会进入 Recovered_xa_transactions，随后注册到 transaction cache，并根据修改表集合创建 MDL backup。原生 InnoDB post_recover 完成 DDL log、表空间缓存等工作，最后调用 srv_start_threads_after_ddl_recovery() 启动 purge。

原生能力的上限 原生 XA 能保证 prepared 事务的 undo 和锁存活，并等待 COMMIT / ROLLBACK 裁决；它不会持久化并恢复业务会话的 Read View、SQL savepoint、session variables、binlog cache 内容、精确 MDL 形态和用户临时表。因此“事务继续执行”不能只依赖原生 XA recovery。

2

再从原生 XA 隔离

只有通过 provenance 认证的 Preserve XID 才不会进入普通 XA cache 和通用 XA 裁决。

3

最后补齐语义

InnoDB post_recover 中优先用已核验的精确 trx_t* 把 PREPARED 认领成 PRESERVED，并恢复 Read View、锁和 detached MDL。

4.2 UUID 为什么提前

snapshot key、server identity 与后续 binlog 使用的是同一个 server UUID。原生代码只要求 UUID 在打开 binlog 前可用；Preserve preflight 要在 TC / XA recovery 前验证 snapshot 的身份绑定，因此必须更早初始化。--initialize 场景仍在 ha_post_recover 之后调用，避免改变初始化流程。

4.3 preflight 到底位于哪个“恢复”之前

preserved_trx_preflight_recoverability() 位于 generic ha_recover(nullptr) 之前，负责预加载认证 provenance、扫描本地 snapshot、校验 snapshot identity digest、provenance 状态和 binlog mode。它不认领事务，也不导入锁。

必须准确表述的时序 代码日志中有“before storage engine recovery”的表述，但按实际调用顺序，InnoDB 的 redo / undo 低层恢复早已在 plugin_register_builtin_and_init_core_se() 阶段完成。这里的“之前”只应理解为：在 TC / handlerton 层的通用 ha_recover() 之前，而不是在所有存储引擎恢复动作之前。

4.4 为什么 preflight 不能直接做完整恢复

  • 此时的职责是判断 snapshot 是否可被当前实例安全识别，而不是改变事务所有权。
  • 完整恢复需要 InnoDB post_recover 阶段的表空间、DD、锁系统等前置条件。
  • 先完成 provenance 认证，才能让后续 InnoDB recover 回调安全地隐藏 protected XID。
  • 认领事务前保持失败面较小；不支持或身份不匹配可直接中止启动，不留下半导入状态。

7.3 为什么放在 purge 启动之前

Preserve 事务的 undo、Read View 和锁都需要在 purge 进入正常工作前建立稳定的所有权。当前 innobase_post_recover() 先执行 preserved_trx_recover_all()，再调用 srv_start_threads_after_ddl_recovery()；而 purge 正是在后者中启动。

7.4 失败如何收敛

  • 目录扫描、认证、attempt ledger 或关键 cleanup 失败会让 recover_all() 返回错误，并由 InnoDB post_recover 走 fatal startup abort。
  • 单 token 在 claim 前发现格式、模式、超时等问题，按原因回滚 snapshot 对应事务或保留失败可观测记录。
  • claim 后语义导入失败，会删除 detached MDL、撤销已导入状态、回滚 claimed trx 并清理 snapshot；cleanup 失败则保留 tainted / failed 状态。
  • prepared trx 不存在时，说明持久引擎锚点已丢失或不匹配，恢复路径删除对应 snapshot 与 sidecar，不伪造可继续事务。

9.1 claim 时发生什么

  1. Index hit 的本地 startup 先通过 verified map 取得精确 trx_t*；旧路径和 Index fallback 才按 XID 遍历 trx_sys->rw_trx_list。
  2. 无论入口是哪一种，都要求事务指针有效、无 THD、未被 claim、状态为 PREPARED、XID 完全匹配。
  3. 在 trx_sys_mutex 下减少 trx_sys->n_prepared_trx，状态改为 PRESERVED。
  4. 设置 preserve_trx_claimed=true，防止并发恢复或普通 cleanup 再次取得该事务。
  5. 事务仍留在 rw trx list，继续持有 rseg、undo 和锁。
PREPARED 与 PRESERVED 的分界 Resurrection Index candidate、anchor verified 和 exact-pointer publication 都不是新的 trx_state_t。它们是仅在 startup recovery 窗口存在的辅助 registry；真实 trx_t 直到共享 recover/adopt 内核 claim 成功才从 PREPARED 进入 PRESERVED，registry 在 preserved_trx_recover_all() 返回时清空。

11.1 MDL policy 为什么不是直接改原生语义

create_backup 和 restore_backup 新增 policy 参数，但默认值是 STANDARD_XA。原生 XA 调用也显式传入 STANDARD_XA，继续保留原来的幂等行为；只有 Preserve 路径使用 PRESERVE_STRICT。这样把新特性的 fail-closed 要求限制在内部恢复路径，不把普通 XA 的兼容行为一并改变。

11.2 purge 的双重保护

正常情况下，prepared / preserved trx 持有 rseg 引用，原生 trx_ref_count 已能阻止部分 truncate。当前代码仍显式调用 trx_preserve_collect_preserved_rsegs() 做第二层判断，防止未来 ref-count 逻辑变化或特殊 no-redo 路径削弱通用保护。

14. 时序与并发边界

“在 purge 前恢复”是正确的，但“在所有后台线程前恢复”并不准确。当前启动路径中，不同后台线程的创建时点不同，安全性依赖事务状态和原生 rollback 规则，而不是单纯依赖线程尚未启动。

14.1 recovery rollback 线程可能已经启动

DD restart 调用 DDSE_dict_recover()，进入 innobase_dict_recover()，随后在 ha_innodb.cc:3673 调用 srv_start_threads(false)。当 trx_sys_need_rollback() 为真时，该函数可在 srv0start.cc:2979-2987 创建并启动 trx_recovery_rollback_thread。这发生在 mysqld 后面的 ha_post_recover() 之前。

为什么仍然安全 原生 recovery rollback 只回滚非 PREPARED 的 recovered transaction；当前分支又明确让该逻辑跳过 PRESERVED。低层恢复阶段 Preserve 事务保持 PREPARED，claim 后变为 PRESERVED，因此线程即使已存在，也不会把它作为普通 active recovered transaction 回滚。这里依赖的是状态不变量，而不是“线程尚未创建”。

14.2 purge 确实在 Preserve 语义恢复之后启动

preserved_trx_recover_all() 位于 innobase_post_recover() 内，且在 srv_start_threads_after_ddl_recovery() 之前。后者在 srv0start.cc:3050-3052 调用 srv_start_purge_threads()。因此“恢复完成后再启动 purge”是可以由实际调用顺序证明的。

14.3 并行启动恢复的边界

preserve_trx_startup_recovery_threads 可让不同 token 的 recovery task 并行执行。每个 worker 初始化 MySQL thread 环境，并按 task 领取 snapshot；具体 claim、trx list 修改、状态转换仍由 InnoDB mutex 和 Preserve record 同步保护。并行化改变总恢复时延，不改变单 token 的语义导入顺序。

最终判断

当前架构的本质 Preserve / Resume 选择“借用原生 XA / Undo 的持久性和事务对象构建，使用认证 Index 消除可证明冗余的 Undo body 扫描，隔离原生 XA 的裁决权，扩展 InnoDB 的 detached transaction 状态，再复用原生 THD 绑定和 commit / rollback 框架”。Index 不是第二份事务主体，receiver artifact 也不是跨重启介质；XID provenance、Undo anchors、snapshot bind、PRESERVED 状态、rseg 保护、语义导入和 RESUME attach 必须保持一致。
