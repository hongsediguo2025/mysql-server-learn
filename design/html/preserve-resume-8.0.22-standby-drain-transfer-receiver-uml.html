范围与结论

这张图描述的是 standby transfer 模式下真实存在的准备链路，不把 promotion simulator、测试插件或接口骨架画成生产物理升主。

最重要的阅读边界 Source 的 final ACK、receiver 的 SAVED_ONLINE、strict registry 的 READY_FOR_GATE 是三个不同事实。Source 可以接受 COMMITTED_NOT_READY 后结束 DRAIN；receiver 在后台继续 prewarm。真实 redo apply fence、角色切换和连接 attach 仍属于未来物理备机产品。

端到端总览

1. 打开 Phase 1进入 WARMCOPY_DRAINING，创建 source transfer epoch。
2. 声明目标以 source connection/thread id 作为 transfer token。
3. 流式传输发送 record-lock、binlog-cache 与 provisional manifest。
4. Receiver 实时处理spool、stage、seal，并异步生成 object proof/candidate plan。
5. Phase 2 稳定点WARMCOPY_CLOSING，等待已入场语句全部 QUIESCED。
6. Final facts有界 catch-up、final metadata、COMMIT_EPOCH 与 final ACK。
7. Promotion-readyreceiver 完成 READY_FOR_GATE；未来 HA 再执行真实升主。

Phase 1 与 Phase 2 的职责

Phase 1：业务运行期准备

  • Drain 状态为 WARMCOPY_DRAINING，业务语句仍可继续。
  • 声明候选 token，token 对应 source 连接的 thread/connection id。
  • record-lock 与 binlog-cache bulk object 尽量在此阶段发送。
  • Receiver 对 sealed object 立即生成 object proof 或 candidate plan。
  • 完整 final facts 尚未到达时，candidate 不能被当作可升主事实。

Phase 2：形成不可再变化的最终事实

  • 进入 WARMCOPY_CLOSING 后拒绝新普通命令。
  • 等待已入场语句结束，目标必须达到 QUIESCED。
  • 允许一次固定位置、对象集合明确的有界 final catch-up。
  • 随后执行 preserve/prepare/detach，发送 final descriptor 与 digest。
  • COMMIT_EPOCH 必须晚于所有 required objects 的 seal。
Phase 2 不是无限补发阶段 如果大量 token 都需要在 Phase 2 重新构造或发送 bulk objects，说明 Phase 1 overlap 没有发挥作用。代码可通过有界 catch-up 保证正确性，但性能证据必须把 catch-up token、bytes 和耗时如实暴露。

Receiver 的两套状态事实

Receiver transfer registry 与 strict prepared registry 服务于不同目的，不能把它们压缩成一个“READY”。

Transfer registry

DECLARED → RECEIVING → SAVED_ONLINE

负责 frame sequence、object range、seal、epoch barrier 和在线 artifact 生命周期。

Object / token prewarm

object proof → candidate plan → PREWARMED_PENDING_FINAL_FACT

Phase 1 可提前完成重工作，但必须等待 final digest/facts 才能升级。

Strict prepared registry

READY_FOR_GATE

表示未来 strict promotion gate 可以消费；它仍不等于已经升主或已经 attach 到客户端。

用户临时表边界 当前 portable temp sidecar 的跨节点路径没有完整闭环。此图中的 bulk objects 不能被解读为“所有用户临时表对象都已支持跨机 transfer/resume”。

ACK、COMMIT 与 READY 的准确语义

事件Source 是否等待Receiver 此时完成了什么不能推导什么
Frame ACK是，作为在线发送结果鉴权、sequence admission、spool write/close不代表 semantic apply、prewarm 或介质断电耐久
Metadata ACK是final metadata 已被 receiver 接收不代表全部 token 已 READY_FOR_GATE
COMMITTED_READY接受epoch facts 已提交，strict resources 已 ready不代表真实 HA role transition 已完成
COMMITTED_NOT_READY同样接受epoch 已提交，receiver 后台继续 prewarm不能把 source final ACK 延迟当成 receiver ready 时间
READY_FOR_GATESource 不再参与receiver 内存 strict registry 满足未来 gate 前置条件不代表物理一致性 provider、redo fence 或新连接 attach 已执行
Drain 与 receiver prewarm 解耦 Source Phase 2 等的是 transfer/final ACK，不应同步等待 receiver 后台 prewarm。Receiver 必须实时 prewarm，但它的完成时间通过 receiver 本地指标单独衡量。

备机升主流程与关键接口

Receiver 达到 READY_FOR_GATE 后，未来物理备机产品应使用一个两段式 bootstrap attempt，把 pre-trx_sys candidate 注册、唯一一次原生 InnoDB 事务构建，以及 post-trx_sys strict adopt 串成同一连续操作。外部 HA 不传 token vector，也不单独解析 trx_t*。

当前实现事实 两个 public wrapper 和私有 handoff 已实现，但当前仓库没有 production HA caller、redo apply coordinator 或 role-transition 接线。外部 HA 必须先完成 redo terminal fence，并从 prepare 开始一直保持 apply/DDL/page-layout freeze，直到 adopt 收敛；这不是 Preserve 接口自行提供的能力。

未来 HA 的真实接入调用形态

Preserve_trx_physical_bootstrap_request request;
request.epoch_id = epoch_id;
request.operation_deadline_us = deadline_us;
request.worker_count = 3;

Preserve_trx_physical_promotion_bootstrap_attempt attempt;

auto status =
    preserved_trx_prepare_before_trx_sys_init_for_physical_promotion(
        preserve_dir, request, &attempt);

if (status != Preserve_trx_physical_promotion_gate_status::OK) {
  // HA policy: abandon Preserve fast continuation, then either continue
  // ordinary promotion or abort promotion. This branch must not fall through
  // into the Preserve adopt call below.
  return handle_promotion_without_preserve(status);
}

// Native InnoDB initialization: exactly once.
purge_queue = trx_sys_init_at_db_start();

// DD/MDL are usable; purge/rollback/write-enable have not started.
Preserve_trx_physical_promotion_gate_result gate_result;
status = preserved_trx_adopt_prepared_epoch_for_physical_promotion(
    preserve_dir, &attempt, &gate_result);
为什么没有独立 resolve API prepare 已从 accepted epoch 构造 exact token keys，并向 InnoDB startup 注册认证的 Resurrection candidates。原生 trx_sys_init_at_db_start() 从 target Undo headers 构造真实 trx_t 后，adopt 内部的私有 prepare_gate_handoff() 再按 token/XID 查询 verified map，检查缺失、重复和 deadline。任何 claim、lock import 或 registry 状态迁移都发生在这些检查之后。

状态主线

READY_FOR_GATEreceiver final facts、lock plan、native binlog handle 已准备。
ADOPT_LEASEDbootstrap attempt 独占当前 epoch，并 pin token。
TRX_SYS BUILT原生 InnoDB 从 Undo headers 构造精确 trx_t。
ADOPTINGgate 按 exact key/trx 执行 claim 和语义导入。
ADOPTED_LOCKED事务已在新主内核中 detached 持锁，尚未绑定客户端。
ROLE WRITABLE未来 HA 完成 post-recovery、fencing 和 write-enable。
ACTIVE目标连接自身 RESUME，attach 并激活该事务。

Bootstrap attempt 的生命周期

时点attempt 持有的事实/所有权退出动作
prepare 成功accepted_epoch 的 ADOPT_LEASED 所有权、内部 gate request 的 exact keys、operation deadline/worker count，以及 strict prepared-token pin。process generation 固化在 accepted epoch 与 token key 中。必须在 purge、recovery rollback 或 write-enable 前消费；否则显式 abort() 或析构清理。
prepare_gate_handoff()私有查询 verified map，按 token/XID 收集 exact trx_t*；缺一个、重复一个、超 deadline 或 epoch/pin 状态不符都拒绝。wrapper 自动调用 abort()，不进入 claim/import。
adopt 全部成功所有 token 已收敛到 ADOPTED_LOCKED；receiver promotion lease 被完成，prepared-token pin 原子释放。complete_gate_handoff() 清空 resurrection verified state 和 attempt；随后才可进入 HA 的 post-recovery/role switch。
adopt 失败per-token core 先按自身结果 rollback 或 taint；epoch attempt 仍不能泄漏。wrapper 调用 abort()；若 receiver epoch 清理失败，返回 CLEANUP_TAINTED，HA 不得把 Preserve 快速续作视为成功。

关键接口的含义和作用

接口 / 对象当前状态主要作用明确不负责
preserved_trx_prepare_before_trx_sys_init_for_physical_promotion() 已实现无生产调用者 仅接收 preserve_dir + epoch/deadline/workers + attempt。它取得当前进程 receiver epoch 的 promotion lease，核验 epoch/fact/token 集，内部构造 gate request/exact keys，pin strict registry token，复制 Resurrection Index entry，并注册给随后唯一一次原生 trx_sys_init_at_db_start()。 没有额外 result 参数；不要求 HA 重复拼 token vector；不 claim 事务、不导入 record locks/MDL、不 attach THD，也不开放写权限。
Preserve_trx_physical_promotion_bootstrap_attempt 已实现RAII owner 把 pre-trx_sys 注册与 post-trx_sys strict gate 绑定成同一次 attempt；直接持有 accepted epoch、prepared-token pin 和私有 gate request。析构或 abort() 会释放/放弃当前 epoch 并清空 startup resurrection state。 不跨 receiver 重启持久化；不能在另一个进程恢复该 attempt。
prepare_gate_handoff() 私有方法 在 adopt wrapper 内把 exact key 的 token 转成 XID，从 trx_preserve_startup_resurrection_find_verified() 取得 exact trx_t*，并同时返回 accepted epoch 与 prepared-token pin。 不是对 HA 暴露的 resolve API；不允许外部传入或替换 verified transaction vector；缺失、重复或超时会在任何 claim/import 前拒绝整批。
preserved_trx_register_physical_resurrection_candidates() 已实现内部 helper 把认证的 token/XID/Undo anchor/table-id 事实交给 InnoDB startup resurrection 逻辑，使原生 trx_sys 构建可以识别目标事务。 不伪造 trx_t，不直接从 transfer payload 创建事务，也不完成 promotion adopt。
trx_sys_init_at_db_start() 原生 InnoDB 从 target Undo headers 构建真正的 prepared trx_t、事务列表和原生恢复状态；Preserve candidate 携带已认证的 prepare LSN，startup resurrection 再核对 XID 与 Undo anchors，并把命中的 exact trx_t* 放入 verified map。 不是在线可重入 API，不能在已经完整初始化的同一个 trx_sys 上再次调用。
preserved_trx_adopt_prepared_epoch_for_physical_promotion() 已实现骨架无生产调用者 外部只传 preserve_dir + attempt + gate_result。wrapper 内部 handoff exact verified trx_t*、accepted epoch 与 token pin，并行执行 epoch adopt；只有整批收敛为 ADOPTED_LOCKED 才返回 OK，并消费 receiver promotion lease。 不执行 server role switch、single-primary fencing、write-enable 或客户端连接创建。
preserved_trx_adopt_prepared_for_physical_promotion() 已实现per-token core 在 gate lease 下对精确 prepared trx 执行 shared recover/adopt kernel：claim、session semantic facts、read view/table/record locks、MDL 与 promotion-owned record 注册。 生产模式不能在缺少 exact verified trx 时现场查找或冷恢复；失败必须 rollback 或 taint，不能跳过后报成功。
preserved_trx_resume_adopted_for_promotion_on_current_thd() 已实现static current-THD core 由目标连接自身的 SQL RESUME 进入；确认 exact promotion key 和 ADOPTED_LOCKED，写 attach intent，挂载 native binlog handle、MDL、GTID 条件状态、temp 条件状态、trx 与 savepoint，最后 activation。 不是跨线程 THD resolver；不能由控制线程拿裸 THD* 替另一个连接执行。旧 peer-THD handle/resolver 已被 source-shape 合同明确禁止。
preserved_trx_set_promotion_apply_state_provider() Legacy gate 给旧 preserved_trx_adopt_standby_pending_all_for_promotion() 提供 apply_frozen/applied_lsn；provider 缺失时旧路径 fail closed。 不是新的 strict physical bootstrap/adopt 接口，也不能证明真实 HA role fencing。
Test-only fence 与 production 物理冻结不能混用 当前 Preserve_trx_physical_fence_lease 的 provider 注册入口只有 ..._for_unit_test。Simulator 可以用它验证 fence 合同；production strict wrapper 则依赖 bootstrap attempt 提供的 accepted epoch 与 exact verified trx_t*，并把真实 apply/DDL/page-layout freeze 留给外部 HA。两者的证据等级不同。

真实物理升主边界

当前仓库可以证明

  • Source Phase 1/Phase 2 的 transfer orchestration。
  • Receiver frame admission、spool、seal 与实时 prewarm。
  • Final fact 绑定和 strict registry READY_FOR_GATE。
  • Simulator/Test-only 条件下的 gate contract 与 fail-closed 行为。

未来 HA 产品必须提供

  • 真实物理备机与 redo apply coordinator。
  • 冻结 apply/DDL/page layout 的 physical lease/fence。
  • single-primary role fencing 与正式 promote caller。
  • 物理一致性成立后的 strict gate、protected THD attach 和 service-open。
不得越界声明 READY_FOR_GATE 是“升主前 Preserve/Resume 准备已完成”，不是“物理备机已经升主”。没有真实 redo/apply fence 时，不得执行异构节点上的事务 DML 来冒充生产一致性证明。
