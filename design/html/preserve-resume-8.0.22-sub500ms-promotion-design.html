Preserve / Resume 事务亚 500ms 升主设计

本文以当前 MySQL 8.0.22 Preserve/Resume 代码为基线，定义可落地的 500ms 数据库内升主口径、内核对象复活方案、升主前准入条件、失败边界、指标和 E2E 验收方法。 重点不是在 gate 中把冷恢复“跑快”，而是把所有可预测工作前移，gate 只做物理事实复核、 内核对象发布、事务 adopt 和写权限切换。

失败策略未预热、事实不一致或预算不足时快速拒绝，禁止冷兜底

1. 设计结论

当前代码已经具备 transfer、receiver prewarm、物理 fence、record-lock metadata plan、 prepared-token registry 和严格 adopt/attach journal 的骨架，但还不能据此承诺 500ms。 原因是当前 READY_FOR_GATE 证明的是 bundle、锁计划、binlog handle 和资源额度已准备， 并没有证明目标 InnoDB 中已经存在可被 trx_preserve_claim_prepared() 找到的 trx_t。

实现成熟度声明 本文同时描述“当前工作树已实现的无物理复制交付”和“达到生产亚 500ms 仍需实现的目标态”。当前已落地 transfer wire v4、Resurrection Index v1、真实 prepare/Undo/TRX_SYS/lock generation 事实、receiver 当前进程期 accepted/query、三档资源治理、startup indexed resurrection、显式指针 shared adopt、test-only targeted publication 与可逆 journal、常驻 3-worker gate pool，以及 simulator epoch all-or-nothing 回滚。生产 apply/freeze/fence provider、 physical-candidate/read-only interlock、source terminal switchover fence、真实 write-enable、跨节点 ReadView/purge handoff、 production peerid Tx->Ty 和物理复制 E2E 仍未实现。在这些缺口关闭前，本文不能作为生产时延承诺。

1.1 Transfer 是进程期 ownership handoff，不是 receiver crash recovery

不可扩大的产品边界 本设计不支持 receiver crash/restart 后继续保留 transfer 得到的 Preserve 状态。receiver 进程一旦退出， 该进程接收的所有 epoch/token、READY/NOT_READY、prewarm plan 和 ack-query 记录全部失效；重启后的 promotion 必须 fail closed。不得增加 startup spool replay，不得从残留文件重建 receiver registry，也不得把 transfer 文件 解释成本地 shutdown/startup Preserve artifact。
本地 Preserve

跨 shutdown/startup 恢复

本地 preserve → shutdown → startup resume 需要跨进程恢复。原有 snapshot/carrier、文件 fsync、目录 fsync、 startup preflight/recovery 和 preserved_trx_recover_all() 合同保持不变。

Standby Transfer

只在当前 receiver 进程内有效

strict v4 的 snapshot、Resurrection Index、epoch fact 和 accepted 状态保存在当前进程内存；文件只用于 phase-1 控制 spool 和 binlog cache/record-lock 等大 external payload。事实权威是当前进程 registry。 frame/artifact fsync=0、directory fsync=0、startup replay=0。文件即使碰巧在重启后仍存在，也没有可恢复语义。

FINAL_ACK 之前
source 负责发送完整 epoch；target 负责 frame/sequence/digest/manifest/epoch fact 校验和完整保存。部分接收、超时、连接断开或 registry 发布失败都不得返回 FINAL_ACK。
FINAL_ACK 的准确含义
当前 receiver mysqld 进程已完整接受并保存该 epoch，且进程内 registry 已发布 ownership。它不表示 promotion-ready、可 resume、可跨 receiver crash 保留，也不表示 HA authority/apply fence/write-enable 已满足。
FINAL_ACK 之后 source 必须停止
立即结束 sender workers、classic data sessions 和 source epoch context；不等待 prewarm、不查询 READY、不发送 promotion/adopt/resume 命令、不参与 target 清理或异常恢复。target 后续失败不得回溯成 source transfer 协议动作。
ACK ambiguity 的唯一例外
FINAL_ACK 不明确时，source 可以对同一仍存活 receiver 进程执行一次有界 QUERY_EPOCH_STATUS。查询只能命中当前进程 registry；receiver 已重启或 registry 无记录时返回失效/未接受，禁止扫描文件推断成功。
兼容状态名不等于 durability 当前 wire 枚举中的 COMMITTED_NOT_READY 在本合同下只表示 ACCEPTED_CURRENT_PROCESS：当前进程已完整接收和保存，但 readiness 不属于 transfer ACK。 新路径不得根据 ready cache 返回 COMMITTED_READY，也不得把 COMMITTED_CORRUPT 当作成功 ownership handoff。后续可在协议版本升级时改名；在此之前必须用注释、指标和测试锁定新语义。

1.4 Promotion 内核能力必须预埋，但由目标端专用流程调用

不是删除 promotion，而是切断错误的调用方向 本轮仍要实现和验证 Preserve/Resume 在升主阶段需要的产品级预埋能力：target-local prewarm、strict gate、显式 trx_t* adopt、promotion-owned record、peer THD attach/resume、deadline、journal 和指标能力。 后续物理备机功能落地时，由 HA 在目标 mysqld 上执行专用升主命令/内部流程，并调用这些统一内核接口； source sender 不参与调用，也不能通过 transfer data session 冒充 HA authority。

物理复制已经负责的内容

数据页、Undo 页、TRX_SYS/rseg 页和其 redo 变更由未来物理复制 apply 到目标端。Preserve 不重复搬运或重放这些页， 也不在 promotion gate 中扫描 Undo body。redo-apply/freeze provider 只证明这些页属于同一 source lineage、 已应用到 required LSN 并在 gate 期间不再变化，同时暴露当前进程 rseg-memory coherence generation。

Preserve 必须补建的内容

redo 不会自动构造目标进程里的 trx_t/trx_undo_t 关联、rw_trx_list/set/ids、 min_active_id、lock_sys、ReadView、MDL、binlog cache handle、savepoint、SQL session 状态、 Preserve record 或 peerid Tx→Ty 绑定。这些对象由 transfer bundle/Index/plan 在 T0 前准备，并由 shared adopt/resume 内核在目标端发布；provider 只提供一致性时点，不替代这些对象的重建。

数量与大小合同 production strict wrapper 不设置固定 token 数或事务大小的语义上限。worker 数只是有界并行度，超过 worker 数的 token 继续从 READY 队列分批消费；内存/IO/cache cap 只产生 backpressure、NOT_READY 或等待下一轮 prewarm，不能把合法事务永久判为 unsupported。当前 simulator 的 N=1/3 仅是性能证据样本，不得下沉到 transfer eligibility 或未来 production admission。 但 gate 的发布成本至少为 O(tokens + locks + MDL)，因此 500ms 只能在发布认证的容量包络内承诺，不能对无限规模给出数学上的固定时延保证。

当前 PROMOTION_PREWARM_TOKEN/PROMOTION_GATE_EPOCH frame 可以保留为 wire decode、 legacy 或测试兼容面，但 transfer receiver 的生产 classic dispatch 不应直接执行 promotion。未来专用命令即使复用 classic protocol，也必须是独立 command surface，校验 target-local HA capability，并只调用 strict wrapper；不能复用 source sender 的 data-session credential、epoch ACK 或重试状态。

本轮按最小合同完成的收缩 receiver 只保留当前进程接收、保存、受限 prewarm 所需状态：不提供 spool replay，不为 transfer 文件执行 file/directory fsync，restart 时先删除 transfer/standby/promotion 残留并跳过 local preserve startup recovery。 FINAL_ACK 成功后 source 当场关闭 data/control sessions 并释放 epoch context；classic transfer 对两类 promotion 控制 frame 固定返回 UNSUPPORTED。未来 HA 使用的 strict physical wrapper、prepared-token registry、 explicit-trx_t* adopt 和 attach/resume 内核继续保留，未被降级为 source 命令或 startup replay。
当前实现

claim 依赖启动期 resurrection

共享 adopt kernel 直接按 XID 扫描 trx_sys->rw_trx_list。物理备机在线接收源端 prepare redo 后，不会再次执行启动期 trx_lists_init_at_db_start()，因此磁盘上即使已有 TRX_UNDO_PREPARED，内存中仍可能没有对应 trx_t。

目标方案

先定点复活，再复用现有 adopt

增加认证过的 Preserve_trx_resurrection_index、接收端本地 trx_preserve_resurrection_plan_t 和可回滚的发布 journal。升主前完成校验、对象预分配、资源 reservation 和 freshness； gate 内核验真实 Undo header 后，把原生 trx_t/trx_undo_t 发布到 InnoDB，再进入现有 isolation、Read View、锁、MDL 和 preserved record 导入流程。

500ms 的承诺对象
初始 profile 只对无 GTID、freeze 时无持久 ReadView、纯 redo-prepared（没有 temp/no-redo 组成）、无不支持锁/DDL/FTS 形态，持续处于 PROMOTION_ARMED，且 token/锁/MDL 总成本位于发布认证容量包络内的 epoch 承诺。当前 simulator 只采样 N=1/3，但这不是 production admission 上限；mixed 与 temp-only 暂不继承该 SLO。
500ms 的完成条件
apply 已冻结且 fence 通过，全部 token 到达 ADOPTED_LOCKED，当前进程 epoch 状态已原子 commit，server 写权限已经打开。
不进入 gate 的工作
传输、对象落盘、大文件校验、Undo body 扫描、页冷读、DD 冷打开、binlog payload 搬运、临时表大对象读取、线程创建。
不满足条件时
在 20ms 内返回 NOT_ARMED/BUDGET_REJECTED，保持只读，不允许在 gate 中转冷路径。
必须接受的工程事实 任意 token 数、任意锁规模、任意磁盘尾延迟和任意 OS 调度条件下，都无法给出无条件的 500ms 成功保证。 可执行的“硬保证”由三部分组成：严格准入、450ms 成功预算、500ms fail-closed deadline。 超出认证包络时不升主，比超时后带着不完整事务状态打开写权限更重要。
两条恢复路径必须区分 本地 shutdown/startup 场景仍由原生启动恢复建立 rw_trx_list，可以利用认证 Index 跳过目标事务的 Undo body 扫描，索引不匹配时允许退回原生扫描；物理备机在线 promotion 不重启 mysqld，必须使用严格的 targeted resurrection，任何缺失或不匹配都快速拒绝，绝不在 gate 中扫描全部 rseg/Undo。

2. 500ms 口径

2.1 T0 与 T1

时间点定义必须满足的事实
T0 HA coordinator 已选定目标，调用数据库物理升主入口的时刻。 目标 epoch 在调用前持续为 PROMOTION_ARMED；token 集合已固定；source terminal lock-mutation fence 已认证且目标已 apply 到其 LSN；目标仍为只读。
T1 目标 server 完成角色切换并允许业务写入的时刻。 authoritative HA lease/CAS 与 write-enable 结果已确认；apply frozen；最终 redo、TRX_SYS、source live lock-plan terminal fence 均复核通过；全部 token 为 ADOPTED_LOCKED；epoch 已在当前 receiver 进程内原子提交。该状态不提供跨 receiver restart durability。
计划切换的写不可用区间必须另报 为形成 source terminal lock fence，源端必须先停止新写/DDL并 quiesce 可能搬移锁坐标的后台活动，目标再 apply 到 terminal LSN； 这些动作是进入 PROMOTION_ARMED/T0 的前置条件，不计入本文 target gate 的 500ms。 但它们会影响计划升主的真实写不可用时间，E2E 必须同时报告 T_source_write_fence_to_T1。若产品承诺“端到端写停顿也小于 500ms”，则计时起点必须前移到 source write fence， 当前 500ms gate 结论不能替代该更强承诺。 
T_db_promote = T1 - T0
             = T_apply_freeze
             + T_fence_acquire_and_validate
             + T_epoch_intent_begin
             + max(T_publish_and_adopt[token_i])
             + T_final_revalidate_and_commit
             + T_enable_write

硬条件：T_db_promote < 500ms

2.2 事务状态完成点

ADOPTED_LOCKED 表示事务已经在新主的 InnoDB 和 Preserve manager 中存在，锁和 Read View 已恢复， 但尚未绑定某个业务连接。该状态足以安全打开普通写流量，因为 preserved 事务的冲突由恢复后的锁保护。 客户端随后执行 resume，将事务从 ADOPTED_LOCKED 变为 ACTIVE。

默认发布口径

T1 = 全 token ADOPTED_LOCKED + server writable。这是 500ms 主 SLO，也是推荐上线形态。

内联激活口径

如果业务要求 T1 前全部 token 已绑定目标 THD 并 ACTIVE，必须使用单独的 INLINE_ACTIVATION profile：预绑定 THD、预恢复 session/GTID/temp 资源，并把清理移出临界路径。 当前 attach 实现不满足该口径。

4.3 当前 promotion resume

preserved_trx_resume_adopted_for_promotion_on_thd() 是独立于 gate 的后续路径。它会写 ATTACHING intent、恢复 session/user vars、接管 native binlog handle、clone MDL、恢复 GTID、 materialize 临时表、attach InnoDB trx、恢复 savepoint，再写 ACTIVATING 和 ACTIVE intent。 成功后还在函数内删除 MDL backup、snapshot、sidecar、provenance 和 intent。

旧 review 中的两个并发缺口已由当前代码关闭：promotion adopt 注册的 record 为 resumable=false/ADOPTED_FOR_PROMOTION，普通 SQL RESUME 无法抢占； Preserved_trx_peer_thd_handle 已通过 Find_thd_with_id 固定 THD 生命周期、推迟 kill、 校验 idle/pristine 并把连接置为 ATTACHING。仍未闭环的是生产 peerid 映射：当前 resolver 仍把源端 connection id 当作目标端 THD id 查找，真实系统必须由 proxy peerid provider 完成 Tx -> Ty。

为什么当前 attach 不能直接计入 500ms legacy/local resume 至少包含多次持久 consume-state 推进、临时表物化和多类文件清理，不能直接计入 strict promotion 的 500ms 证据。 strict attach 已改用 process-local intent，不执行 marker fsync；但带大 temp sidecar、binlog payload 或大量 user vars 的事务仍必须在 T0 前完成 hydrate/plan，不能把大小相关 I/O 留到 gate。

6.1 新增组件

Portable Resurrection Index

跨进程、跨主备传输的认证事实，只包含稳定 ID、物理锚点和 digest，不包含任何内存指针。

Receiver Resurrection Plan

目标 mysqld 当前进程本地对象：定点预验证 Undo anchor、rseg handle、record metadata identity、DD lease、off-list 对象模板和资源预算。receiver 重启后旧 epoch 整体失效，不从文件重建。

Resurrection Journal

记录已经链接的 undo、trx_sys、锁和 Preserve manager 子步骤，用于 gate 失败时按逆序回滚和崩溃后判定。

Target Provenance Registry

在目标 trx 发布前于当前进程绑定 epoch/token/Index/bundle digest，阻止 XA rollback 误处理发布中或 tainted 事务；transfer 接收态不提供跨 receiver restart 保护。

MVCC Horizon Guard

不是单机 target guard：未来协议必须在 FINAL_ACK 前协调源端 ReadView/purge pin、terminal fence、目标进程期 reservation 和 apply-through-fence，完成不可撤回的跨节点保护权交接；ACK 后只剩 target-local active ReadView 安装。

HA Attempt Coordinator

把 apply freeze、fencing generation、500ms deadline、当前进程 epoch commit 和 write-enable 绑定为一次目标端升主调用。角色 ack ambiguity 由 HA authority query 处理；Preserve 不持久化 attempt供重启和解。

Physical Candidate Safety Interlock

启动即强制 super-read-only，并在精确 provenance 尚未在线重建前 quarantine preserve magic XID；只做安全隔离，不做 artifact adopt/resume。

Kernel Resource Lease Manager

统一管理 Undo anchor freshness、record metadata identity、DD/table/index、FD/tmpdir、lock heap 和 target purge reservation；所有 lease 有 cap、generation 和失效回调。record/index 数据页不进入 lease/pin 集合，锁坐标新鲜度由 source-live generation/terminal fence 证明。

Promotion Execution Runtime

T0 前常驻的 worker pool、group-journal writer、monotonic hard watchdog 和 cancellation context；gate 内不创建线程。

Transfer Acceptance Registry

把当前进程 ACCEPTED 与 READY 分开，只在同一 receiver process generation 内提供幂等 status query，处理 FINAL_ACK 歧义；不扫描文件、不跨重启 replay。

术语合同 guard 是源端仍在生效的正确性保护，例如 MVCC horizon 或 live lock generation； reservation 是目标端预留的有上限资源/记账；pause 是 T0 内极短、计入 deadline 的运行时停顿； lease 是可撤销的目标本地对象或 freshness handle。四者不能混用：TTL 只管理可过期 lease/last-mile proof， source structural generation 由事件驱动失效，不靠周期 TTL 猜测正确性。

6.2 状态机

目标态（尚未完整实现）：下面是 SUB500 physical promotion 的状态机；当前 receiver/prewarm 的既有状态仍以第 4.4 节为准，不应把二者混写成当前能力。

OBJECTS_RECEIVING→ APPLY_PENDING→ PREWARMING→ KERNEL_PLAN_READY→ PROMOTION_ARMED→ PUBLISHING→ ADOPTED_LOCKED→ ATTACHING→ ACTIVE
KERNEL_PLAN_READY→ source lock coordinate mutation → LOCK_PLAN_STALE→ re-export + atomic replace → PREWARMING→ terminal fence verified → PROMOTION_ARMED

PROMOTION_ARMED 不是简单重命名。只有 final facts、Resurrection Plan、record-lock plan、 binlog handle、Undo anchor freshness、DD/record metadata identity、source-live lock generation/terminal fence、purge guard、journal slot和成本模型全部通过，token 才能进入该状态。 任一 Undo/DD lease 失效、source lock 坐标 generation 改变、apply generation 改变或 final digest 更新，状态立即退回 LOCK_PLAN_STALE、PREWARMING 或 NOT_READY。

OBJECTS_RECEIVING 到 PROMOTION_ARMED 的每个状态都必须绑定当前 receiver_process_generation。FINAL_ACK 只把 epoch 从 transfer ownership 发布为目标进程本地 ACCEPTED_CURRENT_PROCESS，并不直接推进为 READY/ARMED。receiver 进程退出会整体销毁该状态机； 旧文件不能作为新进程的起点。只有同一进程内的 target worker 和未来 HA 专用命令可以继续推进。

备机启动不等于 promotion 当前通用 startup 对本地 preserve artifact 仍按原合同执行；但 transfer receiver artifact 不属于该合同。 receiver restart 后不加载 spool、epoch fact、commit marker、standby-pending snapshot、ready cache 或 transfer provenance， 不 claim/adopt/attach/resume，也不在线重建旧 registry。未来物理 candidate role 可以负责强制只读安全隔离， 但不能把残留 transfer 文件重新变成有效 epoch；HA 若要使用 Preserve，必须拥有当前 receiver 进程新接收并 ACCEPTED 的 epoch。

7.1 Token、XID 与 peerid 合同

  • token = uint64_t(source THD::thread_id())，即 proxy peerid 中的 Tx；manifest、Index、epoch fact 和 API 全程只保留这一份值。
  • token 不是跨重启全局 UUID；其有效键是 (source server/boot incarnation, epoch, token)。同一 live source/epoch 必须做冲突检查，源端重启或 peer connection 断开使旧映射失效。
  • 该取值只属于 transfer policy。现有本地 shutdown/startup 继续使用 generate_preserve_trx_token()，不改变其 artifact、用例和 SQL token 兼容性；现有 carrier 文件名/legacy API 如需字符串，统一做无损十进制编解码，canonical manifest/Index 字段仍是 uint64_t。
  • Preserve 内部 XID 由 token 和固定 domain/format 规则派生；Index 可以保存完整 XID 与 digest 用于交叉验证，但不能再保存一份同义 source connection id。
  • 目标端真正 attach 时由生产 peerid provider 把 Tx 映射到 Ty，并返回已 pin、已 quiesce 的 THD handle。当前按同 ID 查找的 resolver 只能作为测试占位实现。
  • 源连接在 source 收到目标 FINAL_ACK 前断开时，本轮 transfer 必须失败且 token 不得 ready；若 ACK 不明确，只允许查询同一 receiver 进程 registry。FINAL_ACK 后 target 可独立 prewarm/promotion/adopt，但 receiver restart 会使该 epoch 整体失效。自动 attach 仍要求 proxy 提供有效 Tx→Ty handle，映射丢失时只能保持 ADOPTED_LOCKED 或走明确的人工/客户端恢复策略，不能按 thread id 猜测改绑。

7.2 LSN 坐标合同

当前 source fact builder 采样一次“当前 redo LSN”，同时填充 source_prepare_lsn 和 source_epoch_commit_lsn，只适合骨架验证。目标实现必须从 trx_prepare_low() 的 mtr commit 结果取得每事务 true_prepare_lsn；在 epoch 内全部事务已经进入 PREPARED、事实对象已封口后， 再在同一源端 InnoDB redo 坐标系采集 source_epoch_commit_lsn。必须满足： 

max(token.true_prepare_lsn) <= source_epoch_commit_lsn
source_epoch_commit_lsn     <= source_fence_lsn
source_trx_id_store_lsn     <= source_fence_lsn
source_lock_plan_fence_lsn  <= source_fence_lsn
required_apply_lsn           = max(all true_prepare_lsn,
                                   source_epoch_commit_lsn,
                                   source_trx_id_store_lsn,
                                   source_lock_plan_fence_lsn)

只有目标明确属于同一物理复制谱系、applied LSN 与源端 redo LSN 可比较时，上述 barrier 才成立；跨谱系、 逻辑复制或坐标无法证明时必须 fail closed，不能用时间戳、GTID 或“已追平”文本状态替代。

fence proof 还必须携带源端在同一冻结代际下的 source_trx_id_store、该 header 写入的 redo LSN，以及按 原生启动公式计算的 source_safe_next_trx_id_floor = 2 * TRX_SYS_TRX_ID_WRITE_MARGIN + align_up(source_trx_id_store, margin)。provider 必须证明目标已物理应用到该 header LSN，并从目标真实 TRX_SYS page 读回同值；所有 imported trx_id 必须严格小于该 safe floor。apply 仍运行时禁止目标本地改写 TRX_SYS_TRX_ID_STORE，否则会污染物理谱系。T0 freeze 后只在 trx_sys_mutex 下把进程内 max_trx_id 单调提升到 max(source safe floor, target current floor)；崩溃重启仍可由已复制的 source header 按原生公式重建。source header fact 后续变化会使 ARMED 失效，重新应用并验证前不得进入 T0。

该 LSN 不能靠猜测“最近 redo LSN”获得。源端在 epoch fact 封口时调用 transfer-only 的 trx_preserve_capture_durable_trx_id_store_fact()：持 trx_sys_mutex，把当时 max_trx_id 写入原生 TRX_SYS header，并返回该 mtr commit LSN 和 store 值。它只在 preserve_trx_enable + transfer epoch 下执行，不给 trx_sys_get_new_trx_id() 通用热路径增加 HA/transfer 逻辑。目标 required-apply barrier 覆盖此 LSN；后续 source header 更新由 provider generation/页事实使 ARMED 失效并刷新。 

trx_preserve_trx_id_store_fact_t fact;
trx_preserve_capture_durable_trx_id_store_fact(&fact);
// fact.store_value, fact.redo_commit_lsn,
// fact.safe_next_floor = 2 * margin + align_up(store_value, margin)

temp-only token 没有 redo PREPARED anchor，不能伪造 true_prepare_lsn。Index 必须用显式 TEMP_ONLY_NO_REDO flag 表示该事实，required_apply_lsn 取 epoch commit/fence barrier，正确性另由 owner trx id、no-redo slot/page ownership、sidecar digest 和 target reservation 证明。Index 可以为未来 mixed/temp profile 描述这些对象，但初始 SUB500_ADOPT 只接受纯 redo-prepared token：只要 bundle 含任何 no-redo/temp 组成就返回 UNSUPPORTED_NOREDO_PROFILE。在 no-redo publication、ownership、rollback 和同进程可逆 journal 具有完整正向与逆向证明前， mixed 不能因为“同时具有真实 redo prepare LSN”而进入当前认证包络。

7.2.1 Source live lock-plan generation 与 terminal fence

payload digest 不是物理坐标新鲜度证明 当前 lock_preserve_build_record_lock_metadata_facts() 从导出 payload 本身计算 final_lock_generation_digest 和 page-layout facts；receiver 对同一 payload 重算仍只证明传输完整性。 strict metadata apply 又直接消费 page_no + heap bitmap。因此导出后发生同页 purge reorganize、页 split/merge、 lock inherit/move 时，即使 space_id/page_no/index_id/DD generation 都未变化，旧 heap 坐标也可能已失效。 去掉 legacy page prefetch 没有“制造”该问题：legacy 本地 import 可借 record images/读页做 heap relocation，而 strict metadata-only 路径从来没有这条解析能力；本设计必须由源端 live 事实闭环，不能重新引入目标 record-page 读取。

不能静默改变已落盘 final_lock_generation_digest 的含义。协议升级为 version 2，并把两个事实域分开： lock_object_digest 保持 transport/object integrity；新字段 source_lock_plan_generation/source_live_lock_plan_digest/source_lock_plan_fence_lsn/source_record_store_fingerprint 证明 source live lock_sys 的代际与终止时点。缺失 v2 live proof 的 artifact 可以继续供 legacy/local 路径使用， 但不得进入 SUB500 strict PROMOTION_ARMED。

  1. 源端 seal 前先完成 lock mirror 的完整性闭环。复用现有 lock_warmcopy_record_store_fence_t 的 shard count、mutation/dirty generation 和 canonical fingerprint；补齐 same-page reorganize 的 bulk bitmap reset，以及 split/merge/inherit/move 等所有坐标变更族。
  2. 热路径只允许在 preserve_trx_enable + active transfer epoch + token tracked 下执行 O(1) generation/dirty 标记；禁止在 lock_sys 热路径做 hash、I/O、allocation 或协议发送。
  3. 首次 seal 导出 payload 时记录 generation/fingerprint。seal 后到 T0，只要相关 live lock 坐标变化，源端事件 hook 就把 token 标记为 LOCK_PLAN_STALE 并撤销 ARMED；可选 apply-provider page-touch tracking 只能作为保守补充 invalidator，不能代替 source-live authority。
  4. 后台 source sender 对 stale token 从 live lock_sys 重导出完整 lock payload；receiver 先保存新的当前进程 object，再以 generation-checked manifest/fact CAS 原子替换旧对象和内存 plan。digest mismatch 只会发现问题，不能修复，因此“重导出 + atomic replace”是协议必选项。
  5. 计划升主的 terminal source fence 不是一次普通采样。source coordinator 先关闭新用户写与 DDL，再用 attempt-scoped、可和解的 quiesce provider 停止/排空所有可能搬移 tracked lock 坐标的 producer，包括 purge、B-tree reorganize/split/merge 和 background change-buffer merge；然后关闭 mutation admission、等待 in-flight callback 为 0，重读 live generation/fingerprint 并封口最终 source_live_lock_plan_digest + source_lock_plan_fence_lsn。不得跨网络等待长期持有 lock_sys/page latch，也不得通过随意翻转未归属本 attempt 的全局布尔量冒充 fence。provider 无法证明 no-more-mutations 时 fail closed。
  6. terminal fence lease 必须持续到 target 已 apply/freeze 到该 LSN 且 promotion commit 完成；promotion abort 只有在重新启用 source 写之前释放 lease，释放后旧 ARMED proof 立即失效。目标 gate 比较 receiver plan 与 terminal proof，但仍不读取 record/index 页。
  7. 源端在 authenticated terminal fence 前死亡，无法证明旧 payload 是最终 live 坐标，token 永久 fail closed/abandon；若 terminal fence 已认证、目标已应用并验证到该 LSN，之后源端死亡不自动使当前 receiver 进程内 token 失效。
LOCK_PLAN_CURRENT(generation=g)
  -- relevant source lock coordinate mutation --> LOCK_PLAN_STALE(g+1)
  -- live re-export + receiver atomic replace --> LOCK_PLAN_CURRENT(g+1)
  -- terminal no-more-mutations fence --> LOCK_PLAN_TERMINAL_VERIFIED
  -- target applied_lsn >= source_lock_plan_fence_lsn --> PROMOTION_ARMED
两个独立 release blocker A：seal 前 mirror/fence 必须覆盖 per-bit 与 bulk mutation，尤其 same-page reorganize 的 bitmap reset； B：seal 后直到 T0 必须具备事件失效、重导出、receiver atomic replace 和 terminal fence。 任何一个未完成，strict record-lock token 都不得 ARMED，即使三个 page-read/ibuf/local-redo 零指标成立。

7.3 启动期 Index 快速恢复：尽早识别，但不提前 claim

这是本地 startup 性能优化的关键项。当前 trx_undo_lists_init() 必须遍历 rseg slot 并读取 Undo header/last page；随后 trx_resurrect_insert/update() 会在 rw_trx_list 建成前调用 trx_resurrect_table_ids() 扫描 Undo body。preserved_trx_recover_all() 的调用位置远晚于这些 I/O， 因而只优化该接口本身无法达到目标。目标控制流如下：

三层状态必须分开 第一层是认证 Index 中的 startup candidate classification，它只是按 trx_id 命中的进程内加速提示；第二层是原生 Undo/rseg resurrection 构建出的 TRX_STATE_PREPARED trx_t，并照常加入 rw_trx_set/rw_trx_list/rw_trx_ids； 第三层才是完整 bundle、XID、prepare LSN 和 Undo anchors 校验通过后，由 shared recover/adopt 执行的 PREPARED -> PRESERVED claim。第一层绝不能冒充第三层，也不能新增一个会改变 InnoDB rollback/accounting 语义的“早期 PRESERVED”状态。

Receiver Plan、ready cache、provenance 和 lease 都绑定当前 receiver_process_generation。同一进程内 cache 只有在 READY 前才允许 receiver worker 从其仍拥有的内存对象/临时 external payload 重建；READY 后 semantic bundle、Index、 lock plan 和 native binlog handle 已原子转入 prepared-token resources，receiver staging 随即释放。此后 cache/lease 缺失必须 降级为 NOT_READY 并 fail closed，不能在 gate 冷读文件。receiver 重启则旧 epoch 整体失效， 不调用 preserved_trx_rebuild_standby_prewarm_state() 扫描残留 standby-pending，不恢复 cache/provenance/lease， promotion gate 对旧 epoch 返回稳定的 RECEIVER_EPOCH_INVALID。

  2. 等待 applied_lsn >= max(true_prepare_lsn, epoch_commit_lsn, source_trx_id_store_lsn, source_lock_plan_fence_lsn)，但此时不冻结 apply；任一坐标尚未形成 terminal proof 时只能 PREWARMING。
  3. 取得 apply provider 的 rseg_memory_generation/coherent_lsn，证明目标全量 rseg 内存 lists/accounting 已与该 applied LSN 对齐；否则不能只修 selected token 冒充全局一致。
  4. 按 anchor 定点读取 rseg slot、Undo header 和最后一页；核对 PREPARED、XID、trx_id、type 和 stable digest。
  5. 解析 insert/update redo undo。初始 SUB500 遇到任何 no-redo/temp 组成立即返回 UNSUPPORTED_NOREDO_PROFILE；mixed/temp 的 sidecar 与 ownership validation 只属于未来独立 profile，不得混入当前成功 SLO。
  6. 创建 off-list trx_t、trx_undo_t template、ReadView、锁节点和 journal delta。
  7. 根据 exact modified table IDs 打开 DD/table/index，并持有有期限、可失效的本地 lease。
  8. 构建 record-lock metadata plan，按 space_id/page_no/index_id/DD generation 建立静态 identity，并绑定 source-live generation/live digest/record-store fingerprint。SUB500 strict path 必须绕过 trx_preserve_prefetch_record_lock_pages_for_gate()，不得调用 buf_read_page() 读取 record/index 数据页，也不建立 record-page lease/pin；source generation 变化时 plan 立即 stale，等待重导出和原子替换。
  9. 准备 native binlog handle、MDL descriptor plan、savepoint plan、temp materialize plan。
  10. 在当前 receiver process generation 的 registry 中登记 XID provenance，并把 token/epoch/Index/bundle digest 加载到内存保护表；这是 prewarm 的 TARGET_PROVENANCE_REGISTERED，必须早于 trx publish，但不等于 gate 已验证。
  11. 若 update-undo 含 GTID，只从真实 header 校验 descriptor 并保存 idempotency key/digest；prewarm 不调用 persistor。当前普通不可查询的 add() 不足以让 token ARMED，因此初始 SUB500 直接拒绝该 token。
  12. 为 ReadView 申请有界 purge-horizon reservation；历史已越界或 reservation 超出资源 cap 时拒绝，不破坏当前进程已接受的 transfer 文件，但 token 不得 READY。
  13. 预创建进程内 epoch journal和必要临时 marker，不执行 file/directory fsync；预留 worker slot、内存、FD、tmpdir 和 lock heap。
  14. 运行 aggregate cost 模型；token 数、锁/MDL规模和 worker wave 全部计入预计总 gate，要求 ≤400ms，给运行时 450ms ceiling 留出预测误差。
SUB500 strict 的 T1 前零副作用合同 ibuf/change buffer 不是 Buffer Pool 访问接口；风险来自 legacy helper 发起普通 buf_read_page() 后，二级索引叶页 I/O completion 可能顺带 merge buffered changes。 从 strict prewarm 进入认证准备直到 T1，record/index 数据页读取必须为 0、change-buffer merge 必须为 0、由 Preserve strict path 产生的 target-local redo bytes 必须为 0。三个计数必须按 promotion attempt/strict executor scope 采集；target-local redo 不包含 物理 apply 输入。Undo header/last-page 的定点 anchor 读取仍允许并单独计数，因为 Undo tablespace 不使用 change buffer；该例外不能扩展到普通索引数据页。本文不把 ibuf 设计为 Resurrection Index anchor/baseline，也不允许通过 在线切换 crash-recovery 全局 recv_no_ibuf_operations 来满足指标。T1 后节点已取得 authoritative write 权限，恢复新主 正常的 change-buffer merge 和 redo 行为。
“空 ReadView”的业务含义 初始 SUB500 不是按 isolation level 名称粗判。RR 事务一旦执行过普通一致性读或显式 consistent snapshot，通常会持有持续 ReadView， 因而在跨节点 horizon handoff 完成前不准入；SELECT ... FOR UPDATE 属锁定读，本身不创建该 ReadView，但必须满足完整 lock-plan generation/terminal fence 合同。RC 的 view 可能是 statement-scoped，准入看 freeze 时真实 ReadView 是否仍存在， 不能仅凭“RC”放行，也不能仅凭“RR”拒绝从未做一致性读的事务。

9.1.1 跨节点 MVCC horizon 交接

FINAL_ACK 后 source 已退出，不能把 ReadView handoff 留到 promotion 目标端仅暂停本地 purge，无法阻止 source 在释放 live ReadView 后产生 purge redo。任何要求 promotion 时再向 source 请求 pin/release 的方案都违反 FINAL_ACK 所有权边界。因此初始 strict profile 对非空 ReadView 稳定返回 UNSUPPORTED_MVCC_HANDOFF。
SOURCE_VIEW_PINNED→ SOURCE_TERMINAL_FENCE→ TARGET_APPLIED_AND_RESERVED→ FINAL_ACK→ SOURCE_DECOUPLED
  • 未来若支持非空 ReadView，source pin、terminal no-more-redo fence、target apply-through-fence、history verification和target horizon ownership必须全部在 FINAL_ACK 前完成。
  • FINAL_ACK 返回后，target 必须能仅凭当前进程 reservation/plan 独立完成 view install、promotion 或 abandon；不能再向 source 发送 release ack、重导出请求或状态上报。
  • 任一前置证明缺失时，该 token 不进入本次可接受 epoch；不得先 ACK 再期待 promotion 阶段补齐。
  • receiver restart 仍使 reservation/epoch 全部失效，不做 handoff replay。该协议和真实物理复制 purge E2E 完成前，不扩大初始支持面。

receiver 在 COMMIT_EPOCH 中完成 strict v4 immutable epoch fact 的当前进程保存后，先把 epoch 原子发布到 receiver registry，再返回 FINAL_ACK；ready cache/补投 prewarm job 属于 target 后续工作。transfer ACK 与 promotion readiness 必须完全解耦：

  • strict v4 epoch fact/commit state 只保存在进程 registry，phase-2/COMMIT 不写 spool；外置大对象临时文件也只做普通 write/close，不提供 crash durability。transfer file fsync=0、directory fsync=0。registry 必须先于 FINAL_ACK 发布完整 token set、digest 和 process generation。

FINAL_ACK 到全部 prewarm 完成的正式计时口径 T_ack 取 receiver 已完成 ACCEPTED 发布并生成 FINAL_ACK 的 monotonic timestamp； T_token 取该 epoch 所有 token 完成 hydrate、strict prepare、prepared-resource/ready-cache 发布和 staging finalize 后的最大 monotonic timestamp；T_all 再取 T_token 与全部 object-prewarm job 结束时间的最大值。只有同时观测到 receiver_queued_bytes=0 且 receiver_worker_active=0 时，T_all - T_ack 才能称为“FINAL_ACK 到全部 prewarm 完成”。报告分别输出 receiver_all_token_prewarm_after_final_ack_us 和 receiver_all_prewarm_after_final_ack_us；不能用最后一个已观测 job、READY timestamp 或 source phase-2 结束时间代替。

这里的“prewarm 完成”只表示 target 当前进程的全部 receiver 后台准备工作已经结束，不表示 READY_FOR_GATE、adopt/resume、HA authority 或 write-enable 已满足。当前没有 production physical provider 时，epoch 可以完成全部 prewarm 而保持 COMMITTED_NOT_READY；因此该时间可由 standalone 双 mysqld 真实测量，无需等待物理备机升主功能。

10.3 发布顺序

  1. 复核 authority attempt/fencing generation、deadline 和 token registry lease；确认 target 以 innodb_read_only=OFF 启动且仍由 candidate interlock 保持 super-read-only。
  2. 在已持有的 Undo page lease/resident contract 上复核 rseg slot、Undo state、XID、trx_id、type、header digest 和 last-page facts。
  3. 确认 prewarm 已完成 TARGET_PROVENANCE_REGISTERED；gate 从当前 process generation 的 registry-owned artifact 与内存 entry 重新比对 token/XID/trx_id/epoch/Index/bundle digest，成功后记录 TARGET_PROVENANCE_VERIFIED。
  4. 确认 source terminal lock proof 已认证、目标 applied LSN 覆盖 source_lock_plan_fence_lsn，且 receiver plan 的 source_lock_plan_generation/source_live_lock_plan_digest/source_record_store_fingerprint 全部相等；记录 LOCK_PLAN_GENERATION_VERIFIED。任一不一致进入 LOCK_PLAN_STALE，不得现场读 record/index 页或继续发布。
  5. 在 rseg latch 下把 selected slot 分类为 EXACT_EXISTING_ACTIVE、EXACT_EXISTING_CACHED、PROVEN_ABSENT 或 CONFLICT：active 直接复用；cached 对称转 active；仅 proven-absent 创建/链接并应用一次 size/monitor delta；conflict 失败。
  6. 填充 trx_t 的原生 resurrect 字段，合并 insert/update 的 undo_no 和 DDL/GTID flags；初始 SUB500 对 GTID token 已在 admission 拒绝，gate 不调用当前不可查询、不可撤销的 persistor add()。
  7. 复核目标真实 TRX_SYS page 的 source-derived header fact 与 final fence 一致、其 redo 已应用，且原生 safe floor 覆盖全部 imported trx_id；在 trx_sys_mutex 下只单调提升进程内 max_trx_id。不得把 trx_sys_flush_max_trx_id() 的 read-only no-op 当证明，也不得在 apply 活跃期预写目标本地 header。
  8. 在同一 trx_sys_mutex 临界区发布 rw_trx_set/rw_trx_list/rw_trx_ids、降低/重算 min_active_id。只有 NEWLY_PUBLISHED 才增加一次 publication n_prepared_trx delta；IDEMPOTENT_EXISTING_MATCH 为 0。不得修改 found_prepared_trx：该字段由 trx_lists_init_at_db_start() 在启动恢复结束时根据当时的 prepared 数量设置，并被 upgrade/DD cache 路径解释为启动期历史事实，不是在线 prepared 事务的实时状态。
  9. 根据 exact modified table set 填充 mod_tables 并恢复基础 IX；不调用 Undo body 遍历。
  10. 把明确的 trx_t* 交给新的 shared adopt overload，避免再次按 XID 扫描和 claim race。
  11. 按跨节点 handoff 合同安装 ReadView，使用 origin-aware API 安装显式 table locks，再应用 record lock metadata plan 和 bounded MDL backup，注册 Preserve record。
  12. worker 返回成功后不自行释放 lease，由 epoch coordinator 统一 commit 或 abort。

10.5 Epoch 原子性

对同一 promotion epoch 采用 all-or-nothing：只有全部 token 成功并且最终 fence revalidate 通过，才写 ADOPTED_LOCKED_COMMIT 进程内状态并打开写权限。任一 token 失败则整个 epoch 保持只读，成功 worker 的对象按 journal 逆序撤销。无法证明完整撤销时状态为 CLEANUP_TAINTED，当前进程必须保持只读并由 HA 放弃本轮 attempt； 进程崩溃/重启后旧 receiver epoch 无条件失效，绝不在 startup 自动续接或部分开写。

10.6 500ms 硬 deadline 的执行模型

现有同步调用模型不能单靠函数内的 if (now > deadline) 保证 500ms，因为 fence provider 或某个 worker 可能在检查点之间阻塞。process-local marker 不执行 fsync；目标实现仍必须把“是否允许开写”和“后台任务何时最终退出”分离：

当前 strict 路径使用 my_micro_time()，并在写完 ADOPTING intent 后才构造 fallback deadline；虽然 fallback 以函数入口 started_us 为锚，但前置阶段没有一致的 deadline check，wall clock 也可能跳变。目标 request 必须由 HA coordinator 在进入任何 gate 工作前记录 T0=steady_clock，传入不可修改的 monotonic absolute deadline；所有 phase、 future wait、provider call 和最终 writable CAS 都消费同一个对象，禁止子层重新起表或把 prework 排除在 500ms 之外。 

ARMED -> FENCED -> ADOPTING -> COMMITTING -> PROCESS_COMMITTED_READONLY -> WRITABLE
   \         \          \          \
    +----------+----------+-----------> HARD_TIMED_OUT
                                      \
                                       +-> WRITE_ENABLE_INDETERMINATE

WRITABLE transition requires one CAS with all conditions:
  state == PROCESS_COMMITTED_READONLY
  authoritative_ha_lease_valid == true
  gate_generation == expected_generation
  now_us < hard_deadline_us
  final_fence_revalidated == true
  source_lock_plan_terminal_verified == true
  process_epoch_commit_visible == true
  adopted_count == token_count
  tainted_count == 0
  candidate_started_with_innodb_read_only_off == true
  write_enable_authority_result == GRANTED
  • promotion coordinator、worker pool 和 fence provider 都是 T0 前已存在的常驻执行单元；journal 是预分配的进程内对象，不需要专用 fsync writer。
  • hard watchdog 只能把尚未 process commit 的尝试推进为 HARD_TIMED_OUT。process commit 后若 HA write-enable 结果不明确，返回 WRITE_ENABLE_INDETERMINATE 并保持只读；角色结果由 HA authority query 处理，不从 Preserve marker恢复。
  • worker 在 Undo 复核、rseg 发布、trx_sys 发布、每个锁分块和 MDL 前检查 generation/deadline。迟到 worker 只能回滚或进入 TAINTED quarantine。
  • 超时后 fence/epoch context 由同进程后台 cleanup 持有；新的 promotion 请求在 cleanup 完成前被拒绝。receiver restart 直接清空该状态，不做 reconcile。
  • 任何迟到的 fence 或 worker 成功都不能从 HARD_TIMED_OUT 转为 WRITABLE。
  • 每次尝试绑定 attempt_id + fencing_generation。HA 在 authoritative provider 查询/撤销旧 lease 前不得选择另一 candidate；同一进程可在 cleanup 完成后以新 lease 重试。
  • 节点永远不能因“commit 后发现自己其实成功”而自行打开写；write-enable 必须由仍有效的 authority 调用，并可查询最终角色状态处理 ack loss。
硬 deadline 保证的含义 eligible 请求要么在 500ms 内完整成功并开写，要么在 500ms 内明确失败且保持只读。 若 process commit 已发生但 authority/write-enable 结果未确认，则返回“HA 角色结果不明确且保持只读”，由 HA authority query 处理，而不是依赖 Preserve 文件和解。 它不承诺慢盘或内核卡死时仍能成功，只承诺不会在 500ms 后“迟到成功”并擅自打开一个事实不完整的新主。

11. Adopt 与 Resume

11.1 默认 profile：先开写，后 resume

Preserve 事务本来就是 detached transaction。升主时恢复其内核对象和锁，即可保护并发正确性；不需要为了打开写权限 立即把它绑定到某个用户连接。默认 profile 因此把 session、user vars、GTID、temp table attach、savepoint 和 artifact cleanup 放在 T1 之后。

PREPARED on disk→ PUBLISHED_PREPARED→ ADOPTED_LOCKED→ T1 / write enabled → ATTACHING→ ACTIVE→ CLEANUP_PENDING

11.2 Inline activation profile

只有满足以下附加条件，才允许把 ACTIVE 也纳入 T1：

  • 所有 token 已有受保护、pristine、预绑定的目标 THD；不设固定 N 上限，但总 attach 成本必须通过容量模型准入。当前 simulator 仅认证 N=1/3。
  • session/user vars/savepoints 已解码成目标本地 plan，大小受 release profile 限制。
  • native binlog handle 只转 ownership，attach 过程中 read_bytes=0/write_bytes=0/rename_count=0。
  • 临时表 fil_space、DD/table/index 和 no-redo undo 已 detached materialized，gate 只转 ownership。
  • ATTACHING/ACTIVATING/ACTIVE 使用进程内 epoch group journal，不做每 token atomic-file fsync。
  • MDL backup、snapshot、sidecar、provenance 的删除全部进入异步 cleanup。
当前代码需要改造 本地 SQL resume path 仍会写 durable consume intent，并执行 temp materialize 和多类文件删除；strict promotion attach 已改用 process-local intent，但大对象物化和清理仍必须前移或异步化。在这些工作完成前，不能对 Inline activation 宣称 500ms。

11.3 当前已关闭项与仍待统一的复用

  • 已实现：promotion record 以 non-resumable ADOPTED_FOR_PROMOTION 注册，关闭 adopt 到 attach 窗口的普通 SQL RESUME 抢占。
  • 已实现：Preserved_trx_peer_thd_handle 固定 THD 生命周期、阻止新命令、推迟 KILL，并在 attach 前校验 idle/pristine，关闭裸 THD* UAF 和并发接管问题。
  • 部分复用：SQL resume 已抽出 preserved_trx_resume_record_on_thd()，但 promotion attach 仍有一套独立的长流程；应继续抽取 session/binlog/MDL/GTID/temp/trx/savepoint 的 policy-driven core。
  • 未实现：生产 peerid Tx -> Ty resolver。免权限的 PROMOTION_RESUME_ON_THD policy 只能由内部 HA 入口构造，继续由 source-shape lint 锁定，任何用户 SQL/COM 路径不得传入。

record lock 往往是最慢且随规模增长的阶段。不能凭经验固定“允许多少 pages/bits”；release 构建必须通过校准测试生成 认证包络和保守系数，再由准入公式计算： 

estimated_worker_us = p99_base
                    + C_anchor * undo_anchor_count
                    + C_table  * modified_and_locked_table_count
                    + C_page   * record_lock_page_count
                    + C_bit    * record_lock_bit_count
                    + C_mdl    * mdl_ticket_count

estimated_epoch_us = fixed_gate_us
                   + max(max_token_us,
                         sum(token_estimated_us) / ready_worker_count)
                   + scheduler_wave_margin

PROMOTION_ARMED only if:
  estimated_epoch_us  <= 400000
  and every hard resource cap passes

400ms 是 T0 前的保守 epoch admission 阈值，包含 token 数、每 token 对象成本、worker wave 和模型误差； 320ms/450ms 是 gate worker-pool/epoch 的成功 ceiling。该公式按成本准入而非按 N 拒绝：超出当前窗口只保持 NOT_READY， 可通过更多预热、经认证的 worker 配置或后续窗口推进，不产生永久的 token-count unsupported。运行时超过 ceiling 记 SLO miss； 任一阶段接近 500ms hard deadline 都不得开写。

  • 本地 preserve → shutdown → startup：继续使用 default store durability、startup preflight、Resurrection Index 和 preserved_trx_recover_all()；这是唯一跨 mysqld 进程恢复 Preserve 状态的场景。

  • production apply/freeze/fence provider 有独立 SLA：在复制追平、只读业务压力、CPU steal 和 provider generation 切换下分别报告 freeze/fence P50/P95/P99/max；其认证上界必须落在 35ms phase 预算内，默认 MISSING_PROVIDER 或 simulator provider 不得用于 release 证明。
  • 测试报告包含 max，不只包含平均值/P95；每个超 450ms 样本有 phase 和 first miss reason。
  • eligible 成功路径的所有冷操作零值断言成立；其中 record_index_page_reads=0、ibuf_merges=0、target_local_redo_bytes=0 为独立 release blocker，Undo anchor 定点读取按有界非零指标单列。
  • 每个成功 token 的 source/receiver/gate lock-plan generation、live digest、record-store fingerprint 和 terminal fence LSN 全部匹配；seal 前 bulk mutation coverage 与 seal 后 stale/re-export/atomic-replace 故障矩阵均通过。这一项与三个零指标是并列 blocker，互不替代。
  • ineligible 快速拒绝、fence mismatch、process-local marker 写失败和资源耗尽均不会误开写；strict promotion/transfer receiver 不得产生 fsync。
  • 启动共享路径从 trx_sys_init_at_db_start() 前计时，Index 命中事务 Undo body scan=0；结果不能冒充在线 promotion E2E。
  • 预算数字由 release 校准生成，10k simulator 与数百次真实物理结果分别报告。

19.3 运维准入

  • HA 控制面只选择持续 ARMED 的 target；没有 ARMED candidate 时明确走普通升主或拒绝，而不是偷偷扩大 Preserve gate。
  • 监控覆盖 ARMED token 数、age、失效原因、apply lag、Undo anchor freshness、record metadata identity、source lock-plan generation/reexport/drift/terminal fence、三个 strict 零指标、process-local marker错误和 worker backlog。
  • BUSINESS_FIRST 为默认，ready cache、target purge horizon、source history retention、IO、inflight bytes 和 worker CPU 都有硬 cap；只读业务回归达标。
  • 告警区分“数据库 promotion >500ms”“candidate 不 eligible”“外部选主/路由慢”。
  • 有 TAINTED/cleanup pending 的同进程放弃流程、receiver restart 全量失效/残留清理规则和禁止强行开写的保护；没有 Preserve restart reconcile。
  • 有 COMMITTED_NOT_READY、WRITE_ENABLE_INDETERMINATE、MVCC handoff 失效、peerid 失效和永久无法 re-arm 的值班决策；角色歧义交给 HA authority query。
