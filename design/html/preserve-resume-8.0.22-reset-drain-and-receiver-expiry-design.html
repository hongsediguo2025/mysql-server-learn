Preserve/Resume 8.0.22 · HA 内核能力预埋

RESET DRAIN 与 Receiver 自动失效设计

目标只有两个：HA 取消切换时，source 快速恢复为正常主库；target 已接收但未被升主采用的 Preserve 内核对象，在当前 mysqld 进程内按两段超时自动销毁。RESET 同步路径只负责恢复连接与事务可执行性， 其余 worker 退出和物理清理由后台收敛；两端在 FINAL_ACK 之后不再互相控制。

1. 设计结论

本设计不引入分布式回滚协议，也不让 source 管理 target 的后续生命周期。内核只提供 HA 需要的两个简单能力。

Source：快速取消 DRAIN

HA 执行 RESET DRAIN。命令通过一个进程内 drain attempt 原子抢占取消权，立即停止新 phase2 工作和后续 COMMIT 发布；原 DRAIN owner 复用已有 reattach/activate 逆路径恢复原事务。RESET 等待全部受影响原连接 回到可执行状态并解除本 generation 的 CLOSING/batch gate，但不等待 sender 临时资源、participant 或网络清理完成。

Target：自动失效 Preserve candidate

target 在 FINAL_ACK 后独立 prewarm。10 秒内未形成 epoch READY，或 READY 后 30 秒内未被 HA 取得 ADOPT_LEASED，现有 1 秒 reaper 调用统一 destroy_epoch() 逻辑失效并异步释放对象。HA 不主动调用销毁，source 也不回头干预。

最重要的成功点 RESET DRAIN 返回 OK 表示 source 已经可以继续作为主库提供普通服务，并且本次 generation 的全部原连接 都已恢复为可运行状态：原 trx_t 已重新挂回原 THD、batch state 已清为 NONE、CLOSING/batch gate 已解除。达到该点后命令立即返回，不等待 worker join、participant teardown、sender 临时资源、文件删除或 target orphan candidate 清理；这些动作只能在后台继续，且不得再改变连接的可运行状态。
RESET 同步屏障：RESET_WON → ALL_TRANSACTIONS_RUNNABLE → RESET OK
异步尾部：WORKERS_QUIESCED → CLEANUP_DEBT_DRAINED；不参与 RESET response
不可混淆 receiver 的 transfer 文件只是当前进程的容量扩展，不具备 crash durability。receiver 重启后 epoch/token 全部失效， startup 删除残留，不 replay、不恢复 READY。local preserve→shutdown→startup resume 的 durable carrier 语义保持不变。
外部接口合同不在本文重复定义 HA 控制连接身份、4020 唯一承诺、DRAIN survivor/excluded 结果和代理重放顺序，以 Transfer Phase 2、4020 挂起与 Tx→Ty 事务续作对接指南 为权威面。本文只定义 RESET 的 source 恢复屏障和 receiver TTL。

2. 背景、场景与 HA 关系

该能力服务于计划内主备切换。HA 先在 source 执行 DRAIN TRANSACTIONS PRESERVE，source 将事务内核对象构建并 transfer 到 target。target 返回 FINAL_ACK 后，自行 prewarm，未来由 HA 在目标端调用 promotion 内部接口完成 adopt/resume。

分支连接命运请求续作
FINAL_ACK / promotion 继续 旧 source 普通连接保持 CLOSING，随后随 source handoff/shutdown 关闭。 Proxy 等 HA 在新主完成事务 RESUME，再重发完整 4020 或计划内断连留下的唯一在途请求。
本地 shutdown/startup 旧连接随 mysqld shutdown 关闭，startup 后建立新连接。 新连接先 RESUME，再重发终态前未执行的唯一在途请求；这不是 RESET 分支。
RESET DRAIN 赢 mysqld 不退出，原连接与原 Tx 恢复可运行。 完整收到 4020 的请求在 RESET OK 后重发；未被 mysqld 读取的 packet 留在原 socket，自然执行且不得复制重发。
RESET 与终态断连必须分开 promotion 和 shutdown/startup 最终都会销毁旧连接，因此无需新增逐 THD response fence；RESET 则保留原连接， 只需恢复原事务并解除现有 CLOSING/batch gate。普通网络故障不属于任何计划内分支，仍按结果不确定处理。
1. HA 发起 DRAINsource phase1 预构建；phase2 阻断并 preserve
2. Target 接收在线保存、校验、受限 prewarm
3. 本地竞态source RESET 与 FINAL_ACK terminal CAS 二选一
4A. FINAL_ACK 赢source shutdown；target 等 HA promotion 或 TTL
4B. RESET 赢source 恢复；target orphan candidate 等 TTL 销毁
HA 与内核的职责切分 HA 决定“继续切换”还是“取消切换”，并调用 source 的 RESET 或 target 的 promotion 接口。内核不推断 HA 意图、不在两端 建立长期控制关系，也不实现 HA authority、write-enable、peerid Tx→Ty provider 或物理复制 apply fence。

取消切换的闭环

  1. HA 在 source 调用 RESET DRAIN。
  2. source 先开放未受影响的普通业务，并在 RESET 返回前把全部受影响原事务恢复到原 THD。
  3. source 不向 target 等待 ABORT ACK，也不查询 READY。
  4. target 若留下已接受 candidate，10s/30s TTL 自动销毁。
  5. TTL 失效后未来 promotion 走普通升主，不因 Preserve candidate 缺失而阻塞。

上述闭环只适用于 RESET 赢得 terminal CAS。若 source 已处理 FINAL_ACK 并进入 SHUTDOWN_HANDOFF，RESET 返回 TOO_LATE，source 继续 shutdown；HA 若随后放弃切换，应按既有主库拉起流程重启 source， 而不是要求 Preserve 内核逆转已完成的 shutdown handoff。

3. 范围与非目标

本轮设计与实现范围

  • RESET DRAIN parser、权限、状态与错误合同。
  • phase1、phase1 closing、phase2、COMMIT/ACK 竞态回撤。
  • source 原事务的快速 reattach/activate、CLOSING/batch gate 解除和业务唤醒。
  • 首版仅支持 STANDBY_TRANSFER_SAVE drain attempt；source 非语义资源清理异步。
  • transfer source 的非阻塞取消与连接 I/O 唤醒。
  • receiver ACK→READY 与 READY→HA adopt lease 两段 TTL。
  • target-local epoch 统一销毁和 promotion SKIPPED 前置结果。

明确不实现

  • receiver crash/restart 后恢复 transfer epoch。
  • local carrier / 本地 shutdown-startup preserve 场景的 RESET；其 durability 与 recovery 语义保持不变。
  • source 通过 RPC 删除 target candidate。
  • 新的分布式 ABORT、二阶段提交或反向 ACK。
  • 新的 timer/cleanup 线程或通用任务框架。
  • 真实物理复制升主 E2E、HA authority、开写 CAS。
  • peerid Tx→Ty attach、真实 production apply/fence provider。
  • 为了 RESET 新增 InnoDB Undo/lock/MVCC 热路径 hook。

本轮可以做 standalone 双 mysqld transfer E2E 和本地 source RESET E2E；不能据此宣称真实物理备机升主已实现或达到某个 SLO。

6. Source 状态与线性化

6.1 两层状态，职责分离

不要把所有并发语义塞进一个 manager enum。设计保留现有 manager state，并增加一个很小的 attempt terminal state。

Manager: IDLE → WARMCOPY_DRAINING / BATCH_DRAINING → RESET_CLEANUP → IDLE
Attempt terminal: RUNNING → RESET_REQUESTED  或  RUNNING → SHUTDOWN_HANDOFF
FINAL_ACK winner: SHUTDOWN_HANDOFF → existing Manager SHUTDOWN_REQUESTED
  • RESET_CLEANUP：普通 SQL/protocol 允许；新的 DRAIN、PRESERVE 控制命令拒绝。
  • RESET_REQUESTED：禁止新 phase2 任务、final metadata、COMMIT 和 shutdown。
  • SHUTDOWN_HANDOFF：只属于 attempt terminal，表示 FINAL_ACK 已在 source 本地生效，RESET 只能返回 TOO_LATE。
  • 原 DRAIN owner 随后用精确 state+owner CAS 把现有 manager 切到 SHUTDOWN_REQUESTED；不新增同义 manager 状态。

6.2 Drain attempt 最小对象

struct Preserve_trx_drain_attempt {
  uint64_t generation;
  my_thread_id owner_thread_id;
  Artifact_mode artifact_mode;
  atomic<Terminal> terminal;        // RUNNING / RESET_REQUESTED / SHUTDOWN_HANDOFF
  atomic<bool> all_transactions_runnable;
  mutex sink_mutex;
  Preserve_trx_transfer_encoded_frame_sink *cancel_sink;
};

全局只保存一个受 mutex 保护的 shared_ptr 指向当前 attempt。它不拥有 trx_t*、THD 或 participant， 不暴露 DRAIN 栈上的 vector；原 DRAIN owner 始终是内核对象逆操作的唯一执行者。RESET 线程只做 CAS、请求 transport cancel， 然后以 1ms 间隔等待原 DRAIN owner 发布 all_transactions_runnable。attempt 不保存恢复结果矩阵、THD 列表、 cleanup descriptor 或 participant 生命周期。

all_transactions_runnable 不是单纯的 restored counter：它同时要求全部 in-flight worker 已确认离开“可能 prepare、detach、 publish 或 COMMIT”的语义区间。worker 线程本身可以尚未 join，但 RESET OK 之后只能做栈展开、断链和资源释放，不能再产生新的 preserved state。

6.3 唯一线性化点

RESET 赢

CAS(RUNNING → RESET_REQUESTED) 成功。之后任何 COMMIT outcome 都不能触发 source shutdown；即使 target 已接受，candidate 也只由 target TTL 处理。

FINAL_ACK 赢

ACK 完成完整性/HMAC 校验后，commit_epoch() 在设置 m_epoch_committed、清 final metadata 和释放 transport 之前调用本地 arbiter；只有 CAS(RUNNING → SHUTDOWN_HANDOFF) 成功才使 FINAL_ACK 在 source 生效。

不要把“COMMIT 已发送”当作 TOO_LATE 用户要求的 ownership 边界是 source 本地收到 FINAL_ACK。COMMIT 在网络中或 target 已接受但 ACK 尚未在 source 生效时，RESET 仍可赢； 该 orphan candidate 不会反向约束 source，由 target TTL 清理。HA 发起 RESET 后不得同时发起该 candidate 的 promotion，这是 HA 调用顺序合同， 不是新分布式协议。 
ACK verified
  -> verify attempt.generation + epoch_id
  -> try_final_ack_handoff()  // the only RUNNING -> SHUTDOWN_HANDOFF CAS
       WON  : mark m_epoch_committed, release transport, return committed
              DRAIN owner exact-CAS manager -> existing SHUTDOWN_REQUESTED
       LOST : return RESET_CANCELED; no retry/query/release-as-committed

arbiter 是传入 source epoch session 的窄回调或等价内部函数，不让 transfer 模块依赖完整 drain manager。 target 已 accepted 但 arbiter 输给 RESET 时，不发送反向 ABORT；source 恢复，target 按本地 TTL 处理 orphan candidate。

该分支不增加 transfer status 或 wire 结果。commit arbiter 返回 false 时复用现有 source-local UNSUPPORTED 结果；外层 DRAIN 必须先检查 attempt terminal，若已为 RESET_REQUESTED，就直接进入 source semantic restore，禁止调用 abort_batch_transfer_epoch()、重试 COMMIT 或查询 receiver。原 DRAIN statement 最终映射为 ER_PRESERVE_TRX_DRAIN_RESET。

6.4 并发 RESET 与 attempt 终止

  1. 第一个成功执行 CAS(RUNNING → RESET_REQUESTED) 的 RESET 是唯一 terminal winner，并负责递增 winner/attempt 指标。
  2. 同一 generation 的后续 RESET 看到 RESET_REQUESTED 时，不重复恢复、不返回 busy；它们成为同一 all_transactions_runnable 屏障的 waiter，屏障完成后都返回 OK。
  3. 若恢复触发实现不变量失败，attempt 保存唯一 terminal error，所有 waiter 返回同一个 fail-closed 结果，不能一部分返回 OK。
  4. 后续 RESET 看到 SHUTDOWN_HANDOFF 时统一返回 TOO_LATE；不存在一个 RESET 返回 OK、另一个返回 TOO_LATE 的同 generation 分叉。
  5. RESET_REQUESTED 是 attempt 终止态，绝不回到 RUNNING。业务恢复后可以继续存在，以承载 waiter 和只读观测。
  6. 只有 all_transactions_runnable 已发布，且原 DRAIN owner 完成自己栈内的非语义收尾后，owner 才能精确 CAS manager 从 RESET_CLEANUP 回 IDLE，并销毁 attempt。
  7. attempt 已销毁后再次执行 RESET，按“无 active drain”幂等返回 OK。

Preserve_trx_reset_requests 统计所有 SQL 调用；另设 terminal winner 计数，只由第一个 CAS winner 增加， 避免并发 RESET 重复计算一次业务恢复。

6.5 Manager guard 的必要小修

当前 Preserve_trx_manager_state_guard::transition_to() 与析构使用无条件 store。RESET 跨线程发布 RESET_CLEANUP 后，原 DRAIN owner 可能覆盖该状态。需要把 guard 改为“精确 state+owner CAS”：

  • guard 记录自己最后成功发布的 state。
  • transition_to() 返回 bool，只在 packed (m_current_state, m_current_owner) 仍归 guard 所有时 CAS 到目标值。
  • 每个现有调用点必须处理 CAS 失败，不能继续执行对应 shutdown/cleanup 分支。
  • 析构只从最后成功发布的 state+owner CAS 回原状态；若 RESET 已接管，析构保持静默，不得覆盖。
bool transition_to(State next, Owner next_owner) {
  if (!m_active) return false;
  if (!compare_exchange(m_current_state, m_current_owner,
                        next, next_owner)) {
    m_active = false;
    return false;
  }
  m_current_state = next;
  m_current_owner = next_owner;
  return true;
}

~Guard() {
  if (m_active)
    compare_exchange(m_current_state, m_current_owner, m_from, 0);
}

这是 sql/preserve_trx.cc 内部类的局部修正，不改变原生 MySQL manager 或线程调度。

6.6 不增加 RESET watchdog

RESET 赢得 terminal 后，语义恢复成为原 DRAIN owner 的非可取消区间：控制 THD 的 KILL 或客户端断开只能延后命令返回， 不能中止 reattach/activate。RESET 调用会话断开也不撤销 attempt。若整个 mysqld crash，则走既有进程重启语义； 本设计不承诺跨进程继续 RESET，也不增加 source reset timeout、restore watchdog 或第二恢复 owner。

7. Phase 1 / Phase 2 回撤流程

7.1 RESET 通用入口

  1. 校验认证用户名精确为 preserve_trx_ha_admin、有效持有 SHUTDOWN_ACL，并检查 RESET 会话无活动业务事务。
  2. 取得当前 attempt；不存在则幂等 OK。
  3. 执行 terminal CAS；若已 SHUTDOWN_HANDOFF 返回 TOO_LATE；若已是同 generation 的 RESET_REQUESTED，直接加入现有恢复屏障等待。
  4. 只有第一个 RESET winner 发布 manager RESET_CLEANUP，禁止 drain 继续收紧 admission。
  5. 设置 generation-scoped cancel flag，唤醒 command waiters，并对正在阻塞的 transfer socket 执行 shutdown-only cancel。
  6. 原 DRAIN owner 和 worker 在安全 checkpoint 停止前进；已经 detach 的目标立即进入既有逆路径。
  7. 等待 attempt 的 all_transactions_runnable；不等待 participant、sender、provenance 和临时文件清理。
  8. 立即返回 OK。之后原 DRAIN owner 继续留在原调用栈中，停止/join 自己创建的 worker，并收尾 participant、sender 和普通临时对象。

7.2 Phase 1

phase1 中事务仍在原 THD 运行，没有 detach/claim。RESET 成本应接近常数：

  • phase1 flush/enqueue 循环在每个 batch 前后检查 reset generation，停止新 target 宣告和 blob batch enqueue。
  • 清除属于该 generation 的 PENDING_QUIESCE、QUIESCED、DRAINED_NO_TRANSACTION。
  • 清除属于该 generation 的 batch state；全部事务恢复后再解除 CLOSING gate 并唤醒 command reader。
  • 调用现有 abort_participants()；传输 ABORT/断链是 best-effort，不参与 RESET 返回。

7.3 Phase1 closing

当前 WARMCOPY_CLOSING 已对普通连接的所有新 command 执行 4020 default-deny。RESET 先发布 RESET_CLEANUP 重新开放普通 admission， 再由 DRAIN owner 清除 generation 状态。participant open/close/preflight 前后、进入 WARMCOPY_CLOSING 前后都检查 reset generation；RESET 生效后，任何迟到结果都不能重新进入 BATCH_DRAINING。

phase2 按目标状态分三类处理：

首版不新增 parallel restore。先把当前每 token 一次全局 THD scan 的 O(N×THD) 改为“一次 scan 收集所有匹配 THD pin，按原 reverse order 恢复”。 只有 release NFR 证明 1000 事务仍不达标，才进入条件切片实现 bounded parallel restore。

  • target wait loop 每次唤醒后，以及 worker 取得下一个 target 之前。
  • 进入 prepare/detach 前；不可分割内核 substep 完成并释放关键锁之后。
  • 目标一旦完成 trx_preserve_prepare_current()，取消不得把它遗留在无 owner 的 PREPARED 状态：仍挂原 THD 时走 prepare-failure reactivation；已经 detach 时先 reattach，再 activate。
  • detach 已成功时不得直接 canceled return，必须先走 existing reverse path 恢复该 target。
  • 每个 target 完成后、record/binlog catch-up stream 前后、artifact publish 前。
  • final metadata 编码/发送前、COMMIT_EPOCH 前，以及任意网络 I/O 被 shutdown 唤醒后。

7.5 业务开放与 RESET 返回

  1. manager 进入 RESET_CLEANUP 后，未受本次 generation 影响的连接立即允许普通业务。
  2. 未 detach 的目标清 state 后立即唤醒。
  3. 已 detach 的目标完成原 trx_t、MDL、binlog cache、GTID、savepoint 和 session 状态恢复后，清除 PRESERVED_DRAINED。
  4. 复用现有逐事务 reattach/activate 语义；首版不修改 InnoDB activation/redo flush。若 N=1000 profile 明确证明它是剩余主瓶颈，再单独评审。
  5. 确认每个目标的 batch state 均为 NONE 后，统一解除 CLOSING gate，再唤醒 command reader。
  6. 确认每个 in-flight worker 已越过最后一个语义 checkpoint，之后不可能再 prepare/detach/publish/COMMIT。
  7. 当全部受影响目标均可执行下一条 SQL时，attempt 发布 all_transactions_runnable=true。
  8. RESET DRAIN 立即返回 OK；从这一刻起，后台清理不得再写 batch state、CLOSING gate 或事务生命周期。
  9. 原 DRAIN owner 继续完成栈内非语义清理；清理完成后 manager 回 IDLE，原 DRAIN 语句返回 canceled。
返回顺序不可颠倒 允许先返回 RESET OK、后完成原 DRAIN 栈展开；不允许先把连接留在 PRESERVED_DRAINED，再交给后台慢慢 restore。 后台只能删除或释放已经逻辑失效的非语义对象。

8. 内核对象恢复：复用原对象，不做反序列化

RESET 与 startup/promotion resume 不同：source 进程没重启，原 trx_t 和相关对象仍在内存。因此最快、最可靠的做法是逆转 detach， 不是从 snapshot 重建事务。

8.1 对现有 restore helper 的精确拆分

restore_batch_record_to_original_thd() 当前把语义恢复和文件清理混在一起。拆分点应位于 trx_preserve_activate_reattached_in_original_thd() 成功之后、delete_snapshot_files_with_status() 之前： 

restore_batch_record_semantics_to_original_thd(...)
  -> BUSINESS_RESTORED | INVARIANT_BROKEN

cleanup_reset_batch_artifacts(...)
  -> owner-local cleanup only; never keeps a restored THD in PRESERVED_DRAINED

这不是新增一套 resume core，只是把现有 batch failure reverse path 的同步尾部切开，使 RESET 能在正确的业务恢复点返回。 INVARIANT_BROKEN 不属于可接受的 RESET 成功降级结果；支持场景必须在进入 resettable window 前保留完整逆操作资源， 并用故障注入证明该状态不会被静默转换成 OK。若该实现不变量仍被破坏，复用现有 ER_PRESERVE_TRX_BATCH_CLEANUP_FAILED 和 manager DRAIN_CLEANUP_FAILED fail closed； 不再新增第三个同义错误码，也不得把后续普通文件清理失败与该语义失败混为一类。

8.2 可回撤资格与资源预留

不再增加一个与 artifact_mode 重复的 attempt.resettable 布尔值。首版可回撤资格唯一由 STANDBY_TRANSFER_SAVE、attempt terminal 仍为 RUNNING，以及原 backend THD 仍被支持合同保持存活共同决定。 每个成功 detach 的 Preserve_trx_source_rollback_image 增加 original_binlog_cache_retained，明确原 cache 是否仍可 metadata-only reactivation。

  • 进入 PRESERVED_DRAINED 前构建 rollback image，并预留 restore vector/pin map 所需的 O(N) 容量。
  • RESET 赢时只恢复 retained 原 cache；不读取 prebuilt external blob，也不分配与 binlog payload 大小成比例的内存。
  • FINAL_ACK 赢或正常 shutdown handoff 时丢弃 retained 原 cache；非 transfer、本地 carrier 和普通单事务 preserve 路径保持原逻辑。
  • 支持范围内的 OOM/缺失 rollback image 属进入可回撤窗口前的拒绝条件，不允许在 RESET 已赢后降级成“部分恢复”。

9. Source Artifact 失效与异步清理

9.1 首版只支持 Transfer 模式

STANDBY_TRANSFER_SAVE 使用 transfer artifact sink，不在 source 发布可供 startup resume 的本地 .bin。 RESET 返回前只恢复原事务、清除本次 generation 的 source token 可用性并解除 CLOSING/batch gate；XID provenance reservation、 warm blobs 和 sender 临时状态在 cleanup 阶段删除。source 不等待 target 删除任何内容。

9.2 Local carrier 明确不在首版

避免把两套场景混在一起 local preserve→shutdown→startup resume 要求 durable snapshot、目录 barrier 和跨重启恢复；transfer RESET 是同一 source 进程内的在线逆转。 首版 RESET DRAIN 只接受 STANDBY_TRANSFER_SAVE attempt，不修改 carrier、startup preflight、 Resurrection Index 或 recover_all。local-carrier attempt 不进入本设计的可撤销窗口。

9.4 Source 收尾的最小所有权

当前代码只有 receiver cleanup debt，不能笼统写成“既有 reaper 会清 source”。首版不增加 source cleanup queue： 原 DRAIN owner 保持原栈和对象所有权，在 RESET 已返回后继续完成非语义收尾。

  1. RESET OK 后，原 DRAIN owner 停止并 join 自己创建的 worker；worker 不得继续引用局部 vector、session、sink 或 provider。
  2. owner 对 participant 做逻辑 disable/abort，并按现有接口释放 sender、provider、provenance 和临时文件。
  3. 收尾期间 manager 保持 RESET_CLEANUP：普通 SQL 完全开放，但拒绝新的 DRAIN，避免旧 generation 与新一轮 token 冲突。
  4. 临时清理失败时由 owner 在原栈内每 1 秒有界重试；不移交 THD/trx/participant/session/sink 指针，不增加进程级任务队列。
  5. 收尾全部完成后，owner 用精确 state+owner CAS 将 manager 置回 IDLE、释放 attempt，并让原 DRAIN 语句返回 canceled。

9.5 清理失败

非语义清理失败不能重新关闭全局业务，也不能把已经恢复的 THD 改回 PRESERVED_DRAINED。manager 可暂时留在 RESET_CLEANUP 拒绝新的 DRAIN，由原 DRAIN owner 重试 sender 临时资源、provenance 和文件删除； 原连接继续正常运行。错误通过 error log 暴露，不引入 watchdog。事务 reattach/activate、batch state 清除或 CLOSING gate 解除失败不属于 cleanup debt，RESET 不得在这种状态下返回 OK。

  • 每轮只执行一个有界 cleanup pass，单项失败不阻塞同批其他普通清理。
  • 重试不增加 sysvar，不创建新线程，也不转交给 receiver reaper。
  • 达到固定告警阈值后只做限频 error log；告警不改变普通 SQL 已开放、下一轮 DRAIN 仍被拒绝的语义。
  • 只有 owner 收尾完成才能离开 RESET_CLEANUP；不能为了允许下一轮 DRAIN 丢弃旧 generation 的删除任务。

10. FINAL_ACK、网络取消与幂等竞态

10.1 RESET 不等待网络

当前 classic client sink 用 1 秒粒度的 connect/read/write timeout，phase2 通常设置为 3 秒。仅设置 cancel flag 不能满足快速 RESET， 因为 DRAIN owner 可能阻塞在 simple_command()。需要给 transfer sink 增加一个窄接口： 

virtual void request_cancel() noexcept;

struct Transfer_cancel_slot {
  mutex cancel_mutex;
  bool cancel_requested;
  void *active_connection;  // valid only while protected by cancel_mutex
};

// default classic client op, called while cancel_mutex is held:
mysql_socket_shutdown(mysql->net.vio->mysql_socket, SHUT_RDWR);
// shutdown only: no mysql_close(), no vio_shutdown(), no SSL_shutdown()

每个 data session 使用由 sink 拥有的稳定 cancellation slot。发送线程在进入 simple_command() 前于 cancel_mutex 下发布 active connection，返回后先在同一 mutex 下清除，再允许 disconnect/mysql_close()。 RESET 持有该 mutex 完成 socket shutdown，因而不会发生 fd 复用或 connection/VIO 生命周期竞争。shutdown 只唤醒 TCP、Unix socket 或 TLS 下正在等待的 I/O；SSL 对象的关闭和 mysql_close() 仍只由发送线程执行。

发送线程从网络返回后第一件事是重查 cancel_requested 和 attempt terminal。若 RESET 已赢，直接返回 RESET_CANCELED，不得执行 reconnect、exact-frame retry、QUERY_EPOCH_STATUS 或 committed teardown。 该改动只扩展 Preserve transfer client ops 的可选 cancel 回调，不修改通用 libmysql、connection scheduler 或 server protocol。

10.3 与 CLOSING 命令门禁的关系

本设计不再要求 transfer drain 在 COMMIT_EPOCH 前构造逐 THD accepted/response sequence 或 command-read cutoff。 RESET 只逆转当前已经存在的 CLOSING/batch state，并保持“先恢复原事务，再开放普通 command”的顺序：

  1. RESET 赢得 terminal CAS 后，禁止新的 phase2/final metadata/COMMIT_EPOCH 推进。
  2. 未 detach 目标在确认原事务仍可运行后清除本 generation 的 batch state。
  3. 已 detach 目标必须先完成原事务 reattach/activate，再清为 NONE。
  4. 全部目标恢复后解除 CLOSING gate 并唤醒 command reader；socket 中尚未读取的 SQL 在原 Tx 上自然执行。
  5. 只有所有目标均满足“事务可运行 + batch state 为 NONE + CLOSING 已解除”，RESET 才返回 OK。
4020 不得在 RESET OK 后重复出现 代理收到 HA 的 RESET 成功终局后，只会在原 Tx 上重放明确收到完整 4020 的请求。因此本次 generation 的任何原连接只要仍为 PRESERVED_DRAINED 或 CLOSING/batch gate 仍生效，RESET 就尚未完成；尚未被 mysqld 读取的 packet 则不得由代理再发一份。
RESET 的少量协议边缘不外推到终态路径 若同一 socket 上存在部分 long-data compound 或响应结果不明，按 RESET 专属的 PS/reset 合同处理； 不为此在 promotion/shutdown 热路径增加通用 ps_compound_pending 或 response-fence 状态机。

10.4 ACK 身份与重放

现有 ACK 对 source incarnation、epoch id、sequence、原 encoded frame digest 和 HMAC 的校验继续作为 wire 身份合同； exact-frame retry 保持幂等。新增的只是 source 本地断言：ACK 对应的 epoch id 与当前 attempt generation 创建的 epoch 一致， 且 terminal 仍由该 attempt 持有。该防御不新增字段、不升级 v4，也不把 target 状态查询扩展成长期协议。

11. Receiver 两段 TTL 状态机

Receiver 已经有两套职责不同的 token 状态，不能再用一条 RECEIVING → READY → ADOPTING → ADOPTED 把它们压扁。首版只扩展现有 Preserve_trx_transfer_accepted_epoch，增加轻量 epoch TTL lease；不新建第三个 token registry。

Transfer record / token: DECLARED → RECEIVING → SAVED_ONLINE；失败进入 CLEANUP_PENDING / CLEANUP_TAINTED / CORRUPT / ABORTED
Strict token: OBJECTS_RECEIVING → PREWARMING → PREWARMED_PENDING_FINAL_FACT → READY_FACTS_PENDING_LEASE → READY_FOR_GATE → ADOPTING → ADOPTED_LOCKED → ATTACHING → ACTIVATING → ACTIVE
Epoch TTL lease: ACCEPTED_DEADLINE_ACTIVE → READY_DEADLINE_ACTIVE → ADOPT_LEASED

11.2 ACK→READY：默认 10 秒

  • receiver 完整接受 epoch、确认全部 transfer token 为 SAVED_ONLINE 后，在 accepted registry 中安装 ACCEPTED_DEADLINE_ACTIVE 和 10 秒 deadline，再返回 FINAL_ACK。
  • 若 COMMIT 时所有 strict token 已完成 prewarm，可在 FINAL_ACK 前直接完成 epoch binder 并进入 READY_DEADLINE_ACTIVE，此时 ACK→READY 指标为接近 0。
  • prewarm worker 在重工作前和发布 READY 前各检查一次 accepted epoch 仍 live；10 秒内允许受资源治理的 prewarm。
  • 超时不是传输错误，而是 target-local candidate 失效。
  • 过期不向 source 上报，不等待 HA，不回滚 source。

11.3 READY→HA adopt lease：默认 30 秒

  • 最后一个 token prewarm 完成且 epoch fact 可绑定时，epoch binder 先 snapshot ready_deadline_us = now + preserve_trx_transfer_receiver_ready_timeout_ms。
  • binder 使用同一个 ready_deadline_us 构造全部 token final facts，令 epoch_prepare_deadline_us == ready_deadline_us，再把 token 推到 READY_FOR_GATE。
  • 全部 token 和 epoch fact 成功后，CAS 到 READY_DEADLINE_ACTIVE。不得先发布 epoch READY、再异步修补 token deadline。
  • 未来 HA promotion 入口先执行 epoch CAS： READY_DEADLINE_ACTIVE → ADOPT_LEASED；成功后才调用现有 strict begin_gate_adopt() 让 token 进入 ADOPTING。
  • ADOPT_LEASED 一旦成功，两个 TTL 都永久取消；promotion 后续成功、逆转或 taint 由 strict 状态机处理。
  • 30 秒内 HA 未取得 lease，epoch CAS 到 EXPIRED 并销毁尚未 claim 的 candidate。

11.4 与现有 deadline 字段的关系

  • epoch_prepare_deadline_us 是 strict token 允许开始 gate adopt 的期限；transfer receiver 路径必须使用上述 epoch ready_deadline_us，不能继续从 preserve_trx_transfer_commit_timeout_ms 推导。
  • preserve_trx_transfer_commit_timeout_ms 只表示 source 等 FINAL_ACK 的网络/协议预算，不承担 target READY lease。
  • client_resume_deadline_us 是 token 已进入 ADOPTED_LOCKED 后等待 attach/resume 的既有期限， 不属于 10s/30s 两段 TTL，也不由这两个新 sysvar 修改。
  • epoch lease 与每个 token 的 epoch_prepare_deadline_us 必须使用同一个 monotonic clock 和同一 deadline snapshot； 任一 token 不一致时不得发布 epoch READY。

11.5 进程边界

deadline 和 epoch READY lease 都是当前进程内状态，不写 durable manifest。receiver restart 时现有 preserve_trx_transfer_cleanup_receiver_restart_state() 删除残留，所有 epoch 失效。不会从时间戳或文件恢复 TTL。

reaper 周期为 1 秒，因此默认 10s/30s 的实际物理清理触发时间为 deadline 后 0–1 秒。

HA 不主动调用销毁。两个 TTL 只复用同一个 target-local 内部接口：

12.1 两阶段销毁

  1. 逻辑失效：在 accepted-registry mutex 下只允许状态从 ACCEPTED_DEADLINE_ACTIVE/READY_DEADLINE_ACTIVE → EXPIRED。
  2. lease 防护：若状态已为 ADOPT_LEASED，destroy 返回 LEASED_NOT_DESTROYED；不得删除 strict token、ready cache 或 promotion 资源。
  3. 立即阻断：新的 prewarm publish、READY publish 和 promotion lease 均返回 stale/skip。
  4. 取消排队：在现有 prewarm mutex 下扫描 staged/object 两个 deque，删除匹配 root+epoch 的 jobs，并同步扣回 queued bytes、inflight/deferred set。
  5. 释放内存：删除 object proofs、record lock prepared plan、strict lock/binlog facts、seal state、ready cache、prepared registry。
  6. 删除临时文件：删除 staging、process-local carrier snapshot、external blobs、standby markers、epoch fact/commit marker；不 fsync。
  7. 保留轻量 ACK history：在原 ACK grace 到期前，QUERY_EPOCH_STATUS 仍可回答“当前进程曾接受”，但不得重新构造 READY。

12.2 活跃 worker 不等待

destroy 不 join prewarm worker。job 在开始昂贵工作前校验 accepted epoch 仍 live，发布 proof/cache entry 前再校验一次； worker 发布后若发现 epoch 已 EXPIRED，只删除自己刚发布的匹配 root+epoch entry。这样 destroy 与 publish 无需持两把 cache mutex 做长临界区，也不会让迟到结果重新变成 READY。 

worker(root, epoch):
  if (!epoch_is_live(root, epoch)) return STALE;
  compute_without_epoch_lock();
  if (!epoch_is_live(root, epoch)) return STALE;
  publish_entry(root, epoch);
  if (!epoch_is_live(root, epoch))
    erase_entry(root, epoch);

destroy(root, epoch):
  CAS ACCEPTED_DEADLINE_ACTIVE / READY_DEADLINE_ACTIVE -> EXPIRED;
  if ADOPT_LEASED: return LEASED_NOT_DESTROYED;
  cancel_queued_jobs(root, epoch);
  purge_entries(root, epoch);

13. Promotion：Preserve 是可选加速项

当前仓库没有真实物理复制升主流程。本轮只预埋 target 内部接口的前置 lease/skip 语义，不把 classic PROMOTION_GATE_EPOCH 变成 production HA 入口。 

HA promotion trigger
  -> try_acquire_preserve_epoch(epoch)
       READY_DEADLINE_ACTIVE : CAS -> ADOPT_LEASED, execute preserve adopt
       NOT_FOUND             : SKIPPED, ordinary promotion continues
       ACCEPTED/PREWARMING   : SKIPPED, ordinary promotion continues
       EXPIRED               : SKIPPED, ordinary promotion continues
  -> ordinary role/write-enable flow (future HA code)
“不阻塞普通升主”的准确边界 candidate 缺失、未 READY、已过期必须在任何 trx claim/MDL attach 之前返回 SKIPPED。一旦 epoch READY_DEADLINE_ACTIVE→ADOPT_LEASED 且 strict token 开始 READY_FOR_GATE→ADOPTING 的不可逆 claim， 仍必须使用现有 fail-closed reversal/cleanup 保证内核一致，不能把部分 adopt 当成可直接忽略的 SKIPPED。

epoch lease 成功后不再回到 READY，也不再受 TTL reaper 销毁。promotion 在第一个 token claim 前失败时，只允许当前 lease owner 执行窄的 ADOPT_LEASED → EXPIRED 放弃操作并调用统一 destroy；确认零 claim/零 MDL 后普通 promotion 才可继续。 TTL 线程和普通 destroy 调用都不能抢占已发放的 lease。

ABANDONED_ROLLED_BACK 只有在已 claim 的内核对象被完整逆转并证明 kernel clean 后，才能作为 PRESERVE_ABANDONED 让普通 promotion 继续；CLEANUP_TAINTED 必须 fail closed。二者不能都映射成前置 SKIPPED。

13.1 HA 调用顺序合同

  1. HA 只有在观察到 source DRAIN 成功，即 source 已处理 FINAL_ACK 并进入 SHUTDOWN_HANDOFF 后，才允许调用 target promotion。
  2. 若 source RESET 赢，原 DRAIN 返回 ER_PRESERVE_TRX_DRAIN_RESET；HA 不得再对该 orphan epoch 调用 promotion，target 只等待 TTL 销毁。
  3. 该互斥由 HA attempt/fencing 保证，不增加 source→target cancel RPC，也不让 target 在 adopt 期间反查 source。
  4. 若 HA 违反上述顺序同时发起 RESET 与 promotion，属于 HA authority 错误；Preserve 内核不以跨节点回滚协议掩盖该错误。

估算不包含真实物理复制/HA promotion 集成。最大不确定性是 source transport 的跨线程 socket cancel 在 Unix/TLS 下的验证、 CLOSING gate 与 THD 状态恢复顺序、source owner-local cleanup，以及 1000 THD reattach 的 release NFR；不是事务 payload 大小。

18.1 Review blocker

  • 任何设计把 RESET 返回绑定到 receiver ACK/prewarm/cleanup。
  • 任何设计在 RESET OK 后继续恢复某个原事务、batch state 或 CLOSING gate。
  • 任何设计让 source 在 FINAL_ACK 后继续轮询 target READY。
  • 任何设计为 receiver TTL 写 durable marker 或 startup replay。
  • 任何设计在 RESET 正常路径读取 snapshot/binlog/record-lock payload。
  • 任何设计从 RESET 线程调用 SSL_shutdown() 或 mysql_close()；RESET 只允许调用 shutdown-only vio_shutdown() 唤醒阻塞 I/O，disconnect 仍由 sender owner 完成。
  • 任何设计引入 source cleanup queue/debt 或把 THD/trx/participant/session/sink 指针移出 DRAIN 栈。
  • 任何设计增加 source reset timeout、restore watchdog 或跨 mysqld crash replay。
  • 任何设计修改 InnoDB Undo scan、lock move 或 crash recovery 热路径。
  • 任何设计在 pre-claim candidate 不可用时阻塞普通 promotion。
  • 任何设计在 transfer receiver record 中复制 READY_FOR_GATE/ADOPTING/ACTIVE，或另建一套 strict token registry。
  • 任何设计继续用 preserve_trx_transfer_commit_timeout_ms 生成 transfer strict token 的 epoch_prepare_deadline_us。
  • 任何设计允许普通 TTL destroy 删除 ADOPT_LEASED epoch。
  • 任何设计仅凭 READY 类 state 把不同 object-set digest 的二次输入判为幂等成功。
  • 任何设计首版直接引入跨 THD parallel restore，而没有串行索引化 NFR 证据。

19.2 GUnit

  • attempt CAS：RESET vs FINAL_ACK 两边各赢；无双 winner。
  • ACK 验证后、m_epoch_committed/transport release 前完成 arbiter；RESET 输赢两条路径均无窗口。
  • manager guard 精确 CAS：RESET_CLEANUP 不被原 guard transition/析构覆盖。
  • 无 drain 幂等、重复 RESET、TOO_LATE。
  • admission_reopened、all_transactions_runnable 与 owner_cleanup_done 三个里程碑分离；RESET 只等待第二个。
  • source cancel：final payload/COMMIT 阻塞时 shutdown-only wake；cancel mutex 覆盖 active connection 生命周期，取消后不 reconnect/query。
  • 一次 THD scan、reverse restore 顺序、pin 生命周期。
  • binlog retained cache reactivation，payload read bytes=0。
  • source 非语义收尾只由原 DRAIN owner 执行；重复 cleanup pass 幂等，完成后精确 CAS 回 IDLE。
  • 全部恢复目标 batch state=NONE 且 CLOSING gate 已解除；不得出现 RESET OK 后再次返回 4020。
  • receiver 三层状态映射，以及 epoch ACCEPTED_DEADLINE_ACTIVE/READY_DEADLINE_ACTIVE/ADOPT_LEASED/EXPIRED 转移；pre/post live check 防迟到 publish。
  • epoch binder 为全部 strict token 使用同一个 ready deadline；不再从 commit timeout 生成 epoch_prepare_deadline_us，不一致时 epoch READY 发布失败。
  • strict READY 类重入必须比较 object-set digest/version：相同为 IDEMPOTENT，不同为 DIGEST_CONFLICT/CORRUPT。
  • destroy 幂等、ACK history 保留、ready cache/prepared registry per-epoch purge。
  • 过期 ACK、destroy 与 publish 交错、queued bytes/inflight set 精确回收。

19.3 MTR

  • grammar、SHUTDOWN privilege、显式事务拒绝、无 active drain OK。
  • phase1、closing、phase2 before/after one target preserve 的 RESET。
  • active warmcopy participant、DRAIN owner KILL、RESET caller 断开/重试和恢复期间 SHUTDOWN busy。
  • RESET_CLEANUP 期间普通 SQL 可运行，新 DRAIN/Preserve control 被拒绝。
  • 原 DRAIN 返回 canceled 专用错误；RESET 返回 OK。
  • RESET OK 后在原 Tx 重放触发 4020 的 SQL，正常执行且不再返回 4020。
  • CLOSING 时尚未读取的 packet 在 RESET OK 后由原 socket 自然执行；Proxy 不重发，最终执行次数为 1。
  • local-carrier drain attempt 不进入首版 RESET 支持范围。
  • preserve_trx_enable=OFF 原生路径不受影响。

19.4 Standalone 双 mysqld E2E

  • source phase1/phase2 各 DEBUG_SYNC 点执行 RESET，原事务继续 UPDATE/COMMIT。
  • Unix socket 与 TLS/TCP 两种 transport 在 final payload/COMMIT wait 中被 shutdown-only cancel 快速唤醒。
  • COMMIT 已发送但 ACK 尚未处理时 RESET 赢：source 业务恢复，target candidate 到 TTL 后消失。
  • FINAL_ACK CAS 赢：RESET TOO_LATE，source 继续 shutdown。
  • 缩短 TTL 验证 ACK→READY timeout、READY→ADOPT_LEASED timeout 和 restart invalidation。
  • expired/missing candidate 的 test promotion wrapper 返回 SKIPPED，不执行 claim。
证据命名 该 E2E 只能命名为 STANDALONE_TRANSFER_RESET_E2E。没有物理复制 provider、role switch 和 write-enable， 不得命名为 physical promotion E2E。

20. 推荐落地顺序

以下是风险隔离顺序，不是要求一次性铺开修改。

  1. S0：strict digest 幂等前置修复。修复 READY 类快速返回：相同 object-set digest 才返回幂等， 不同 digest 标记 CORRUPT 并返回 DIGEST_CONFLICT；在 TTL/destroy 接入前先锁住 registry 身份。
  2. S1：SQL + commit 内 attempt CAS + manager guard。先证明 RESET/FINAL_ACK 只有一个 winner，且 guard 不覆盖 RESET。
  3. S2：source phase checkpoints + socket cancel + waiter wake。覆盖 phase1/closing 和网络阻塞，不碰 detach restore。
  4. S3：restore split + retained binlog cache + 一次 THD scan。完成 phase2 原事务快速恢复、batch state 清除和 CLOSING reopen。
  5. S4：owner-local cleanup。证明 RESET response、原 DRAIN RPC 返回与物理清理三者解耦，不增加 source queue/reaper。
  6. S5：receiver 三层状态映射 + TTL + destroy。扩展现有 accepted-epoch registry 并复用 receiver reaper， READY 时统一绑定 token deadline，先逻辑失效后取消队列/异步释放。
  7. S6：promotion lease/SKIPPED/ABANDONED。只做 pre-claim optionality和既有 post-claim fail-closed 对齐，不扩真实 HA。
  8. S7：MTR/E2E/NFR。根据 1000 事务数据决定是否启用条件 parallel restore。

每个切片都应保持 preserve_trx_enable=OFF、普通 XA、本地 startup resume 和现有 transfer E2E 不变；不应在 S1 就改动 InnoDB、startup recovery 或 wire codec。
