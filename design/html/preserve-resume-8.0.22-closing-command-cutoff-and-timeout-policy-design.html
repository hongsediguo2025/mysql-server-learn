进入 CLOSING 之前

正常业务继续执行，Phase1 继续构建和发送可提前完成的 Preserve 内容。

在 Phase1 尾部只读统计正在执行的 command 数量与最老执行时长。若已有明显长命令，则在 Phase1 剩余预算内等待其自然完成。

进入 CLOSING 之后

普通业务连接的所有新 command 都不能进入执行主体。source 仍在线并完成该 command 的本地响应时返回 ER_PRESERVE_TRX_SESSION_DRAINED（4020）；若计划内 shutdown/promotion 先关闭连接，则由代理在确认 HA 终态且事务 RESUME 成功后重发。

切换前已经执行中的 command 继续完成；每个 command 到达边界后立即独立 Preserve并发送 provisional prewarm objects。首版 early pipeline 固定 A=ON；参数 B 到期仍有 command 未完成时整批回撤。A=OFF 继续使用现有 legacy transfer 路径。

不要扩大“部分成功”语义 参数 A 只处理“CLOSING 时旧 command 未按期结束”这一种情况。snapshot、seal、传输、digest、receiver commit、 final metadata 或任一 survivor 的 Preserve 失败，仍按现有 all-or-nothing 语义终止整批。
提前发送不等于提前交权 receiver 在 COMMIT_EPOCH 前只能保存和预热 EARLY_STAGED token；不得发布 accepted epoch， 不得进入 promotion/adopt。source 在收到 FINAL_ACK 前仍拥有全部 survivor，并负责 RESET、失败回撤和整 epoch ABORT。
provisional object 不等于最终 snapshot record-lock plan 在其他旧 command，或其他已提交事务的后台 purge 仍可能修改 B-tree 页布局的窗口内，只能作为 provisional generation。 early 阶段可以提前发送和预热 record-lock、binlog cache 等大对象，但不能把包含其 digest/size 的 snapshot、 Resurrection Index 和 final manifest 提前定稿。最终 descriptor 必须在 final validation window 中复验后再写入 snapshot。
这里不需要保护 survivor 自身的 Undo Preserve 的对象是未提交、已到 command 边界并可继续执行的事务；它经 PRESERVE_FREEZE 进入 TRX_STATE_PREPARED，其 Undo 仍为 ACTIVE/PREPARED 所有权，不会被 purge 当作 history 清理。 本文讨论的 terminal page-layout fence 只处理“其他已提交事务的 purge 可能删除 delete-marked 记录并搬移 survivor 的 record/gap/next-key lock 坐标”这一问题。transfer ABORT 表示放弃传输并恢复 source 事务，不表示该事务已经回滚； 真正完成 rollback 的事务不再是 Resume 候选。
early pipeline 首版不承接 A=OFF 当前 legacy standby-transfer 路径已经支持 timeout exclusion，继续保留参数和回归。新的逐 token early pipeline 只在 A=ON 下启用， 不为 simulator 再实现一套 early exclusion、逐 token ABORT 和 survivor-only finalization。未来若物理备机项目确实需要 A=OFF，再以独立切片评审。

2. 背景与场景

本文实现主体服务于在线 transfer 和未来物理备机计划内升主；同时用本地 shutdown/startup 说明相同的“终态断连后续作”边界。 RESET DRAIN 是唯一保留原 source 连接并重新开放执行的分支，必须单独理解，不能拿它反向复杂化两个终态场景。

2.1 先区分三种运行场景

场景连接终态尚未进入执行主体的 command恢复与重发顺序
物理备机计划内升主（本文主场景） source 在 FINAL_ACK/handoff 后退出主身份并关闭普通连接；target 后续由 HA 在线升主。 若 source 已读到完整 packet，则 CLOSING gate 返回 4020；若连接先进入计划内关闭，则该请求只得到断连。两种情况都不得在 source 执行。 HA 先在 target 完成 token adopt、Tx→Ty attach 和 RESUME；代理确认对应 attempt/generation 后，才在 Ty 上重发一次。
本地 preserve → shutdown → startup 原 mysqld shutdown，全部业务连接断开；startup recovery 后重新提供连接。 处理原则与上行相同：完整 4020 是显式未执行证据，未读/未 dispatch 请求随计划内断连结束，不要求旧进程逐连接补发 4020。 代理重连；先执行 RESUME 恢复事务，再重发尚未执行的 command。本文不修改本地 durable carrier/recovery 实现。
RESET DRAIN source 不 shutdown，原 Tx/连接恢复并继续作为主库服务。 已完整收到 4020 的请求由代理挂起；尚未被 mysqld 读取的请求仍留在原 socket，gate 解除后由原连接自然读取，代理不得重复发送。 RESET 先恢复原事务并解除 CLOSING gate，再返回 OK。只有明确收到 4020 的请求才由代理在原 Tx 重发；无响应 PS compound 的边界由 RESET 对接文档单独约束。
简化成立的两个内核事实 第一，CLOSING 前已经进入执行主体的旧 command 必须先完成并到达原有 command boundary，随后其事务才可 Preserve； 第二，CLOSING 后的新 command 由 default-deny gate 保证零业务副作用。前者防止把已执行但响应未收敛的请求误判为可重发， 后者使计划内终态断连后的请求能够在 RESUME 成功后重发。普通网络故障、非计划内断连或不满足半双工约束时仍是结果不确定，不能套用该合同。

2.3 为什么仍然需要 4020，但不要求每条 late command 都收到 4020

HA 可以通知代理停止新建连接，但已有代理连接在没有收到特殊错误前仍会继续下发 command。 因此 source 仍应在存活期间对已读到的新业务 command 尽快返回 4020，使代理立即挂起并停止继续下发。 但在计划内 promotion 或 shutdown/startup 的终态路径中，连接本来就会关闭；不能为了保证每个 late command 都收到完整 4020， 再增加逐 THD accepted/response sequence、read cutoff 或 compound-obligation 状态机。

真正需要闭合的是旧 command，不是所有 late response CLOSING 前已进入执行主体的 command 要么完成并到达现有 PENDING_QUIESCE → QUIESCED/DRAINED_NO_TRANSACTION 边界，要么在参数 B 到期时使 A=ON 整批回撤。CLOSING 后的 command 只需证明没有进入执行主体：收到完整 4020 时显式挂起； 在 promotion/shutdown 的计划内终态关闭连接时，由 HA 终态和成功 RESUME 共同授权重发。任意非计划内 transport failure 仍按歧义处理。

2.4 HA 专用管控连接

协议层在解析 SQL 之前已经能够读取认证后的 Security_context。首版直接以 Security_context::priv_user() 精确等于 preserve_trx_ha_admin 识别专用 HA 账号， 并要求该账号持有原有的 SHUTDOWN_ACL。gate 只读取认证账号与有效权限，不解析 SQL 文本、 不按业务命令类型做白名单，也不新增 role、动态权限或 wire capability。

  • HA 身份必须同时满足：认证上下文中的 priv_user() 精确等于 preserve_trx_ha_admin，且有效全局权限包含 SHUTDOWN_ACL。
  • root、SUPER、SYSTEM_USER、SHUTDOWN 或其他动态权限都不会单独获得 HA 身份；MySQL 初始化 root 自动拥有大量权限，因此不能把任一普通 privilege 等同于该专用账号属性。
  • protocol gate 与 SQL gate 仅按上述身份放行，不读取 SQL 文本，也不根据连接当前要执行的是 RESET、SHOW 或 DML 做分类。
  • RESET DRAIN 真正执行时再次要求固定 HA 账号，并沿用 check_global_access(..., SHUTDOWN_ACL) 做最终授权。
  • HA 管控连接必须保持 autocommit 且无活动业务事务。readiness 忽略该控制连接；target 枚举若发现它持有显式事务或 RW participant，则整批 fail closed，不把该事务静默排除。
当前内核校验与部署合同要分开 RESET DRAIN 和 CLOSING 两层 gate 已同时校验固定用户名与 SHUTDOWN_ACL； Preserve_trx_drain_service::execute() 当前只调用 check_global_access(..., SHUTDOWN_ACL)， 尚未拒绝其他持有 SHUTDOWN 权限的账号发起 DRAIN。首版不为 early pipeline 增加账号目录查询或自动建号逻辑：部署必须预先创建并验证 preserve_trx_ha_admin，HA 始终使用该账号。账号存在性与权限应由 HA/部署健康检查在发起 DRAIN 前验证； 不在 DRAIN 热路径查询账号目录，也不由 Preserve 自动创建账号。若未来要把固定用户名升级为 DRAIN 的内核硬门槛，需单独评审兼容性。
信任边界 该连接在 CLOSING 中执行 DML 会绕过 4020，破坏业务封口假设。因此它必须是 HA 专用控制面连接； 内核不为“高权限账号同时承载业务 SQL”提供 Preserve 正确性保证。

首版只在 protocol gate 的唯一计数点累计 Preserve_trx_closing_control_connection_commands，用于发现 CLOSING 期间控制连接的实际使用；SQL gate 不重复计数。本文不新增逐 DML warning 或另一套 SQL 风险分类，具体语句继续由现有 audit/general log 记录。该指标只帮助发现账号误配，不能把“控制账号承载业务 SQL”变成受支持用法。

2.5 为什么既要提前 Preserve，又不能提前定稿

真实业务中的旧 command 完成时间并不整齐：有的几十毫秒结束，有的接近参数 B，少数会超时。 若 source 等全部 command 完成后才统一 Preserve，第一个已静止事务的序列化、外部 blob 传输和 receiver prewarm 都被最慢 command 无意义地阻塞，CLOSING 尾部会重新变成串行长尾。因此，命令一到边界就开始 Preserve并在线预热是本设计要保留的核心优化。

但 early token 的显式 record locks 仍可能被其他尚未结束的 command 或后台 purge 引起的页重组、split/merge、inherit/move 搬移坐标。传输 digest 只能证明“收到的 payload 与发出的 payload 相同”，不能证明它在统一 COMMIT 时仍对应 live lock state。 另一方面，snapshot 会编码 external record-lock blob 的 size/digest，receiver 也会要求 snapshot descriptor 与最终 manifest 精确一致。 所以不能先发送最终 snapshot、再只替换 record-lock blob；正确顺序必须是“大对象可 provisional 预热，最终 metadata 延迟定稿”。

2.6 本次设计需求与目的

需求目的成功标准
任一旧 command 完成即开始 Preserve把 source 构建、网络传输和 receiver prewarm 与其他慢 command 重叠。首个 token 的 staged prewarm 早于最后一个旧 command 完成。
默认 A=ON 保持整批原子性成功路径不存在 excluded command 继续修改 survivor lock plan；超时路径统一回撤。任一 command 超时即无 accepted epoch，source early token 全部可恢复。
1000 token 也能快速识别漂移避免对所有 token 重扫 lock shard、重算 payload digest。检测复杂度为 O(N) 小型 stamp 比较，与事务锁数量无关；深验和重导出只作用于 D 个漂移 token。
漂移 token 定点修复避免常见 purge/reorg 漂移把整个健康 epoch 直接打回。只替换更高 generation 的 record-lock object；未漂移 token 的 receiver prewarm cache 保留。
最终 snapshot 与 lock plan 一致保证 receiver 看到的 descriptor、manifest 和实际 sealed object 是同一 generation。snapshot/Index/final manifest 在 terminal generation 锁定后生成，COMMIT 前二次快筛无变化。
保持非侵入性不把 HA 调度逻辑扩散到通用 InnoDB 热路径。不新增 wire/version、accepted 状态、sub-epoch 或原生 lock mutation hook site；Preserve OFF 路径不增加计数与锁。

3. 边界与非目标

本轮设计范围

  • Phase1 尾部 lightweight readiness 观察。
  • CLOSING 后普通客户端的所有新业务 command 都在执行主体前截断；source 仍在线并完成响应时返回 4020。
  • 基于认证上下文中的固定 preserve_trx_ha_admin 用户名与 SHUTDOWN_ACL 识别并豁免 HA 专用管控连接。
  • 参数 B 定义旧 command 的统一 deadline。
  • 保留已交付的参数 A/B；early pipeline 首版只在 A=ON 下启用。
  • source 进入 CLOSING 后只按 HA 管控连接身份豁免，不为其他命令类型增加放行口。
  • CLOSING 中联合观察 pending，逐 token Preserve、发送 provisional objects 和 receiver staged prewarm。
  • RESET/failure 对 EARLY_STAGED token 的整 epoch ABORT 与 source restore。
  • A=ON 成功路径在 COMMIT 前执行 per-token fast stamp 快筛、漂移 token record-lock generation replacement 和最终二次复验。
  • 最终 snapshot、Resurrection Index 与 token manifest 延迟到 terminal generation 锁定后生成。
  • 复用现有 inflight/command-boundary 状态闭合 CLOSING 前已执行 command；不新增 late-response fence。
  • 并发裁决、指标和真实测试。

明确不做

  • 不实现 peerid 的 Tx 到 Ty attach。
  • 不修改本地 shutdown/startup Preserve。
  • 不 KILL 长 SQL，不强制回滚事务。
  • 不新增 transfer wire frame 或 wire version。
  • 不改 artifact 格式或内核对象序列化。
  • 不新增常驻调度线程、预测器或 Pre-CLOSING 状态。
  • 不实现通用对象 replacement；只复用 v4 已有的更高 generation record-lock replacement。
  • 不实现 per-token sub-epoch，不把 provisional token 提前 accepted。
  • 不支持任意 Preserve 失败后的部分成功。
  • 不新增专用账号表、动态权限或控制面 wire 协议。
  • 不把 A=OFF timeout exclusion 接入新的 early coordinator；继续回归现有 legacy 路径。
  • 不实现物理备机的 apply、authority、write-enable、terminal mutation provider 或真实 promotion E2E。
  • 不支持同一 mysqld 在同一次流程中同时作为 CLOSING source 和 transfer receiver；链式复制拓扑留给物理备机项目单独定义。

7. Phase1 尾部 lightweight readiness

已交付基线 readiness 的目的只是减少 CLOSING 刚发布时的在执行命令数量，尤其是避免把已经明显变成长 SQL 的 command 带入 1 秒 closing deadline；early pipeline 直接复用，不修改该机制。

7.1 观察内容

在最后一次 Phase1 target/lock/binlog prepare 完成后、发布 CLOSING 之前，执行只读 THD 观察：

  • inflight_business_command_count：当前正在执行的业务 command 数。
  • oldest_inflight_command_age_us：最老 command 的已执行时长，单位微秒。
  • long_command_count：执行时长已经达到参数 B 的 command 数。

不读取 THD::start_utime。在现有 preserved_trx_mark_inflight_command_packet() Preserve hook 中， 为可执行长业务工作的 command 记录受同一同步纪律保护的 preserve_command_sequence 与 preserve_command_started_monotonic_us。readiness 仅用它们识别和统计当前 command；不修改通用 THD::set_time()，也不把该 identity 带入 artifact 或 wire。当前 collector 对所有已认证 HA 管控连接都不计 readiness 指标； “该连接不得持有活动事务”由后续 target/participant 枚举单独校验并整批 fail closed，不由 readiness 统计承担。

OFF-path 合同 preserve_trx_enable=OFF 时，command marker 必须在写入上述字段、读取 monotonic clock 或获取 LOCK_thd_data 之前立即返回。这里保证的是“无新增字段写入、取时钟和取锁”，不宣称消除现有 hook 调用与一次 enable 分支本身的 CPU 开销。

7.3 预算与采样纪律

  • 不新增 readiness sysvar。长命令阈值复用参数 B。
  • 等待集合只在 readiness 首次采样时冻结；元素身份使用 (thread_id, preserve_command_sequence)。同一 THD 开始下一条 command 即表示原 command 已完成，新 command 交给 CLOSING+B 处理。
  • readiness 等待上限复用现有 Phase1 总预算；当前 two-phase drain 已捕获 monotonic absolute deadline。
  • preserve_trx_transfer_phase1_timeout_ms 当前既是 phase1 classic operation timeout 的数值来源，也限制 Phase1 readiness。
  • 采样 sleep 必须发生在不持 LOCK_thd_data、manager mutex、participant lock 或 transfer session mutex 的位置。
  • 首次采样执行一次全 THD 摘要扫描；后续只按冻结的 thread id 定点查询，不得每 10ms 反复全量扫描所有 THD。
  • 定点查询不读取事务 payload、不扫描 Undo、不导出锁对象；固定 10 至 50ms 采样即可，不做自适应算法或新 worker。
为什么不能等待 inflight count 变为 0 Phase1 期间代理仍可在已有连接上持续下发 command。在高吞吐下，count 可能始终非零。 readiness 只等待首次采样时“已经明显长”的 command；随后必须依靠 CLOSING 截断新 command，关闭最后的竞态窗口。

8. CLOSING 全命令截断

8.1 “所有 command”的精确定义

本文门禁只作用于 client protocol dispatch，不扩展到 replica applier、event scheduler 或其他 internal THD。 对普通客户端连接，所有新业务 command，包括文本 SQL、prepared statement 执行、cursor fetch、schema/session 操作以及其他 classic protocol 业务命令， 均必须在产生业务副作用前被截断；source 仍在线并读到完整 response-bearing packet 时返回 4020。 不能只覆盖 COM_QUERY，也不能继续依赖 CF_CHANGES_DATA。

现有 batch target 枚举会对当时已经存在的 system-thread RW participant 或 inflight statement fail closed；但本轮不把客户端协议门禁扩展为 terminal internal-writer census。扫描后新出现的 applier/scheduler 写入、source terminal authority 和 page-layout 静默窗口，均属于未来物理备机 provider 的生产合同；当前 fast scan 只验证本仓库可观测的 Preserve lock-plan 流水线。

实现规则是 default-deny 普通认证客户端在 CLOSING 中默认被截断；只有 HA 管控连接可以继续执行新命令。DRAIN owner 的当前 DRAIN 与 t0 前 command 属于已经进入执行的旧 command；无响应清理包只完成协议资源释放，不构成业务命令放行。 COM_CHANGE_USER、COM_RESET_CONNECTION、COM_STMT_RESET、PING、STATUS、KILL 等均不得因当前风险分类没有命中而漏过。

8.3 错误映射

当前已实现内部 block result BLOCK_CLOSING_DRAINED，由 protocol 和 SQL 两个 dispatch 入口都映射为 ER_PRESERVE_TRX_SESSION_DRAINED。不要把全局 CLOSING 伪装成 THD 已永久进入 PRESERVED_DRAINED， 因为 RESET 后这些连接需要恢复正常执行。

两个 gate 共用 preserve_trx_is_ha_control_connection(thd)：直接检查 Security_context::priv_user() 是否精确等于 preserve_trx_ha_admin，并确认有效权限含 SHUTDOWN_ACL。该判断发生在 SQL 解析前，不读取 SQL 文本。实际 RESET 执行仍再次检查账号与 check_global_access()；普通 root、PROCESS、SUPER、SYSTEM_USER 或用户名包含 admin 都不会自动获得豁免。 连接误持事务不是 gate 的 SQL 分类条件，而是在 target 枚举中触发整批 fail closed。

4020 的唯一承诺 本次 command 没有执行，代理可以挂起。4020 不承诺该事务最终一定被 transfer、prewarm 或 promotion； 后续 HA 还要结合 DRAIN result 的 survivor/excluded 列表决定重放位置。
没有 4020 不自动等于可重发 只有与当前 drain generation 匹配的计划内 shutdown/promotion 终态、旧 command 已收敛、连接按终态关闭且事务随后 RESUME 成功时， 代理才可把未得到完整结果的队首请求视为 CLOSING 后未执行请求并重发。普通网络故障、mysqld 异常退出或无法匹配 HA attempt 的断连仍是歧义，禁止盲重放。

错误码 4020 和中性客户端文案 Preserve drain is active; this command was not executed 已交付。 该文案同时兼容 CLOSING 截断与已 drained 会话，不声称事务已经 Preserve 成功。

诊断窗口 普通业务连接在 CLOSING 中执行 SHOW、STATUS、KILL 仍返回 4020，不增加命令级诊断白名单。 HA 使用专用管控连接查询状态或执行 RESET，因此既保留业务硬截断，也不存在控制面诊断盲窗。

9.1 这是全局 deadline，不是每事务 timeout

  • 所有 t0 前正在执行的 command 共享同一个 deadline。
  • 不能在等待某个 token 时重新开始 B，否则 N 个 target 会串行放大为 N×B。
  • target wait 应批量观察或逐个读取同一绝对 deadline。
  • deadline 判断使用 monotonic clock，不使用 THD 的启发式 command start 时间。

9.2 两级 deadline 与串行预算

参数 B 只度量“旧 command 收敛窗口”，它是现有 CLOSING 总预算内的子截止线，不是独立于总预算之外再追加 1 秒。 有 warmcopy participant 时，现有 preserve_trx_warmcopy_close_timeout_ms 从 t0 形成 overall_close_deadline_us；没有 warmcopy participant 时，复用现有 drain hard deadline 作为外层安全上限。

禁止预算偷换 不能把 3 秒 operation timeout 写成 Phase2 总预算，也不能让 participant prepare/close 在 command wait 后重新开始一轮 30 秒。 现有 Phase2 总指标可继续覆盖 CLOSING 后全链路，但报告必须另外给出 command wait、participant close、transfer tail 和 CLOSING 到 FINAL_ACK 总时间。

当前 sysvar help 已明确：preserve_trx_transfer_phase1_timeout_ms 同时约束 Phase1 classic operation 和 readiness； preserve_trx_transfer_phase2_timeout_ms 是 classic session 单次 connect/read/write operation timeout，不是 Phase2 总时限。

10. 参数 A：early 首版固定 A=ON

参数与选择策略均已实现 A=OFF 的现有 legacy 行为不变；当前工作树只为 A=ON 启用 early 路径。

10.1 A=ON：整批终止

  1. 任一 target 在 closing_command_deadline 仍为 PENDING_QUIESCE，本次 drain 失败；只有这个状态表示 CLOSING 前的旧 command 尚未完成。
  2. 终止 source transfer epoch，receiver 不得形成 accepted epoch。
  3. 停止投递并 join Preserve worker；复用现有 batch restore，把已 EARLY_STAGED 的事务挂回原 THD。
  4. 清除 batch generation，沿用现有回撤/失败路径。
  5. 不 KILL 仍在执行的 command，不把 timeout 转换成事务 rollback。
  6. HA 让原主继续承担业务；代理在 HA 确认后把已挂起的 4020 command 重放到原连接。
A=ON 的成功路径 如果 deadline 前全部旧 command 都已结束，pending 集合必须为空，随后才进入当前仓库可验证的短时 guard、 两次 O(N) fast-stamp scan 和脏 token 的定点 replacement。A=ON 的价值不只是“超时整批失败”，还在于成功路径中不存在 被排除但仍继续写入的 command。当前仓库以 conversion freeze、两次 scan 和再次漂移即 fail closed 验证共享流水线； 这不是未来物理备机所需的 production terminal proof。

10.2 A=OFF：维持现状，不进入 early coordinator

当前 strict standby-transfer legacy 路径已经支持 command-timeout exclusion、结构化 survivor/excluded result 和空 survivor 处理； 本设计不删除也不重写这些能力。attempt 创建时若观察到 A=OFF，固定选择 legacy batch 路径，后续不能切换到 early。

为什么不在首版扩展 A=OFF early A=OFF 需要逐 token ABORT 确认、survivor-only participant finalize、排除后的持续写隔离和新的终态 mutation 合同， 这些都不是“谁先结束谁先 Preserve”这一实际性能问题的必要条件。为避免扩大状态机和 HA 语义，首版明确不实现。

11. CLOSING 逐 token Preserve 与终态锁计划

当前工作树已实现：strict v4 + A=ON 本节解决两个同时存在的目标：多个旧 command 中谁先结束，谁就先开始 Preserve 和 receiver prewarm； 但 early 阶段不能把可能变化的 record-lock descriptor 写死到最终 snapshot。设计因此明确分为“provisional object 预热”和 “terminal generation 下最终 metadata 发布”两层，epoch 接受和所有权切换仍保持批次原子性。

11.3 ready 发现与投递纪律

  1. 进入 CLOSING 时冻结 target identity；新 command 被 4020 截断，不再扩充 target 集合。
  2. coordinator 每轮对全部 pending target 做一次联合观察，不再按 vector 顺序逐个阻塞等待。
  3. 在同一次 LOCK_thd_data 临界区原子观察到本 generation 已从 PENDING_QUIESCE 发布为 QUIESCED 后，先把 coordinator 状态从 PENDING 转为 PRESERVING 并移出 command-timeout 集合；随后完成该 token 的 session/temp 边界校验、binlog seal 和 lock participant seal，采集初始 fast stamp，再投递 Preserve worker。
  4. 若 enum 已为 QUIESCED 但 m_server_idle=false，旧 command 已在此前 idle boundary 完成。coordinator 还要在同锁下确认 generation/member、连接未 killed、未进入 release/teardown 且 CLOSING gate 仍生效；满足时把当前活动识别为后续 closing rejection，复用现有允许 rejection-inflight 的 pin 纪律继续 Preserve，不再归入参数 B 的 timeout 集合。任一资格条件不满足则按 target eligibility 失败处理，不能把它伪装成 ready，也不能降回旧 command 的 PENDING_QUIESCE。
  5. 发现 DRAINED_NO_TRANSACTION 后清理本 generation 标记，不产生 Preserve token。
  6. 其他 command 继续在原 THD 执行；coordinator 不持 LOCK_thd_data、manager lock、participant lock 或 transfer session mutex 等待。
  7. 到绝对 deadline B 时，只检查仍在 PENDING 的 command；任一存在即按 A=ON 整批回撤。已经转为 PRESERVING 的 token，包括已入队但尚未获得 worker 的 token，不再属于 command timeout 集合；其后队列、participant、worker 或剩余预算失败均按 post-ready 整批失败处理，不受参数 A 排除。
“一结束就 Preserve”的可测定义 首版不在 command hot path 建队列或执行回调。coordinator 使用 10ms 级控制面轮询，目标为 command_boundary_to_preserve_enqueue_us P99 小于 20ms（worker 有可用容量时）。这里的 boundary 明确定义为 同锁观察到本 generation 的 QUIESCED，且确认它来自 CLOSING 后的旧-command completion boundary。这是有界发现延迟， 不是等待整批结束；业务 workload 本身不调用 sleep。

11.4 participant 的最小拆分

binlog participant 已按 THD/token 保存候选，可增加窄的单 target prepare/seal 入口，并让现有 batch 入口继续作为 wrapper。 lock participant 当前的 prepare_quiesced_targets() 会裁剪 target map 并清空全部 artifacts， phase2_preflight() 也会全量清空；因此不能拿 singleton vector 反复调用现有 destructive batch API。

  • 增加非破坏性的 prepare_quiesced_target(thread_id) 与 seal_quiesced_target(thread_id)。
  • 单 target API 只生成或固化自己的 artifact，不删除其他 pending/early token 的候选和已封存结果。
  • 现有 batch API 复用单 target helper，并只在 survivor set 固定后执行一次最终 pruning/accounting。
  • 全局 close_phase1() 仍在 pending command 收敛后调用；不得因某个 early token 完成而停止其他事务的 Phase1 capture。
  • candidate token/XID 确定后，本 generation 只执行一次 provenance begin-many；成功后只对最终 survivor 统一 bind-many，不改成每 token ledger/fsync。

11.5 provisional Preserve 与 receiver object prewarm

  1. Preserve worker 复用现有单 target Preserve 核心、内核对象序列化、detach 和 Preserve_trx_batch_item 回撤信息。
  2. worker 只通过现有 begin_token_prewarm_manifest() 发送可独立预热的 provisional external object，例如 record-lock blob 和 binlog cache。
  3. early 阶段不发送最终 snapshot、Resurrection Index，不调用 finalize_token_manifest()；source 在 generation-local item 中保留 bundle candidate 与 object descriptor。
  4. receiver 每收到一个对象的 SEAL_OBJECT 即复用现有 object prewarm；旧 generation 被替换时，复用现有 cache/staging invalidation。
  5. receiver 此时仍处于 DECLARED/RECEIVING 语义；不得发布 accepted epoch，不得供 production promotion gate 使用。
  6. source session mutex 只串行化短小 frame 发送。首版不增加第二套 sender scheduler；若 E2E 证明该互斥成为瓶颈，再依据指标单独优化。
FINAL_ACK 前所有权不变 EARLY_STAGED 不是 durable、accepted 或 promotion-ready。source 保存已 detach 的 trx_t* 与 rollback image； RESET、worker 失败或最终复验失败时，先停止发现并 join worker，再 ABORT 整个 receiver epoch，最后复用现有 restore helper 挂回原 THD。

11.6 为什么最终 snapshot 必须延后

struct Preserve_trx_lock_fast_stamp {
  lock_warmcopy_trx_lock_fence_t trx_fence;
};

现有完整 record-store fence 需要遍历 shard 并计算 canonical SHA，只用于单 target seal 前证明 Phase1 派生缓存没有变化； 它不进入 1000 token 的 terminal 快筛。fast stamp 直接保存现有 lock_warmcopy_trx_lock_fence_t： trx_locks_version 在锁对象加入/移出事务锁链时单调递增，n_rec_locks 保存记录锁数量， coordinate_generation 覆盖 reorg/move/inherit 等锁坐标变化，conversion flags 覆盖 freeze 后的隐式锁转换风险。 这些字段在既有 trx_preserve_sample_lock_warmcopy_fence() 中持 trx_mutex 一次读取， 不扫描 record payload、数据页或 Undo。

零记录锁与 ABA 合同 n_rec_locks=0 的 survivor 不产生 record-lock payload、空 blob、空 shard、文件或额外 runtime identity。 它仍保存一份有效 trx fence；若中间出现并再次释放锁，原生锁链 add/remove 会推进 trx_locks_version， 因而“0 -> 非 0 -> 0”不能伪装成 clean。record store 的 clear/reseed 是派生缓存生命周期，不是 terminal 事务身份； candidate 生成后由 live trx fence 判断事务是否漂移，不能再用重写 shard generation 总和复制一套权威状态。
  • 初始 Preserve 完成后保存一份 stamp；final validation window 中逐 token 调用现有 trx_preserve_sample_lock_warmcopy_fence()。
  • early→第一次 terminal scan 比较 lock version/count、coordinate generation 和 conversion flags；任一变化即加入 D。
  • freeze_generation 不参与上述比较，因为获取 guard 本身会递增它；第一次 terminal scan 保存新值，第二次 scan 必须保持相同，conversion flags 也必须持续为 false。
  • live fence 相同且 terminal freeze 合法的 token 复用 receiver 已预热的旧 generation。
  • 第一层只读固定大小字段，不扫描 record payload、数据页或 Undo；检测复杂度为 O(N)，内存开销为 N 份小型 stamp。
  • 只对 D 个 dirty token 执行完整 fence、payload 重导出和 digest 计算，复杂度为 O(N) + O(脏 token 的锁总量)。
  • stamp 读取失败、trx_t* 不再属于 active drain、conversion flag 异常或第二次 scan 再变化时整批 fail closed。
采样锁序与性能裁定 每次 sample 只短暂持有一个事务的 trx_mutex，释放后才处理下一个 token；不持 record-store partition mutex， 不在锁内编码 payload或发送网络 frame。首版不增加 batch sampler。N=1000 的两次 O(N) sample 必须由 Release NFR 测量； 只有它被证明确实成为 500ms 窗口瓶颈时，才单独评审批量读取或分片并行，不能预先把新的 generation 维护扩散到全部 record-store 写路径。 当前仓库无 production page-layout provider，验证报告仍必须标记 terminal_page_layout_fence=false。
不增加第二套 generation source_live_generation 仍只表示 transfer object 发布版本；它不参与 live lock dirty 判断。 本轮不增加全局/per-target record-store generation、热路径 dirty set或空 token identity，避免重复维护事务权威状态和扩大 OFF-path。 第二次 scan 仍比较 replacement 后保存的 live trx fence；不得用网络发布成功掩盖导出期间发生的真实锁变化。

11.8 终态复验与定点 replacement

  1. deadline 前确认 pending 为空，等待所有 Preserve worker 完成并关闭全局 Phase1 participant。
  2. 复用现有 target eligibility 与 participant closure，并对 token 启用现有 conversion freeze；不新增 writer census、writer registry 或全局 purge 控制。
  3. 执行第一次 O(N) fast-stamp scan，得到 dirty set D。
  4. 对 D 个 token 使用现有 worker 并行重采完整 fence与 record-lock payload，分配更高 source_live_generation。
  5. source 复用 v4 DECLARE_OBJECT -> OBJECT_CHUNK -> SEAL_OBJECT replacement；receiver 复用 generation-CAS 语义清理旧 prepared/cache/staging并预热新 generation。
  6. 把 generation-local bundle candidate 的 record-lock descriptor 更新为新 object；此时才生成最终 snapshot、Resurrection Index并调用 finalize_token_manifest()。
  7. 发送 COMMIT_EPOCH 前执行第二次 O(N) stamp scan，并确认全部 CLOSING 前旧 command 已通过现有 command boundary 收敛。任一 token 再次变化、replacement 失败或 deadline 不足，均整批 ABORT并恢复 source，不做无界重试。

当前 guard 只覆盖最后快筛、D token replacement、最终 metadata与 COMMIT/FINAL_ACK 窗口，不覆盖整个 CLOSING。 这样 early Preserve/prewarm 仍可与慢 command 在线重叠。conversion freeze 在成功 handoff、失败或 RESET 后都必须释放。 若 lease/freeze 在同一 commit attempt 内意外释放或需要重新获取，旧 attempt 立即 fail closed；不得把新的 freeze_generation 当成旧 attempt 的延续。重新尝试必须从新的 attempt/generation 重新建立 fast stamp 与最终发布，不复用旧验证结果。 receiver 的在线接收/prewarm 不停止 target purge，也不改变只读业务资源治理合同。

物理备机接口边界 fast stamp、replacement 与二次 scan 只能验证当前仓库的共享流水线。production promotion 仍要求外部 provider 给出 terminal mutation/apply/authority proof； provider 缺失时现有 promotion wrapper 必须 fail closed。provider 如何冻结 purge/reorg、追平 apply 或取得 authority 不在本文实现范围。

最终发布必须复用 early 阶段已构建的 bundle candidate，只修补 record-lock external descriptor并执行 canonical encode； 不得在 final validation window 内重新扫描全部内核对象或重新读取 clean token 的大 payload。这样窗口成本主要是 O(N) stamp、O(D) replacement 与小型 metadata 编码。

worker result 必须在 generation-local batch item 中保留显式 trx_t*、early stamp、最终 stamp 与 object descriptor； 不能只靠可复用的 numeric token 在稍后重新推断事务身份。active drain 期间 reaper 不得 claim/reclaim 该 record；RESET、ABORT 和 COMMIT 由同一 coordinator 结束这段指针生命周期。

11.9 COMMIT

pending 为空、worker 全部成功、participant 全局关闭、replacement 完成、最终 metadata已发布且第二次 fast-stamp scan 通过后， source 才发送唯一一次 COMMIT_EPOCH。早期 token 自己携带的 LSN 只描述构建事实，不能因某个 token 已 prewarm 就提前 accepted 或 adopt。

12. HA 与代理合同

唯一接口权威面 HA 身份、4020 唯一承诺、DRAIN survivor/excluded 结果、计划内断连、RESET 与 promotion 后请求重放，以 Transfer Phase 2、4020 挂起与 Tx→Ty 事务续作对接指南 为权威接口合同。本文只定义 CLOSING 内核编排，不另建第四套 HA/Proxy 协议。

12.1 本文保留的最小合同

  • 4020 只表示本 command 未执行，不表示事务已经 Preserve 成功。
  • strict transfer 当前结构化 DRAIN result、单响应和 shutdown 顺序保持不变，本文不修改 schema。
  • RESET/失败后由 HA 确认原主 gate 已解除，再在原 Tx 单次重放；未来切换到新主时必须先 RESUME 成功，再单次重放。
  • FINAL_ACK 仍是 source/target transfer 所有权边界；source 此后不等待 READY，不触发 promotion。

完整账号矩阵、结果列、代理重放和断连语义只维护在上述权威对接指南中，避免本设计与接口文档分叉。

12.2 旧 command 收敛与终态断连

正确性不要求在 COMMIT_EPOCH 前让每个普通连接再收到一次 4020。真正必须闭合的是 CLOSING 发布前已经进入执行主体的旧 command： 它保持 PENDING_QUIESCE，完成正常响应并回到下一次 command-read 边界后，才发布 QUIESCED 或 DRAINED_NO_TRANSACTION。参数 B/A 继续约束这一收敛过程。

  1. CLOSING 发布后，普通连接新读入的 command 由现有 protocol/SQL default-deny gate 在执行主体前截断；source 在线时尽快返回 4020。
  2. 不发布额外 final_response_cutoff_published，不在 get_command() 前 park 普通连接，也不增加 per-THD accepted/response sequence。
  3. promotion 或 shutdown/startup 成功路径保持 CLOSING gate 直到普通连接关闭；代理先消费连接关闭前已经到达的完整 MySQL response，再处理终态断连。
  4. 只有 HA 终态与当前 attempt/generation 匹配，并且对应事务已在终态节点 RESUME 成功，代理才重发没有得到完整结果的队首请求。
  5. RESET 不关闭原连接：已收到完整 4020 的请求由代理重发，尚未被 mysqld 读取的请求保留在 socket 中，gate 解除后自然执行；代理不得重复发送。
  • classic protocol 半双工是本合同前提；同一 backend connection 不支持多个 response-bearing request pipelining。
  • COM_STMT_SEND_LONG_DATA/COM_STMT_CLOSE 保持无响应协议语义。终态路径在新 backend reprepare并全量重发；RESET same-socket compound 由对接指南单独约束。
  • 非计划内网络故障、mysqld crash、无法匹配 generation 的断连或不满足旧 command completion barrier 时，结果仍不确定，不得自动重放。
  • 该简化不等待 receiver READY，不改变 FINAL_ACK 后 source/target 解耦，也不新增 timeout sysvar。

12.3 FINAL_ACK 后边界不变

source 收到 FINAL_ACK 后 transfer 协议结束。target 后续 prewarm、TTL、promotion 或 abandon 由 target 和 HA 管控； source 不查询 READY、不触发 promotion，也不因 target 后续失败重新打开本 epoch。

14. 并发与竞态

14.1 transition 与新 command

command admission 必须读取 manager state 的同一发布序列。若 command 在 CLOSING publication 前完成 admission，它属于旧 command； publication 后才进入 gate，普通业务连接返回 4020，HA 专用管控连接绕过门禁。不能出现“看见 CLOSING 但仍按 SQL 风险分类放行”的中间态。

classic protocol 每个连接一次只处理一个 command；t0 前旧 command 未完成时，同连接不会并行 dispatch 下一条 command。 本设计依赖该半双工不变量区分 old/new command；同一 backend connection 的 response-bearing request pipelining 明确不支持。 未来若引入 pipelining，必须重新设计 command identity、终态请求归属与 admission，而不能沿用本合同。

控制连接豁免只解决控制面可达性。readiness 直接忽略专用控制连接，避免 PING/SHOW/RESET 拖住 Phase1；target 枚举若发现它持有显式事务或 RW participant，则必须把该事实作为不满足控制连接合同处理并整批失败， 不能一边绕过 command gate 一边把它从 Preserve 正确性集合中静默删除。

14.2 command boundary 与 deadline 同时发生

在目标 THD 的同一次 LOCK_thd_data 临界区完成一次性裁决：

  • 若 command boundary 已发布 DRAINED_NO_TRANSACTION 或本 generation 的 QUIESCED，说明 CLOSING 前旧 command 已完成，按 ready 处理。
  • QUIESCED && !m_server_idle 只有在同锁确认 batch member、generation、连接生命周期和 CLOSING gate 均有效时，才表示随后读入且会被 gate 拒绝的新 packet；它不接触事务状态，也不重新把 token 降回 pending。否则按 eligibility 失败处理。
  • 若仍为本 generation 的 PENDING_QUIESCE，说明旧 command 未完成，deadline 到达时按 A=ON 整批失败。
  • ABORT 网络发送、worker join 和 participant restore 在解锁后完成；持 manager mutex/participant lock 时不得获取目标 LOCK_thd_data。

14.3 RESET

RESET 赢时先锁存 reset marker 并停止发现/投递新 token；coordinator 取消尚未开始的 job并等待运行中的 Preserve worker 退出。 若已有 EARLY_STAGED token，source 发起整 epoch best-effort ABORT/transport cancel，并复用现有 batch item/rollback image 把已 detach 事务挂回原 THD；仍在执行 command 的 target 不做 detach/reattach。RESET 的同步成功条件只包含 source 原连接恢复可运行和 4020 gate 解除，不等待 target ABORT ACK、READY 或物理 staging 清理；receiver orphan 由既有进程内 TTL 销毁。 worker 退出、sender/participant teardown 与 target 清理由后台收敛。本设计不重新定义 FINAL_ACK 后 RESET 的所有权合同。

14.4 ABORT 与 COMMIT

early 首版只有整 epoch ABORT 或唯一一次 COMMIT_EPOCH，不存在逐 token exclusion 与 survivor commit 并发。 RESET/失败先停止发现并 join worker，再发起 best-effort epoch ABORT并恢复 source；commit 一旦开始则沿用现有 session 终态约束，不能再切回 RESET。

14.5 Preserve worker 与 coordinator

  • 只有 coordinator 修改 generation-local 流水线状态；worker 返回不可变结果，不直接决定 epoch commit/exclusion。
  • worker 开始后，即使 deadline B 到达，也按 Preserve/transport 的既有剩余预算完成或失败；A 不能把 Preserve 慢误判为 command timeout。
  • 单 token participant seal 与 Preserve 不持目标 THD 的 LOCK_thd_data 跨越序列化、文件或网络操作。
  • 提交前 join 全部 worker；任何 worker 未完成、失败或结果缺失都禁止 COMMIT_EPOCH。
  • receiver prewarm 成功早于 COMMIT 只形成可丢弃缓存，不能反向驱动 source 状态。

14.6 final validation window、快筛与 replacement

  • final validation window 只能在 A=ON 且 pending 为空后进入；进入前先做不暂停 purge 的 optimistic catchup。
  • batch stamp sample 固定为“逐 partition 第一次 generation 复制 -> 逐 trx fence sample -> 逐 partition 第二次 generation 复读”；每次只持一个锁，partition mutex 与 trx_mutex 绝不嵌套，也不得持 transfer session mutex 或任一采样锁发送 frame。
  • 第一次 fast scan 只冻结 dirty set D；完整 payload 重导出在 scan 锁外执行，但仍位于 final validation window 内。
  • receiver 接受更高 generation 的 replacement DECLARE 时即按现有 v4 语义失效旧 prepared/cache/staging；新 generation 完整 seal/prewarm 前 token 保持 NOT_READY，失败不得把新旧任一 generation 标成 accepted。
  • 最终 snapshot 必须引用 replacement 后的 descriptor；第二次 fast scan 在 COMMIT 前完成，任何变化均停止 COMMIT。
  • RESET 或任一失败路径必须幂等释放 conversion freeze；同一 commit attempt 不允许 thaw/re-freeze 后继续使用旧 stamp。
  • 第二次 scan 不是 production terminal proof；报告必须明确 terminal_page_layout_fence=false，production wrapper 在 provider 缺失时继续 fail closed。

14.7 DRAIN result 与 shutdown

token 集合在 COMMIT 前冻结；FINAL_ACK 确认后结果内容不再变化。active attempt 必须先 CAS 到 terminal handoff，拒绝后续 RESET， SQL owner 再在进入 SHUTDOWN_REQUESTED 和 server shutdown 前同步发送结果，且 shutdown 路径不得再发送第二个 OK。 若连接在响应期间断开，不能反向修改 receiver 已接受的 epoch；HA 按控制连接断开处理，不由 source 重开 transfer。

下列短名称是 E2E report-field alias，不要求新增同名 SHOW STATUS。性能报告同时输出 phase1_readiness_wait_us、closing_command_wait_us、 现有 Preserve_trx_phase2_participant_prepare_us / Preserve_trx_phase2_participant_close_us、 phase2_transfer_tail_us、closing_to_first_early_staged_us、final_fast_scan_us、 replacement_us、报告元数据 terminal_page_layout_fence 和 closing_to_final_ack_us， 禁止只展示其中最短的一段或把 3 秒 operation timeout 当作总耗时上限。

17. 测试计划

验收主线：MTR + Standalone E2E 测试代码和 release 证据以真实 mysqld 为主。MTR 负责单/多连接协议行为、权限、DEBUG_SYNC 竞态和零副作用； standalone 双 mysqld E2E 负责 source/receiver、ABORT/COMMIT/FINAL_ACK、READY 与 token 对账。 GUnit 只验证不需要网络、THD 生命周期或真实 receiver 的纯决策逻辑，不能单独关闭任何端到端验收项。

17.1 GUnit：仅纯决策辅助

  • default-deny command 分类表及 t0 前 inflight、HA 管控连接、无响应 teardown 的纯 block-result 决策。
  • min(t0+B, overall close deadline)、剩余预算、clamp 计数和多 target 不产生 N×B 的纯时间计算。
  • readiness frozen identity 集合的 sequence 比较、首次冻结和后续新 command 不扩充集合。
  • coordinator 内部 token stage 只允许单向迁移；deadline 只分类 PENDING，不分类 PRESERVING/EARLY_STAGED。
  • fast stamp 的 lock version/count、coordinate generation 和 conversion flags 全字段相等/单字段变化，以及 N token 到 D token 的稳定分类。
  • 验证零记录锁的 0 -> 非 0 -> 0 仍因 trx_locks_version 单调变化而判 dirty，不要求空 record-store identity。
  • 验证 v4 replacement 只推进 source_live_generation，不会自行改变 live trx fence；第二次 scan 不因发布动作误报，也不能通过事后重置 baseline 掩盖 export 窗口中的真实 mutation。
  • final descriptor 只能选择 replacement 后 generation；第二次 scan 变化必须阻止 COMMIT，不能再次进入无界 replacement loop。
  • 不得为方便 GUnit 在生产头文件增加 *_for_unit_test API；需要真实 THD/网络/receiver 的行为直接进入 MTR/E2E。

17.2 MTR：协议、并发与零副作用主回归

  • 在 source 保持在线的 CLOSING DEBUG_SYNC 窗口，由普通连接发送 COM_QUERY、prepared execute/fetch、INIT_DB、PING、SET、DO、SHOW、STATUS、KILL、CHANGE_USER、RESET_CONNECTION、STMT_RESET 等；除明确的无响应 teardown 外，已读 packet 均得到 4020 且业务主体零副作用。
  • 测试启动时显式创建 preserve_trx_ha_admin 并授予 SHUTDOWN_ACL；该专用连接在同一窗口可执行 PING、SHOW STATUS 和 RESET DRAIN，普通 root 或仅持 SHUTDOWN 的连接不能绕过。另用非固定用户名但持 SHUTDOWN 的账号证明当前 DRAIN 入口仍可发起命令，从而锁定“部署合同不等于 DRAIN 硬校验”的现状；若未来硬化 DRAIN 身份，该用例就是兼容性评审基线。
  • 控制连接依次执行 PING、SHOW STATUS 和 RESET DRAIN 时，Preserve_trx_closing_control_connection_commands 每个 protocol command 只增加一次，SQL 二次门禁不得重复计数。
  • 仅持有 PRESERVE_TRX_TRANSFER_ADMIN、不具备 HA 身份的连接在 source CLOSING 窗口同样得到 4020；另设 receiver 正常状态用例证明原 transfer handler 未受影响。
  • 另一个 HA 控制连接持有活动事务时，DRAIN 整批失败而不是忽略该事务。
  • 验证每条被 4020 截断的 command 没有数据、事务、schema、session variable 或 cursor side effect。
  • 4020 客户端文案只声明 command 未执行；无事务会话不得收到“事务已经 Preserve”的误导文本。
  • 一个 t0 前已执行的长 command 正常返回并发布 command boundary；同连接随后读到的新 command 得到 4020。
  • 在 t0 前旧 command 的正常响应完成前暂停，验证该 THD 仍为 PENDING_QUIESCE，不得 Preserve 或发送 COMMIT_EPOCH；释放并进入下一次 command-read boundary 后才可转为 QUIESCED。
  • 在 CLOSING 后 4020 本地发送点暂停，验证该 command 主体零副作用；promotion/shutdown 终态不因等待该 late response 新增 final cutoff，RESET 则按原连接是否已收到完整 4020 分流。
  • 三个旧 command 通过确定性 DEBUG_SYNC 分别到达边界；验证每个 token 都在自己的 PENDING→QUIESCED 边界后进入 Preserve，而不是等待第三个 command。
  • 构造 token 已为 QUIESCED、随后 CLOSING rejection 正在发送且 m_server_idle=false 的窗口；同锁确认 member/generation/连接生命周期有效后 coordinator 仍可 Preserve，因为旧 command 已在更早边界完成，rejection 不得接触事务状态；另测 teardown/killed 时稳定 fail closed。
  • 一个 token 已 EARLY_STAGED、另一个仍 PENDING 时执行 RESET；验证早期 token 挂回原 THD、pending command 不被 detach、receiver 无 accepted epoch。
  • 通过 Debug-only 的确定性 lock-list 或 coordinate-generation 变化注入一个 early token 漂移；验证 survivor 自身 Undo 仍为 PREPARED、只把该 token 分入 D，未漂移 token 不重算 payload。测试不得依赖后台 purge 恰好调度到该页，也不得把运行时全局暂停 purge 当成成功条件。
  • 验证 dirty token 以更高 generation replacement，receiver 旧 cache/staging 失效，新 generation prewarm，最终 snapshot descriptor 指向新 object并可正常 COMMIT。
  • 验证同 generation/更低 generation replacement 被现有 v4 合同拒绝；replacement 后二次 stamp scan 再变化时整批恢复。
  • 验证当前 guard 只在最终窗口启用 conversion freeze，成功、RESET和故障注入后都释放；报告元数据固定为 terminal_page_layout_fence=false。
  • receiver 的 purge 状态在整个 transfer/prewarm 中不变；本轮不以停止 target purge 换取 READY。
  • A=ON：确定性长 command 超过 B，source 不发送 accepted epoch；HA 解除 gate 后，代理在原连接重放先前 4020 command 成功。
  • 现有 CLOSING/A/B、structured result、receiver TTL 和 RESET MTR 作为回归基线复跑，不为 early pipeline复制同义用例。
  • RESET 在 readiness/CLOSING wait 中解除 gate；代理模拟客户端在原连接重放 4020 command 成功。
  • legacy/A=OFF 回归：被 timeout exclusion 的旧 command 在排除后继续写入；survivor artifact/digest 必须保持不变。该测试只关闭现有 legacy 污染风险，不把 exclusion 引入 early pipeline。

17.3 Standalone 双 mysqld E2E：transfer 真实性主证据

  • source 真实 DRAIN，target 真实 receiver save/prewarm；代理模拟层挂起 4020 command。
  • 代理模拟层保持每 backend connection 单一 response-bearing outstanding request；先消费断连前到达的完整 MySQL packet。完整 4020 直接挂起；只有匹配当前 HA terminal generation 的计划内断连，才允许在事务 RESUME 成功后重发无完整结果的队首请求。
  • 注入非计划内 TCP 断开、mysqld crash 或 generation 不匹配，验证请求保持 ambiguous，不得借用计划内终态合同自动重放。
  • 三个 command 分别在约 20ms、200ms、900ms 到达边界；每个 token 的 receiver staged prewarm 都在自己的完成点后启动，且第一个 prewarm 早于最后一个 command 完成。
  • 验证 EARLY_STAGED token 在 COMMIT_EPOCH 前不能被 accepted/promotion gate 消费；FINAL_ACK 后才出现 accepted epoch。
  • A=ON 超时发生时，已提前发送的 token 与未完成 token 一起导致整 epoch ABORT，source 早期事务全部恢复。
  • 两个 token 已 EARLY_STAGED、第三个 Preserve worker 注入失败：禁止 COMMIT，source 已 detach 的两个事务按逆序恢复，receiver 无 accepted epoch；ABORT 清理成功时 staging 消失，清理失败时只能进入既有 cleanup-pending 且仍不可 promotion。
  • readiness 场景分别覆盖无长 SQL、一个长 SQL在 Phase1 完成、长 SQL跨越 Phase1 deadline。
  • N=1000 分别运行确定性的 D=0、D=1 和小比例 D；D=0 必须通过受控 mutation 静默窗口建立，不依赖后台 purge 的偶然调度；证明第一层只读 stamp，clean token 不做完整 fence，且 replacement 数严格等于 D。
  • 报告 readiness、每 token boundary→enqueue/staged/prewarm、early/late token 数、两次 fast scan、D、replacement bytes/time、terminal_page_layout_fence=false、participant prepare/close、transfer tail、CLOSING 到 FINAL_ACK 时延和 source/receiver token 对账。
证据边界 当前仓库没有真实物理复制和升主流程。E2E 只能证明 command 截断、strict v4 transfer、receiver save/prewarm 和共享流水线， 不能宣称完成真实物理 promotion E2E。

17.4 Local startup：共享回归，不是本设计验收

既有 local preserve/shutdown/startup/resume E2E 继续回归共享序列化与恢复内核，但 early pipeline 不修改该路径， 也不以 startup timing 关闭本设计的 transfer/receiver 时序验收项。代理场景额外验证：shutdown 窗口内未进入执行主体的队首请求因连接关闭而保留， startup 完成后先在新连接 RESUME 事务，再重发一次；不得在 RESUME 前发送，也不得重放 shutdown 前已取得完整结果的旧 command。

17.5 隔离性回归

  • preserve_trx_enable=OFF 时 command dispatch 与原生 MySQL 完全一致。
  • MTR 运行同一 command matrix 验证 OFF 时原生行为；辅助 source-shape lint 同时锁定 OFF 短路位于新 CLOSING default-deny 分支以及 command identity 字段写入、monotonic clock 读取和 LOCK_thd_data 获取之前，并锁定 CLOSING gate 不重新退化为 SQL/protocol 风险命令枚举。
  • 单事务 local preserve、shutdown/startup recovery、SQL RESUME 行为不变。
  • 参数 B 的 CLOSING command deadline 作用于所有 two-phase 路径，包括 standby transfer、temp-table Phase1 和要求 two-phase 的 lock/binlog warmcopy；A=OFF 的 timeout exclusion 只在 standby transfer streaming 中生效，其他路径无论参数 A 取值都继续整批失败。
  • 逐 token early pipeline 只在 strict standby transfer sink 生效；本地 durable shutdown/startup Preserve 继续使用原批次路径。
  • preserve_trx_enable=OFF 时 record-store generation 不递增、不多取 partition mutex；source-shape lint 确认没有新增原生 lock/B-tree/purge hook site或 purge stop/run wrapper。
  • 增加 mutation-site 枚举 lint：Preserve record store 的 set/replace/reset/discard/invalidate/seed/clear 写入口必须统一调用私有 generation bump helper；只读 export/fence/sample 不得误推进 generation。
  • 既有 receiver restart 无状态、FINAL_ACK 后 source 解耦合同不变。
