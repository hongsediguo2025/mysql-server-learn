1. 快速理解

Preserve/Resume 允许把未提交的显式事务保存为 token，重启后用 token 恢复到新连接。保存的是事务语义，不是自动提交结果；普通 token 可以继续执行 SQL 后再 COMMIT 或 ROLLBACK。带用户临时表 no-redo undo sidecar 且已经进入 native-adopted 状态的 token，也可以在 resume 后继续执行受支持的用户临时表 DML；旧 manifest 或 restored-only 路径仍只能完成读、COMMIT 或 ROLLBACK，不能继续写临时表。

核心原则：Preserve/Resume 是 fail closed 能力。事务无法完整保存时，命令应失败或回退安全路径，而不是生成语义不完整的 token。

2. 命令用法

2.1 单事务 Preserve

START TRANSACTION;
UPDATE t SET v = v + 1 WHERE id = 1;
PREPARE SHUTDOWN PRESERVE TRANSACTION WITH TIMEOUT 300;

可选项包括 WITH TIMEOUT n、WITH USER VARS、WITH NO USER VARS。成功后服务端返回 token，并触发 shutdown 流程。token 应安全保存，后续用于 resume。

2.2 Batch Drain Preserve

DRAIN TRANSACTIONS PRESERVE WITH TIMEOUT 1800 WITH USER VARS;

该命令由控制连接执行，用于停机前批量保存实例上的 eligible 事务。控制连接自身不能处于显式事务中。SOFT 模式先等待活跃事务自然收敛，超时后按配置升级；HARD 模式会杀掉其他活跃用户事务以收敛停机。

2.3 Resume

RESUME PRESERVED TRANSACTION '<token>';
COMMIT;

Resume 成功后，当前连接持有恢复后的事务。普通 preserved transaction 可以继续执行 SQL，然后提交或回滚。带用户临时表 no-redo undo sidecar 的事务只能继续 COMMIT 或 ROLLBACK；继续写恢复出的临时表会被拒绝。默认只能恢复自己账号创建的 token；跨账号恢复需要动态权限。

2.4 查看 token

SHOW PRESERVED TRANSACTIONS;

SELECT TOKEN, USER, HOST, STATE, EXPIRES_AT, BINLOG_STATE,
       BINLOG_CACHE_SIZE, BINLOG_WARMCOPY_STATE, TEMP_TABLE_STATE, LAST_ERROR
  FROM performance_schema.preserved_transactions;

5. 典型场景

5.1 维护窗口保存一个长事务

START TRANSACTION;
UPDATE orders SET state = 'processing' WHERE id = 1001;
PREPARE SHUTDOWN PRESERVE TRANSACTION WITH TIMEOUT 3600 WITH USER VARS;

重启后执行：

RESUME PRESERVED TRANSACTION '<token>';
COMMIT;

5.2 停机前批量保存空闲事务

SET GLOBAL preserve_trx_drain_mode = 'SOFT';
SET GLOBAL preserve_trx_batch_max_transactions = 1000;
DRAIN TRANSACTIONS PRESERVE WITH TIMEOUT 1800;

如果需要更强收敛，可改用 HARD，但要接受活跃用户事务被杀。

5.3 大 binlog cache

大事务启用 binlog 时，需要同时关注普通 MySQL binlog cache、单事务 sidecar 上限和 warmcopy 总预算。preserve_trx_warmcopy_max_total_bytes 控制单个 drain epoch 可接收的 warm external blob 总量；调大它主要增加允许接收的 artifact 容量和磁盘 IO，不表示预分配同等堆内存。

5.4 锁很多的大事务

锁预算首先受 preserve_trx_max_lock_count 控制。这里的锁包括 record locks、table locks、predicate locks、AUTO_INC locks 和 materialized implicit locks；read view、savepoint、MDL 也会进入恢复语义校验。当前 full 1s 目标要求大锁对象尽量在 phase 1 mirror 和 external artifact 中处理；如果 phase 2 仍重扫、排序、编码大量锁，就只能保证功能正确，不能宣称 1s SLO。

5.5 用户临时表

preserve_trx_temp_table_enable=ON 时支持受约束的用户 InnoDB temporary table。已存在临时表的事务型 DML 通过 physical image、dirty page overlay、dict binding、no-redo undo sidecar 和 ownership manifest 保持语义；native-adopted token 在 resume 后可以继续执行受支持的临时表 INSERT/UPDATE/DELETE，再 COMMIT 或 ROLLBACK。旧 manifest 或 restored-only token 仍按保护路径拒绝继续写临时表。用户临时表 DDL/元数据变更、缺失或损坏的 sidecar/undo 信息仍 fail closed。若该变量在 resume 前被关闭，普通 token 不受影响，但带 temp manifest 的 token 不会被消费，会返回可重试的 unsupported 状态，恢复时需重新打开该子功能。

6. 排障与限制

症状优先检查处理建议
Preserve 命令被拒绝总开关、权限、是否显式事务、XA/复制/升级/force recovery 状态。先修正环境；不要绕过 fail-closed 检查。
Batch drain 不收敛preserve_trx_drain_mode、grace、hard timeout、活跃事务列表。SOFT 适合温和维护，HARD 适合强停机。
Warmcopy 预算耗尽binlog cache 大小、warmcopy total、tail budget、pending range。调大预算前先确认 preserve 目录磁盘空间和 IO 能力。
锁导出失败lock count、modified table、scan pages、materialize timeout、spatial predicate。调参只能放宽已支持形态；unsupported shape 仍会失败。
Resume 失败token owner、read_only、binlog/GTID 模式、对象权限、snapshot integrity。保留 token 和 sidecar，查看 P_S LAST_ERROR。
重启后看不到已有 token实例是否以 --preserve-trx-enable=OFF 启动。startup recovery 只在启动时且总开关为 ON 时扫描 preserve 目录；运行中改 ON 不会补扫，应以 ON 重新启动。

6.1 当前不支持或不承诺的范围

  • 不支持把 LOCK TABLES、GET_LOCK()、global read lock、backup lock、HANDLER 等会话/全局状态作为 v1 preserve 目标。
  • R-tree/spatial predicate locks 不做 lock warmcopy 优化，fallback ON 走 live export，fallback OFF reject。
  • 物理复制集群中的跨机 artifact 同步和备机自动 resume 是接入方案，不是当前代码已经完成的能力。
  • phase 2 约 1 秒是性能目标；超过后功能仍应按正确语义继续，除非测试以 strict SLO 模式判失败。
