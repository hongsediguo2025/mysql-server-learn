Preserve/Resume 8.0.22 用户手册

面向 DBA、HA 平台、运维和值班支持，说明未提交事务跨受控停机的保存、恢复、备机传输、物理晋升接入，以及完整的配置和观测方法。

事实源：语法、系统变量、P_S、SHOW STATUS 与当前实现源码
4 条 SQLpreserve、batch drain、resume、show
64 个参数含本地、warmcopy、传输和晋升
29 个 P_S 字段与 SHOW PRESERVED 输出一致
183 个状态量逐项说明口径、单位与重置边界
使用前先确认边界 Preserve/Resume 面向受控停机。它保存的是未提交事务语义，不是提交结果，也不是任意 mysqld 崩溃后的事务续跑机制。生产备机形态还要求物理复制面与 Preserve 语义面共同满足晋升栅栏。

1. 特性定位

Preserve/Resume 把一个受支持的显式事务从当前连接中安全分离，保存为可验证的 durable snapshot 和外部对象；服务重启后，再把同一事务附着到新的连接。恢复成功后事务仍处于未提交状态，客户端可以继续执行受支持的 SQL，最后自行 COMMIT 或 ROLLBACK。

它解决的是维护停机、版本切换或物理备机晋升期间，长事务不希望全部回滚重做的问题。它不改变 MySQL 的提交语义，不把普通事务暴露成 XA 操作，也不保证所有会话状态都能跨进程恢复。

1.1 保存了什么

类别保存内容说明
事务内核状态InnoDB prepared transaction、内部 XID、undo/锁相关身份由 prepare、detach、startup recovery/attach 共同保持。
并发语义record/table locks、可物化隐式锁、read view、transaction-duration MDL恢复时重新验证并导入；不支持的锁族 fail closed。
SQL 事务语义隔离级别、当前 schema、SQL/InnoDB savepoint、modified tablesresume 前复检对象权限与目标 session 状态。
binlog/GTIDbinlog 状态、transaction cache sidecar、sql_log_bin、gtid_next只支持 ROW；恢复环境必须与保存时兼容。
可选会话数据用户变量 payload只有显式 WITH USER VARS 才保存。
受约束临时表InnoDB 用户临时表 image、no-redo undo sidecar、manifest仅支持实现已验证的形态；跨机 portable transfer 当前不接受非空 temp manifest。

1.2 没有保存什么

普通连接身份、网络连接、客户端协议状态、open cursor、HANDLER、用户级锁、global read lock、backup lock、LOCK TABLES 等不会被转换为可恢复状态。这些上下文要么在入口直接拒绝，要么要求业务在停机前自行收敛。

2. 核心概念

概念准确含义常见误解
Preserve把显式活跃事务 prepare、detach，并发布经过校验的 snapshot/sidecar。不是提交，也不是只把 SQL 文本保存下来。
Resume把 preserved transaction 恢复并附着到当前新 session。不是重放历史 SQL；成功后仍需 COMMIT/ROLLBACK。
Token本地模式通常是 32 位小写十六进制随机串；传输模式可能是源端连接 ID 的十进制字符串。token 不是跨集群全局唯一身份；跨机还要结合 source UUID、epoch、generation/incarnation。
Snapshot bundle认证后的事务元数据，加 binlog cache、record-lock、临时表等外部对象。单看一个 .bin 文件不能证明事务完整可恢复。
Carriersnapshot/对象被持久化和交付的载体。可选本地目录或 standby transfer。carrier 不是事务一致性的全部证明。
Drain停机控制面：阻止新风险工作、收敛目标 session、批量 preserve，再请求 shutdown。单事务 preserve 也会做实例级收敛，不是完全局部操作。
Warmcopy在 phase 1 提前复制 binlog/锁对象，phase 2 只封口、复检和写最终元数据。不是跳过正确性检查；fallback 可能显著拉长 phase 2。
Standby pending接收端已持久化且等待外部 HA 在物理晋升时认领的传输产物。不等于普通本地 token，也不会自动出现在 P_S 表中。
Promotion adopt物理栅栏满足后，严格 gate 将 prepared token 转为晋升方拥有的状态。ADOPTED_FOR_PROMOTION 不能再由普通 SQL RESUME 消费。
Fail closed任何无法证明完整性、权限或一致性的路径都拒绝发布/消费 token。失败不表示可以删文件重试；越过 durable point 后要按状态处理。

2.1 Token 与记录身份

本地 token 用于 SQL resume；跨机传输的严格身份还包括 source server UUID、epoch、generation/incarnation 和对象摘要。运维系统不得把 token 字符串单独当作跨实例主键。

当前 SQL 响应行为 当前实现中，PREPARE SHUTDOWN PRESERVE TRANSACTION 成功时返回普通 OK，OK 包不携带 token；batch drain 也不返回 token 列表。受控重启后，应由具备 PROCESS 权限的管理连接通过 SHOW PRESERVED TRANSACTIONS 或 P_S 取得完整 token。生产传输模式则由外部 HA 控制面保存严格身份元组。

3. 本地模式快速使用

3.1 前置条件

SHOW VARIABLES WHERE Variable_name IN
  ('preserve_trx_enable', 'preserve_trx_transfer_artifact_mode',
   'binlog_format', 'read_only', 'super_read_only');

-- 预期：preserve_trx_enable=ON
-- 本地模式：preserve_trx_transfer_artifact_mode=LOCAL_CARRIER
-- binlog_format=ROW

3.2 保存单个事务

START TRANSACTION;
UPDATE orders SET status = 'processing' WHERE id = 1001;
SET @maintenance_id = 'mw-20260713';

PREPARE SHUTDOWN PRESERVE TRANSACTION
  WITH TIMEOUT 3600
  WITH USER VARS;

命令成功后服务端请求 shutdown，原连接断开。不要期待 OK 包中出现 token。

3.3 重启后查询并恢复

-- 使用具备 PROCESS 权限的管理账号
SHOW PRESERVED TRANSACTIONS;

SELECT TOKEN, USER, HOST, STATE, EXPIRES_AT, BINLOG_STATE,
       BINLOG_CACHE_SIZE, TEMP_TABLE_STATE, LAST_ERROR
  FROM performance_schema.preserved_transactions;

-- 使用 token owner，或具备跨账号恢复权限的受控账号
RESUME PRESERVED TRANSACTION '0123456789abcdef0123456789abcdef';

-- 校验业务状态后，由客户端决定
COMMIT;
-- 或 ROLLBACK;

3.4 批量停机

SET GLOBAL preserve_trx_drain_mode = 'SOFT';
SET GLOBAL preserve_trx_batch_max_transactions = 256;

DRAIN TRANSACTIONS PRESERVE
  WITH TIMEOUT 1800
  WITH NO USER VARS;

即使没有目标事务，batch 命令也可以成功并继续请求 shutdown。恢复前先查询实际 token 数量，不要按 drain 前连接数推断。

4. SQL 语句与接口

4.1 语法总览

PREPARE SHUTDOWN PRESERVE TRANSACTION
  [WITH TIMEOUT seconds]
  [WITH USER VARS | WITH NO USER VARS];

DRAIN TRANSACTIONS PRESERVE
  [WITH TIMEOUT seconds]
  [WITH USER VARS | WITH NO USER VARS | NO USER VARS];

RESUME PRESERVED TRANSACTION 'token';

SHOW PRESERVED TRANSACTIONS;

WITH TIMEOUT 和用户变量子句可以交换顺序，但同类子句重复会在语法合并阶段拒绝。只有 batch 兼容不带 WITH 的 NO USER VARS。

4.2 PREPARE SHUTDOWN PRESERVE TRANSACTION

项目行为
目标当前连接上的显式活跃事务。
权限静态 SHUTDOWN。
超时没有子句时取当前 session 的 preserve_trx_default_timeout；显式值还受 min/max 约束。
成功响应普通 OK，不含 token；OK 成功交付后记录才转为 resumable，随后请求 shutdown。
实例影响为了建立可控停机边界，会收敛其他活跃事务；不要把它当作只影响当前连接的轻量命令。
失败边界durable point 前尽量保留原事务；越过 prepare/detach 后失败则 reattach、rollback 或记录可观察故障。

4.3 DRAIN TRANSACTIONS PRESERVE

项目行为
控制连接不能处于显式活跃事务中；需要 SHUTDOWN。
目标选择收集可保存的业务 session；目标必须可静默到达 idle/quiesced 状态并通过支持性检查。
SOFT先阻止新风险语句并等待 grace；到期后升级 HARD。
HARD立即 kill 其他活跃用户事务，等待其退出；被 kill 的事务不会生成 token。
返回值普通 OK，不返回 token 列表；成功后请求 shutdown。
清理失败若 batch rollback/cleanup 不能完整撤销，返回专用错误并要求先检查 P_S 和目标 session，不能盲目重试。
目标 session 的体验：drain 期间命中阻断条件的业务语句会收到 ER_PRESERVE_TRX_SESSION_DRAINED。该错误只说明 session 被 drain，不携带 token。

4.4 USER VARS 的准确语义

写法保存行为resume 对目标 session 的影响
不写任何 USER VARS 子句DEFAULT；不生成用户变量 payload。不导入，也不清空目标 session 现有用户变量。
WITH NO USER VARS显式 EXCLUDE；不生成 payload。与 DEFAULT 相同，不覆盖目标 session。
batch 的 NO USER VARS语法兼容写法，语义仍是 EXCLUDE。与 WITH NO USER VARS 完全相同。
WITH USER VARS为每个目标业务 session 导出其变量集合；不是导出 drain 控制连接的变量。导入 token 中的集合。即使保存时集合为空，也会记录“空集合 payload”，resume 时会清空目标 session 的现有用户变量。

支持的值族包括字符串、实数、整数和 decimal。非法 charset/collation、无法编码的值或损坏 payload 会 fail closed。

4.5 RESUME PRESERVED TRANSACTION

resume 会先验证 token、owner、动态权限、对象权限、binlog/GTID 模式、只读状态和目标 session，再依次恢复 session 状态、MDL、binlog cache、临时表、InnoDB transaction、read view、锁和 savepoint。只有整个激活过程成功后才消费 snapshot。

不要把 RESUME 当作幂等查询 它会认领并移动 token 状态。失败后先看 STATE、LAST_ERROR 和错误日志，确认 token 仍为 PRESERVED 再决定是否重试。

4.6 SHOW PRESERVED TRANSACTIONS

SHOW 与 performance_schema.preserved_transactions 使用同一份 registry snapshot、同一套 owner 可见性和 token 脱敏规则，输出同样的 29 列。查询会等待本次 startup recovery 完成；总开关关闭时返回空集合。

5. 本地保存与恢复原理

5.1 Preserve 的关键阶段

  1. 检查总开关、classic protocol、SHUTDOWN、显式事务和不支持上下文。
  2. 完成 binlog preflight，确认 ROW、GTID 状态和 cache 分类。
  3. 检查只允许 InnoDB 和有效 binlog participant，拒绝非事务表修改。
  4. 导出/物化 read view、record/table locks、MDL、savepoint、modified tables、可选用户变量和临时表信息。
  5. 生成 token 与内部 XID，持久化 XID provenance。
  6. 调用引擎/binlog prepare，detach THD 上的事务；这是最关键的 durable 边界。
  7. 写认证 snapshot 和外部对象，注册 durable record。
  8. 确认成功响应交付后把 token 标记为可恢复，并进入 shutdown。

5.2 Resume 的关键阶段

  1. 等待 startup recovery，按 token 找到可消费记录。
  2. 校验 owner、跨账号权限、sql_log_bin 特权、对象 ACL、只读和 binlog 模式。
  3. 把状态从 PRESERVED 原子认领到 RESUMING。
  4. 读取并验证 snapshot、sidecar、摘要、XID 和资源预算。
  5. 恢复 schema/session state、用户变量、GTID/binlog cache、MDL、临时表和 InnoDB transaction。
  6. 恢复 read view、锁和 savepoint，验证 attached transaction 可继续运行。
  7. 激活成功后清理 snapshot；失败则按阶段回退状态、rollback 或标记错误。

5.3 为什么不是 SQL 重放

恢复依赖的是 prepared transaction 和持久化语义对象，而不是重新执行历史语句。这样才能保留事务的 undo、锁、read view 和 binlog cache 边界，也意味着 snapshot 损坏、物理页不一致或 XID 不匹配时必须拒绝恢复。

6. Batch drain 与 warmcopy

Batch drain 是真实停机流程的主要入口。它把实例级收敛、多个目标事务的 phase 1 预处理、phase 2 封口和 shutdown 组织在一个控制流程里。

6.1 SOFT 与 HARD

SOFT 先等待业务语句自然收敛，在 preserve_trx_drain_grace_ms 到期后升级 HARD。HARD 会 kill 其他活跃用户事务，并最多等待 preserve_trx_drain_hard_timeout_ms。它提高停机可控性，但应用必须能承受被 kill 事务的回滚与重试。

6.2 Binlog warmcopy

phase 1 复制 transaction binlog cache 的稳定 prefix，并持续接收 mirror；phase 2 关闭 admission、等待 mirror 收敛、验证 truncate generation、复制受限 tail、封存摘要。它减少停机阻塞窗口，但不改变 preserve_trx_max_binlog_cache_bytes 和最终完整性检查。

6.3 Lock warmcopy

锁 warmcopy 与 binlog warmcopy 是两个独立开关。它在 phase 1 建立锁对象/journal，phase 2 只处理 dirty shards、MDL 描述符和 final fence。artifact 无效时，preserve_trx_lock_warmcopy_fallback_to_live_export=ON 可以整 target 回退 live export；OFF 则严格拒绝。

6.4 资源预算不是同一个数字

预算约束对象不能据此推断
snapshot/binlog/temp sidecar size单 token 持久化对象大小不等于堆内存占用。
memory budget/per-token leasePreserve 通用 heap lease不覆盖 mysqld 全部内存，也不等于外部 blob 字节。
warmcopy max total单 drain epoch 的 binlog warm artifact 总量不会预分配同等内存。
lock warmcopy memory/journal锁 artifact 内存保留和 journal不是所有锁系统内存的总上限。
transfer max inflight接收端一个 epoch 尚未 seal 的字节不等于已提交 spool 总磁盘量。

7. 启动恢复、超时与关闭策略

7.1 启动恢复

启动时先读取 XID provenance 和本地 artifact，清理 staging/taint 状态，更新恢复尝试 ledger，再并行恢复 snapshot 对应的 prepared transaction、MDL、read view 和锁。恢复完成后才向 SHOW/P_S 发布 registry snapshot。

普通启动恢复只处理本地 carrier；standby transfer spool 不会被普通目录扫描自动变成 SQL token，也不会自动完成 promotion adopt。

7.2 超时、宽限与回收

  • token 的 EXPIRES_AT 使用墙上时间，由 preserve timeout 决定。
  • 首次启动恢复遇到已经过期的 token，可应用 preserve_trx_recovery_grace_seconds 宽限。
  • 同一 token 的启动恢复次数达到 preserve_trx_recovery_max_count 后，不再无限尝试，进入 rollback/清理。
  • 运行期 reaper 对过期 token 认领 EXPIRED_ROLLBACK 并回滚；清理失败进入 EXPIRED_CLEANUP_FAILED。

7.3 崩溃恢复边界

本地 preserve artifact 与实际 InnoDB crash recovery 同时存在时，启动会拒绝继续。该特性要求受控、干净的 shutdown，不能把任意崩溃后的 redo recovery 与 preserved transaction 拼接起来。

7.4 总开关关闭时的历史工件策略

策略启动行为运维含义
FAIL_IF_PRESENT发现任何历史 Preserve artifact/XID provenance 就拒绝启动。默认且最严格，防止 OFF 路径无意绕过历史事务。
IGNORE不做特性恢复，保留文件给外部工具处理。OFF+IGNORE 下不保留 Preserve magic XID 保护；必须有明确的外部处置责任人。
RECOVER复用启动扫描处理本地 artifact，但 SQL preserve/drain/resume/transfer/promotion 仍关闭。不是“关闭总开关但仍可 SQL resume”。
ABANDON尝试可审计地 rollback/清理本地历史 snapshot、prepared trx 和 orphan。涉及 transfer/promotion marker 时仍需外部 HA 确认所有权。

8. 生产形态：备机传输与物理晋升

真实上线形态不是把本地 preserve/ 目录简单复制到另一台机器。它同时依赖两条数据面：物理复制保证 InnoDB 数据页/redo 到达备机，Preserve 传输保证事务 snapshot、binlog/锁对象、摘要和 epoch 事实到达备机。晋升时必须用物理栅栏证明两条数据面在同一个一致性边界汇合。

8.1 源端流程

  1. 以 preserve_trx_transfer_artifact_mode=STANDBY_TRANSFER_SAVE 启动，并配置唯一的 TCP 或 Unix socket 目标、目标 UUID、账号和凭据。
  2. batch drain 打开 transfer epoch，固定本 epoch 的 batching 参数。
  3. phase 1 按对象分帧发送 binlog/record-lock 数据；接收端按 range 幂等落盘并可以提前 prewarm。
  4. phase 2 封存事务最终元数据、对象摘要和 epoch 事实，等待接收端 commit ACK。
  5. 只有远端 commit 得到确认，源端才按该 carrier 语义完成 token 发布与 shutdown。

8.2 接收端流程

  1. 接收端必须以 preserve_trx_transfer_receiver_enable=ON 启动，并固定 allowed source UUID、target UUID 和凭据。
  2. 内部 classic command COM_PRESERVE_TRX_TRANSFER 校验动态权限、HMAC、source/target 身份和帧结构。
  3. 对象写入 .part/.ranges；这只是 staging，不代表 epoch committed。
  4. 最终元数据与摘要通过后写 epoch.fact、epoch.commit，再发布 .standby_pending projection。
  5. receiver 对对象和 prepared resource 做预热，状态通过 transfer receiver 指标、日志和磁盘 marker 观察。

8.3 晋升与严格 gate

仓库提供 production physical fence provider 注册点、strict adopt core、peer THD 解析和 promotion resume attach 接口；完整 HA 编排由外部系统负责。严格路径会校验 epoch commit、物理 apply fence、token generation/incarnation、对象摘要、intent lease 和目标 THD 身份。

preserved_trx_register_production_physical_fence_provider(...)
preserved_trx_adopt_prepared_epoch_for_physical_promotion(...)
preserved_trx_resolve_peer_thd(...)
preserved_trx_resume_adopted_for_promotion_on_thd(...)

严格 gate request 的 operation_deadline_us=0 时使用当前 preserve_trx_promotion_gate_timeout_ms 计算截止时间；worker_count 只能为 1..8。系统变量 preserve_trx_promotion_gate_workers 的 1..1024 范围属于旧 gate/default request budget，不能提高 strict physical gate 的硬上限。

仓库内没有完整的生产 fence provider 和 HA 调用编排；plugin/test_preserve_trx_promotion 是测试接入示例，不是生产 HA 实现。旧的 ready-cache/apply-barrier gate 与严格 physical gate 是两条不同路径，不能用前者的成功代替生产物理一致性证明。

8.4 传输安全

  • TCP 必须配置 CA/capath，使用 SSL_MODE_VERIFY_IDENTITY，连接后还会确认实际 cipher 非空。
  • Unix socket 路径不使用 TLS；目标必须在 TCP 与 socket 中二选一，不能同时配置或都不配置。
  • 凭据优先按 credential name 从复制通道凭据存储解析；也可使用受约束的 secret file。
  • secret file 以 no-follow 打开，必须是当前 euid 所有的普通文件，group/other 不得有权限。
  • HMAC/fingerprint 由 secret 与 target UUID 派生；ACK 也必须通过 HMAC 验证。
  • 接收端同时校验 allowed source UUID 和 target server UUID。

8.5 当前跨机限制

portable transfer 当前拒绝带非空临时表 manifest 的 token。本地模式可以支持受约束的用户临时表恢复，但不能据此推断临时表 sidecar 已支持跨主机迁移。

9. 权限、可见性与安全边界

操作最低要求额外检查
单事务 preserve静态 SHUTDOWN当前连接必须有显式事务，且上下文、引擎和对象形态受支持。
batch drain静态 SHUTDOWN控制连接不能有显式事务；每个目标独立检查。
resume 自己的 token(priv_user, priv_host) 与 owner 精确匹配仍复检 schema/table/routine/trigger/tablespace/modified table 权限。
跨账号 resume动态 RESUME_ANY_PRESERVED_TRANSACTION对 modified table 要求完整写权限；不绕过对象 ACL。
跨账号恢复 sql_log_bin=OFF token上述动态权限，另需 SUPER 或 SYSTEM_VARIABLES_ADMIN/SESSION_VARIABLES_ADMIN防止借恢复绕过 binlog 管理权限。

内部 transfer command动态 PRESERVE_TRX_TRANSFER_ADMIN还要求总开关和 receiver startup option；否则按 unknown command 隐藏。

token 在错误日志和审计事件中只记录脱敏值。不要把 token 输出到普通业务日志；完整 token 应由受控管理面读取和保管。

10. 参数详解

当前实现共有 64 个 preserve_trx_* 系统变量。参数不是越大越好：容量类参数决定准入边界，超时类参数决定失败窗口，warmcopy/并行类参数主要改变停机阶段的工作分布，transfer/promotion 参数则属于跨机身份和一致性协议。除明确标为 session、只读或启动期的项目外，其余为 global 动态变量；动态修改只影响后续操作，不会重写已经持久化的 artifact。

10.1 上线必审 Top 15

这里的 Top 15 按“配置错误后的生产影响”排序，不是使用频率榜，也不是建议优先调大的参数。上线评审必须为每一项写下取值依据、容量证据、失败处置和回退方式。

Top参数为什么必须先审上线决策与验收证据
1preserve_trx_enable决定整个实例是否进入 Preserve/Resume 能力域，也是所有 SQL、transfer 和 promotion 路径的总门。确认构建支持 snapshot、所有节点启动配置一致，并演练 ON/OFF 两种启动路径；不能把运行期 SET 当成切换开关。
2preserve_trx_off_artifact_policy总开关关闭但磁盘上仍有历史事务时，它决定实例拒绝启动、忽略、恢复还是放弃。生产默认应保持 FAIL_IF_PRESENT，其他策略必须有工件所有权、prepared transaction 和外部 HA 的书面处置流程。
3preserve_trx_dirsnapshot、binlog/temp sidecar、warm artifact、transfer spool 和 marker 共用这一持久化根目录。验收容量、inode、权限、磁盘故障告警和备份排除策略；容量模型必须覆盖峰值 batch，而不是只看单 token。
4preserve_trx_transfer_artifact_mode决定保存结果留在本地 carrier，还是发布到备机；选错模式会直接改变恢复入口和 HA 责任边界。本地维护使用 LOCAL_CARRIER；生产备机链路才使用 STANDBY_TRANSFER_SAVE，并完成 receiver、凭据、TLS/HMAC 和 promotion gate 联调。
5preserve_trx_drain_mode决定停机收敛是先等待业务退出，还是立即 kill 其他活跃用户事务。常规维护优先 SOFT；只有业务明确接受强制终止且客户端具备重试/回滚策略时才使用 HARD。
6preserve_trx_drain_grace_ms决定 SOFT 阶段给非目标事务和新风险语句留下多长收敛时间。依据业务长事务分位数和停机窗口设置；演练期间记录升级 HARD 的比例，不能仅按平均事务时长估算。
7preserve_trx_drain_hard_timeout_ms决定 HARD 阶段等待活跃事务真正退出的最后期限，超时将使 drain 失败。必须覆盖 kill 后的引擎清理和线程退出尾延迟，并为超时保留停止重试、保存现场的操作窗口。
8preserve_trx_max_total是实例本地 registry 的总 token 上限，直接限制一次维护可留下多少未决事务。按峰值 eligible 事务数、恢复并发和磁盘容量共同确定；与 per-user、batch 上限取共同约束。
9preserve_trx_batch_max_transactions限制单次 DRAIN 接受的目标数；设置过低会拒绝预期批次，设置过高会扩大 phase 2 和启动恢复压力。用真实锁规模、binlog cache 和 temp sidecar 分布做压力演练，不能只按连接数设置。
10preserve_trx_default_timeout客户端省略 WITH TIMEOUT 时决定 token 可恢复窗口，过短会在维护期间过期，过长会长期占用锁和 prepared transaction。至少覆盖停机、启动恢复、HA 决策和人工接管时间，并与 min/max timeout、reaper 和告警阈值对齐。
11preserve_trx_max_snapshot_bytes是单 token snapshot metadata 的硬上限；复杂锁、MDL、read view 和 session 状态会增加该对象。采集真实业务 snapshot 大小分位数并保留余量；达到上限属于准入失败，不能依赖 spill 绕过。
12preserve_trx_max_binlog_cache_bytes限制单事务 binlog cache sidecar，直接影响大事务是否可保存以及目录容量。与业务最大事务、binlog_cache_size 实际增长、single-phase 阈值和 warmcopy epoch 总量一起评估。
13preserve_trx_memory_budget_bytes是所有活跃 Preserve 操作共享的通用 heap 租约总预算；过小会触发 spill/拒绝，过大会与 mysqld 其他内存竞争。按并发 token 数、单 token 上限和压测峰值设定，同时监控 current/peak 与 spill 指标。
14preserve_trx_warmcopy_enable决定是否在 phase 1 前移 binlog cache 复制工作，是 batch 停机窗口的主要性能开关之一。上线前同时验证 warmcopy 成功、degraded/fallback 和关闭路径；开启不等于 phase 2 一定满足时延目标。
15preserve_trx_lock_warmcopy_enable决定是否在 drain 前移锁元数据导出；锁多事务的 phase 2 时延与失败面主要受它和 fallback 策略影响。使用 lock-heavy 业务压测，核对 artifact valid/fallback/strict reject、journal 和 dirty shard 指标后再定。
备机上线还有一组不可省略的身份与一致性参数 Top 15 是全场景优先级，不是备机配置清单。使用 STANDBY_TRANSFER_SAVE 时，还必须逐项审查 preserve_trx_transfer_receiver_enable、source/target UUID、host/port 或 socket、账号与 credential、inflight/commit timeout，以及三个 preserve_trx_promotion_gate_* 参数。缺少生产 physical fence provider 时，参数配齐也不能完成安全晋升。

10.2 参数联动与调参顺序

先确定语义和失败边界，再做容量与性能调优。推荐按下面的链路评审，避免只改一个“看起来相关”的变量。

  • 总开关与历史工件enable → off_artifact_policy → 本地 artifact/XID provenance 处置；先演练启动行为，再允许生产留下 token。
  • Token 准入有效批次上限同时受 max_total、每个 owner 的 max_pending_per_user 和 batch_max_transactions 约束。
  • 可恢复时间窗default/min/max_timeout 决定创建时的 EXPIRES_AT；recovery_grace_seconds 和 recovery_max_count 只处理启动恢复边界，不能替代合理 timeout。
  • 停机总窗口SOFT 场景至少包含 grace、HARD 收敛、phase 2 preserve 和 shutdown；任何单个 timeout 都不是完整维护窗口。
  • 单 token 与总资源snapshot/binlog/temp 是持久化对象上限，memory total/per-token 是 heap lease，warmcopy total 和 transfer inflight 又是不同预算，不能互相换算。
  • Binlog warmcopywarmcopy_enable 打开 phase 1；chunk、pending range/bytes、tail budget、close timeout 和 epoch total 共同决定能否在 phase 2 前收敛。
  • Lock warmcopyenable、memory/journal、dirty shards、MDL descriptors、seal threads 与 fallback 策略共同决定“直接使用、整 target 回退或严格拒绝”。
  • 备机与晋升artifact mode → receiver startup identity → endpoint/credential → inflight/commit → epoch/prewarm → promotion strict gate；任一步失败都不能跳过物理一致性证明。
上线调参方法 先记录默认值下的 P_S、SHOW STATUS、错误日志和磁盘峰值；再按单一假设调整一个参数组，覆盖成功、资源耗尽、超时、fallback 和重启恢复用例。动态参数的修改只用于后续操作，已有 token 仍按其持久化事实和创建时边界处理。

11. 用户使用场景

11.1 维护窗口保留一个长事务

适用于明确知道目标事务、能够接受实例收敛和关机的场景。设置足够的 timeout；若业务依赖 session 用户变量，必须显式写 WITH USER VARS。重启后先以 PROCESS 账号找 token，再用 owner 恢复。

11.2 批量保存多个空闲事务

使用 batch drain。先统计 eligible 事务数、锁规模、binlog cache 和目录空间，确认不超过 max total、per-user 和 batch 上限。SOFT 适合常规维护，HARD 只用于业务已接受强制收敛的停机窗口。

11.3 大 binlog cache 事务

同时评估单 token binlog sidecar 上限、single-phase 上限、warmcopy epoch 总量、tail budget、preserve 目录空间和 phase 1 带宽。扩大 warmcopy 总量主要增加磁盘与 I/O 容量，不代表等量堆内存。

11.4 锁很多或修改表很多的事务

检查 lock count、modified tables、scan pages 和 materialize timeout。lock warmcopy 能把大部分工作前移，但 unsupported family、final fence mismatch 或资源耗尽仍会 fallback/reject。只调大线程数不能绕过这些语义限制。

11.5 带用户临时表的本地事务

只使用受支持的 InnoDB 用户临时表形态，并验证 temp image、undo 和 manifest 都为 READY。native-adopted 路径允许继续受支持的 temp DML；旧 manifest 或无法证明 undo/ownership 的形态会 fail closed。上线前必须用与业务相同的 DDL、savepoint 和 statement rollback 模式验证。

11.6 物理备机快速晋升

使用 standby transfer，而不是拷贝本地目录。外部 HA 必须保存 epoch 严格身份、冻结/证明物理 apply、调用 strict adopt，再把 token 定向附着到受保护目标 THD。生产验收要同时检查 transfer commit、prewarm readiness、physical consistency mode 和真实 redo apply 标志。

12. 可观察性全集

Preserve/Resume 的状态分散在四个证据面。排障时不能只看其中一个：SQL/P_S 反映本地 registry，SHOW STATUS 反映过程与性能，日志/审计说明决策原因，磁盘 marker 说明持久化阶段和 HA 所有权。

当前唯一的专用关系视图是 performance_schema.preserved_transactions；没有对应的 INFORMATION_SCHEMA 或 sys schema 视图。SHOW PRESERVED TRANSACTIONS 是同一 registry snapshot 的语句封装。

12.6 指标判读规则

  • 微秒：*_us 一般为耗时或 steady-clock 时间点。带 monotonic 的值不是 Unix 时间，不能跨进程/重启直接比较。
  • 最近一次：phase2、SQL resume、startup recovery、promotion gate 中的部分变量会被下一次操作覆盖，采集系统需要按事件保存快照。
  • 累计：lock warmcopy、binlog attach I/O、receiver 多数计数从 mysqld 启动起累计；用速率或前后差值分析。
  • 当前值：memory current、staged token active 和 ready-cache 聚合是 gauge；不要对 gauge 做累加。
  • 直方图：p50/p95/p99/max 是进程内聚合或当前 attempt 聚合，具体以表中口径为准。
  • 状态码：两个 *_prewarm_last_status 使用 0..16 的 promotion adopt status；传输 API/日志中的 transfer status 使用另一套 0..6 枚举；strict physical gate 又是独立返回协议。

实现中的 Preserve 日志主要使用 PRESERVE: 前缀。应关注：

  • startup recovery begin/end、token 分类、orphan rollback 和各阶段耗时；
  • batch phase 2 指标与 phase2_slo_reason；
  • binlog/lock warmcopy fallback、resource limit、seal/fence mismatch；
  • transfer connect/send、manifest/object build、spool、ACK、prewarm 和 commit；
  • promotion prewarm、physical fence、attach intent、cleanup/taint；
  • RESUME PRESERVED TRANSACTION '****xxxx' failed: reason。

日志中的 token 只保留末四位；跨节点关联应优先使用 source UUID、epoch、generation/incarnation 和时间窗口。

12.9 审计事件

服务端通过 MYSQL_AUDIT_MESSAGE_INTERNAL 发出 category=mysqld、component=preserve_trx 的内部消息。主要事件：

事件字段/动作说明
preserved_transactionaction=preserve/recover/promotion-adopt/resume/promotion-resume/rollback；result=success/timeout/failure/expired带脱敏 token、结果和可选 reason。
preserved_transaction_controlaction=drain、result、target_count、token_count描述 batch 控制操作。

这些事件只有在部署了能够消费 internal message 的审计插件/组件时才会形成可查询或可检索记录；“代码发出事件”不等于默认已有审计表。

12.10 磁盘工件与 marker

preserve_trx_dir 默认为 <datadir>/preserve/。下面的文件名用于诊断持久化阶段，不是运维 API。

文件/目录含义判读边界
<token>.bin认证 snapshot metadata。单独存在不证明外部对象或 prepared trx 完整。
<token>.binlog_cachetransaction binlog cache sidecar。只有 LOGGED_WITH_CACHE 需要。
<token>.blob.<name>通用 external blob，例如 record locks；可能位于 blob_shards/。要与 snapshot 摘要匹配。
<token>.tempts.<space>.image/.undo用户临时表 image 和 no-redo undo sidecar。必须与 temp manifest 和 ownership 一致。
<warmcopy_id>.<blob>.warm.<epoch>、.descwarmcopy artifact 与 descriptor。staging/未封存文件不能被当作最终对象。
*.tmp原子发布前 staging。启动时可能清理；存在说明上次流程未完成。
<token>.tainted事务/工件进入不可安全自动消费的 taint 状态。不要手工移除 marker 后强行 resume。
<token>.consume_state消费状态记录。用于避免重复或不完整消费。
<token>.standby_pendingreceiver 发布的 standby projection。不是普通本地 SQL registry 行。
<epoch>.promotion_adopted/.promotion_abandoned晋升采用/放弃的终态摘要。与 intent 和外部 HA 状态联合判断。
<id>.promotion_intent严格 attach/adopt 所有权 journal；attach id 可为 attach-<sha256>。存在时说明操作可能处于租约/恢复窗口。
.recovery_attempt_ledger启动恢复尝试次数。与 P_S RECOVERED_COUNT 配合。
.xid_provenancePreserve 内部 XID 来源和保护信息。OFF 策略和 orphan 处理的重要依据。
.transfer/<epoch>/receiver.frames接收帧日志。不能代替 epoch commit。
.transfer/<epoch>/epoch.fact持久化 epoch 事实。仍需 commit marker。
.transfer/<epoch>/epoch.commit接收端 epoch commit marker。表明语义面提交，不等于物理晋升 fence 已满足。
.transfer/<epoch>/<token>/<object>.part/.ranges对象 staging 和已接收 range。只代表可续传/幂等落盘进度。
禁止把文件系统当控制接口 不要通过手工删除、改名或复制 marker 来“修复” token。文件存在仅说明某个持久化阶段发生过；是否可恢复必须结合 registry、epoch commit、prepared transaction、摘要、promotion intent 和外部 HA 状态判断。

12.11 当前观测空白

  • 没有专用 SQL/P_S 视图展示 receiver spool、epoch commit、strict prepared-token registry、promotion/attach intent 或当前 drain manager/epoch ownership。
  • 普通 P_S 表看不到 standby-pending token，也不会扫描 .transfer/。
  • 当前没有 Preserve/Resume 专用的 Performance Schema stage/wait 或 PROCESSLIST 状态列；通用 thread/processlist 只能辅助看仍存活的连接，不能代替 durable token/epoch 状态。
  • 四个内部 getter 当前未注册到 SHOW STATUS：preserve_trx_transfer_phase2_snapshot_bundle_bytes_status()、preserve_trx_transfer_phase2_snapshot_bundle_count_status()、preserve_trx_transfer_phase2_final_metadata_frame_count_status()、preserve_trx_transfer_phase2_final_metadata_encoded_bytes_status()。
  • LAST_ERROR 只覆盖本地 registry 能记录的错误；receiver/strict gate 错误可能只在日志、status 和 marker 中出现。
  • 生产 HA 必须自行持久化 source UUID、epoch、token generation/incarnation、physical fence proof 和调用结果，仓库不提供统一的运维视图。

13. 限制与注意事项

13.1 通用不支持上下文

  • 非 classic protocol；initialize/bootstrap/upgrade thread；innodb_force_recovery > 0。
  • 复制 SQL/applier thread、Group Replication 运行中，或实例存在已配置 replica channel。
  • XA 状态不是 XA_NOTR；DD update statement；子语句或 stored routine runtime。
  • global read lock、instance backup lock、LOCK TABLES、user-level locks。
  • open HANDLER table、open server-side cursor。
  • 不受支持的用户临时表 session 状态。

13.2 事务内容限制

  • 修改非事务表会拒绝；read-write handlerton 只允许 InnoDB 和有效 binlog participant。
  • binlog_format 必须为 ROW。
  • 锁数、modified table、scan page、snapshot、binlog/temp sidecar 和时间预算都可能导致 fail closed。
  • 恢复环境不能是 read_only/super_read_only，不能已有多语句事务，且 binlog/GTID 模式必须兼容。
  • 普通 SQL RESUME 不能消费 ADOPTED_FOR_PROMOTION。

13.3 操作注意事项

  • 单事务 preserve 也会做实例级 drain；在生产执行前先通知业务并停止新流量。
  • batch 可在零目标时成功并关机；成功不等于有 token。
  • 没有 PROCESS 时拿不到完整 token；提前确认恢复账号与管理面。
  • 默认/NO USER VARS 不会清空恢复 session 的既有变量；WITH USER VARS 的空集合会清空。
  • fallback 保证兼容性，不保证 phase 2 性能目标。
  • 调大容量前同时检查 datadir 空间、inode、I/O、启动恢复时间和接收端 inflight。
  • 物理备机路径必须有外部 fence provider 和 HA 编排；测试插件不能直接上线。

14. 错误与排障

错误/症状含义优先检查建议动作
ER_PRESERVE_TRX_DISABLED总开关关闭。启动参数和 OFF artifact policy。先确认历史 artifact 处置策略，再以正确启动配置重启。
ER_PRESERVE_TRX_INVALID_STATE当前 session/事务或 token 状态不允许该操作。显式事务、目标 session、P_S STATE。不要并发 resume；按状态恢复或清理。
ER_PRESERVE_TRX_UNSUPPORTED上下文、对象、引擎或 sidecar 形态不支持。复制/XA/锁/临时表/binlog/DDL 边界。消除不支持状态；调大容量不能解决 unsupported family。
ER_PRESERVE_TRX_DRAIN_TIMEOUTHARD drain 未在截止时间内收敛。活跃事务、kill 是否生效、hard timeout。查 processlist 和日志，修复阻塞源后重新规划停机。
ER_PRESERVE_TRX_BATCH_CLEANUP_FAILED失败后的 batch cleanup 不完整。P_S、目标 session、taint/consume marker。保留现场，先确认所有权和状态；禁止立即重复 drain。
ER_PRESERVE_TRX_NOT_FOUNDtoken 不存在、已消费、已过期清理或不在本地 registry。token 是否脱敏、owner、transfer/standby 路径。用 PROCESS 查询完整 token；跨机走 HA registry。
ER_PRESERVE_TRX_ACCESS_DENIEDowner、动态权限或对象 ACL 不满足。priv_user/host、resume-any、表/库/例程权限。只授予所需权限，不通过 SUPER 粗暴绕过对象检查。
ER_PRESERVE_TRX_BINLOG_MODE_MISMATCH当前 binlog/GTID 环境与 snapshot 不兼容。ROW、global/session log_bin、GTID_NEXT。恢复到兼容环境，勿修改 snapshot。
ER_PRESERVE_TRX_CORRUPT_SNAPSHOTsnapshot/sidecar/摘要/XID 校验失败。磁盘、文件权限、日志、taint、transfer ACK。停止重试并保留文件，按恢复/回滚 runbook 处理。
ER_PRESERVE_TRX_SESSION_DRAINED业务 session 在 drain 期间被阻止继续风险语句。当前 drain epoch 和目标 session。客户端停止继续发 SQL，等待停机或按业务重连策略处理。
重启后 P_S 无记录可能未做本地恢复，或 token 属于 transfer standby。总开关、OFF policy、startup logs、.transfer/。区分本地 carrier 与 transfer；不要靠目录文件猜状态。
晋升 gate 失败ready cache、epoch、物理 fence、摘要或 lease 不满足。status code、physical mode、real redo apply、intent marker。按状态码修复前置条件，不能跳过 strict gate。

14.1 排障顺序

  1. 记录原始 SQL 错误和时间，不要先重试。
  2. 查询 P_S/SHOW，保存 29 列快照；没有 PROCESS 时由管理账号补查完整 token。
  3. 采集对应前缀的 SHOW STATUS，并标记 mysqld 启动时间，避免混淆累计与最近一次值。
  4. 按 token 末四位、epoch、source UUID 和时间窗口检索错误日志/审计。
  5. 只读检查 marker 与文件权限/大小；不要改名、删除或复制。
  6. 跨机问题补充外部 HA 的 physical fence、epoch 和 strict gate 调用记录。
  7. 确认 token 所有权和当前状态后，再决定 resume、rollback、abandon 或重做停机。

15. 运维检查清单

15.1 停机前

  • 确认总开关、carrier mode、ROW binlog。
  • 确认恢复账号具备 PROCESS，业务 owner 可用。
  • 统计 eligible/active 事务及 owner 分布。
  • 估算锁、modified tables、binlog/temp sidecar。
  • 检查 preserve 目录空间、inode 和 I/O。
  • 确认 timeout、recovery grace 和业务窗口。
  • 决定 USER VARS 策略并记录。
  • 决定 SOFT/HARD 及应用重试策略。
  • 传输模式确认 endpoint、TLS/secret、UUID。
  • 保存基线 status 与 mysqld 启动时间。

15.2 命令成功后与关机前后

  • 确认控制命令收到 OK，而非假定收到 token。
  • 确认 mysqld 按预期 shutdown。
  • 保存 phase2、warmcopy、transfer 指标快照。
  • 查日志中 token count、SLO reason、ACK。
  • 传输模式确认 epoch commit 与 receiver readiness。
  • 不得手工搬运本地 artifact 代替 transfer。

15.3 重启或晋升后

  • 确认 startup recovery 完成且 error=0。
  • 用 PROCESS 查询完整 token 与状态。
  • 核对 token 数、owner、到期时间和 LAST_ERROR。
  • 先恢复一个低风险 token 验证链路。
  • resume 后验证业务数据与 session 状态。
  • 明确 COMMIT/ROLLBACK 责任方，避免悬挂。
  • 晋升模式确认 physical mode=3 且 real redo apply=1。
  • 归档 status、日志、审计和 HA 调用结果。
