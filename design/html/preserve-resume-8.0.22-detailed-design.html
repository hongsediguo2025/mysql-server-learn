1. 事实源与术语

本文以当前仓库源码和现有设计文档为事实源。核心入口包括 sql/sql_yacc.yy、sql/sql_parse.cc、sql/preserve_trx.cc、sql/preserve_trx_drain.cc、sql/preserve_trx_bundle.*、sql/preserve_trx_carrier*、sql/binlog_warmcopy.*、sql/preserve_trx_lock_warmcopy.*、storage/innobase/lock/lock0preserve.cc、storage/innobase/lock/lock0warmcopy.cc、storage/innobase/trx/trx0preserve.cc、storage/innobase/trx/trx0temp_preserve.cc、storage/innobase/read/read0read.cc、sql/mdl.*、sql/handler.cc、sql/xa.cc、storage/perfschema/table_preserved_transactions.*。

术语含义
preserve把一个未提交显式事务转换为 durable token 和 snapshot，使它可以跨重启恢复。
resume用 token 在新连接中重新绑定 preserved transaction，并继续提交、回滚或执行后续 SQL；带用户临时表 no-redo undo sidecar 且已经 native-adopted 的事务，恢复后也可以继续执行受支持的用户临时表 DML。旧 manifest 或 restored-only 路径仍只能读、COMMIT 或 ROLLBACK。
drain停机前收敛实例中的目标事务，批量执行 preserve。
snapshotdurable metadata 文件，记录 token、账号、binlog、锁、read view、savepoint、临时表 manifest 等恢复所需语义。
sidecar大对象外置文件，例如 binlog cache、用户临时表 image、no-redo undo、warm external blob。
warmcopy在 drain 第一阶段提前复制或镜像大对象，让第二阶段只处理 bounded tail 和一致性校验。
durable point事务已经 prepare/detach 或 snapshot 可能存在后，失败处理必须避免丢失所有权。

2. 总体架构

Preserve/Resume 是 SQL 层、binlog、InnoDB、P_S、文件 carrier 和资源预算共同组成的内核能力。它不只是 XA 包装：XA prepare 只能保存存储引擎事务状态，而 Preserve/Resume 还必须恢复 SQL session 语义、binlog cache、MDL、锁、read view、savepoint、临时表与权限边界。

2.1 分层职责

SQL Surface

语法、命令分发、权限、drain gate、协议边界和 token delivery。

Preserve Kernel

单事务 preserve 的核心状态转换，负责 preflight、prepare、detach、snapshot write 和错误收敛。

Bundle/Carrier

定义 snapshot 格式、HMAC/CRC、外部 blob 描述符、文件写入、删除、taint 和 listing。

InnoDB Adapter

导出/导入 read view、savepoint、record/table/predicate locks、临时表物理 sidecar。

Warmcopy

在 batch drain phase 1 提前复制 binlog cache 或镜像锁信息，减少 phase 2 阻塞窗口。

Observability

P_S 表、SHOW、status counters、错误原因和 release/NFR 报告。

3. 状态机与生命周期

Preserve/Resume 的核心状态机围绕 token、InnoDB trx、snapshot 文件和内存 record 展开。状态转换必须 fail closed：不能把一个语义不完整的 token 标成可恢复，也不能在 durable point 后丢掉 prepared transaction 的所有权。

4. 单事务 Preserve

单事务 preserve 作用于当前连接上的显式事务。它在命令成功响应后触发 shutdown，token 在重启后可用于 resume。关键原则是：prepare 前失败应尽量保持原事务仍在 session；prepare/detach 后失败必须通过 reattach、rollback、taint 或 observable record 收敛。

用户入口命令包括 PREPARE SHUTDOWN PRESERVE TRANSACTION、DRAIN TRANSACTIONS PRESERVE、RESUME PRESERVED TRANSACTION 和 SHOW PRESERVED TRANSACTIONS；语法与操作细节在用户手册中完整列出。

4.1 Preserve 前置检查

  • 全局开关 preserve_trx_enable 必须为 ON。
  • 执行用户需要 SHUTDOWN 权限。
  • 当前连接必须处于显式活跃事务，不能是复制线程、升级路径、force recovery、标准 XA 活跃状态或不支持的协议上下文。
  • 事务不能包含非事务表修改，也不能包含 InnoDB/binlog 之外的 read-write handlerton 参与者。
  • 对象权限、MDL、read view、savepoint、锁、binlog cache、临时表均必须能导出并通过预算限制。

4.2 Durable Point 与失败收敛

在 ha_prepare_low(thd, true) 前，失败一般可以返回错误并保留原连接事务。进入 prepare/detach/snapshot write 后，失败处理不能简单返回：因为 prepared transaction、snapshot 文件或 sidecar 可能已经存在。当前实现通过 cleanup lambda、taint marker、observable record 和 rollback-by-token 保留可审计路径。

5. Batch Drain Preserve

Batch drain 用于停机前批量保存目标事务。它比单事务 preserve 多出全局 gate、target 分类、SOFT/HARD drain、warmcopy phase 1 和 participant cleanup。

5.1 Phase 2 约 1 秒目标

当前 full warmcopy-only NFR 证据显示大锁数场景仍可能达到分钟级阻塞，原因是大 payload 生产、编码、写入和 per-target preserve 仍集中在 phase 2。目标架构必须把 O(lock count) 的扫描、排序、编码、checksum、外部 artifact 写入移到 phase 1，并在 phase 2 只做 bounded tail、final fence 和 descriptor adopt。超过 1 秒是性能 SLO miss，不能改变功能正确性。

6. Resume 与 Startup Recovery

Resume 从 durable snapshot 中恢复语义，并把 claimed transaction 重新绑定到当前 THD。Startup recovery 只在 mysqld 启动且 preserve_trx_enable=ON 时扫描 preserve 目录，导入有效 token，回滚过期或不可恢复 token，清理 staging/orphan 文件；实例以 --preserve-trx-enable=OFF 启动时不会扫描，运行中再 SET GLOBAL preserve_trx_enable=ON 也不会补扫既有 snapshot。

7. Snapshot、Sidecar 与资源预算

Snapshot metadata 是恢复语义的索引；大对象不应无界塞入内存或主 snapshot。当前实现已有 binlog cache sidecar、temp table sidecar、warm external blob、lock warmcopy spill。phase 2 1s 目标要求 lock artifact 进一步 descriptor 化，避免 phase 2 materialize 大 payload。

8. 锁、MDL、Read View、Savepoint 与临时表

这些对象共同决定事务恢复后的可见性、冲突行为和提交语义。任何一个对象不能导出或不能验证，都必须 fail closed 或按 per-target all-or-live fallback 回退。

本文中的锁对象包括 record locks、table locks、predicate locks、AUTO_INC locks、implicit locks、MDL tickets、read view、savepoint 和 temporary table 相关恢复对象。

对象当前处理逻辑限制
record locks导出显式 record/predicate payload；lock warmcopy 目标中 record payload 可来自 sealed store。R-tree/spatial predicate 不做 warmcopy 优化；implicit lock materialization 受扫描和数量预算限制。
table / AUTO_INC locks导出 table lock payload，并与 record lock 共用锁数量预算。后续 1s fast path 要求 table family 也进入 phase 1 mirror。
MDL导出 transaction-duration MDL descriptors，resume 前做权限复检。不支持 session/global 状态 preserve；LOCK TABLES、GET_LOCK、global read lock、backup lock 不纳入当前 v1。
read view导出/导入 InnoDB MVCC read view。需要确保 purge/read view 状态可恢复，失败则拒绝或保留 token。
savepoint保存 SQL savepoint 与 InnoDB savepoint payload。ROLLBACK TO SAVEPOINT 会影响锁和 MDL ordinal，warmcopy 目标需要 fence。
用户临时表支持受约束的 InnoDB 用户临时表 image、DD/dict binding、fil space adoption、no-redo undo sidecar reconnect 和 native-owned undo adoption。native-adopted 路径允许恢复后继续受支持的临时表 DML；旧 manifest/restored-only、缺失/损坏 sidecar、DDL/metadata/savepoint/statement rollback 边界仍必须拒绝。

9. 约束、失败处理与当前限制

  • 总开关：preserve_trx_enable=OFF 时 preserve/drain/resume 拒绝；文档不应暗示关闭后仍执行特性流程。
  • 安全原则：无法完整导出或验证事务语义时 fail closed。
  • 权限原则：resume 重新检查 token 所属权和对象权限；跨账号 resume 需要 RESUME_ANY_PRESERVED_TRANSACTION。
  • binlog 原则：binlog open、session sql_log_bin、GTID state 必须与 snapshot 兼容。
  • 锁原则：不混用不同时间点的 required lock family payload。
  • 临时表原则：仅支持当前实现可证明完整捕获的用户 InnoDB 临时表形态。
  • 复制集群：当前代码没有完成跨机器 artifact 传输和备机自动 resume 编排；这是后续接入方案，不是当前功能。
