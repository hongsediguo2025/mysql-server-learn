Transfer Phase 2、4020 挂起与 Tx→Ty 事务续作对接指南

本文说明代理节点如何只依赖 ER_PRESERVE_TRX_SESSION_DRAINED (4020) 挂起尚未执行的请求，并在 HA 完成目标节点升主和事务接管后，将该请求准确地重放到 Ty 上。 文档同时标出当前源码已经具备的行为、尚缺的响应完成屏障，以及最小化的内核补强范围。

代码基线：302ae0940a58040ef35c0a0d0f6a289eb1708cc7 · 生成日期：2026-07-16 · 范围：standby transfer 在线升主预埋，不讨论本地 startup resume

挂起触发器只认错误码 4020
事务标识token = uint64_t(Tx)
成功续作HA attach Tx→Ty 后重放原请求
回撤续作RESET 成功后在原 Tx 重放

1. 对接结论

代理、HA 与 mysqld 的职责可以压缩成三个简单合同，不需要把 HA 状态机或代理协议状态放进 Preserve 内核。

mysqld

Source 将事务 preserve 成功后，把 Tx 会话置为 PRESERVED_DRAINED。 之后读取到的新命令不执行，统一返回 4020。

Proxy

收到 4020 后不向客户端返回错误，保存原始请求并停止向 source 继续下发； 后续客户端请求按连接顺序排队。

HA

HA 决定最终走升主还是 RESET。升主成功后提供 Tx→Ty 接管结果； RESET 成功后通知代理原 source 已恢复；Preserve 接管放弃时明确结束续作。

核心流程 source 正常执行的请求返回正常结果；source 明确返回 4020 的请求保证未执行，由代理恰好重放一次。 HA 升主成功则在 Ty 上重放，RESET 成功则在原 Tx 上重放。
不能把“连接断开”当成 4020 若代理没有收到完整的正常响应，也没有收到完整的 4020，而只看到网络断开，则请求结果不确定。 代理不得盲目重放。当前源码还缺一个在 COMMIT_EPOCH 前关闭命令准入并等待响应完成的 batch drained response fence，用于关闭 source 已读取请求的本地响应竞态。

2. 场景与边界

本文只描述 transfer 模式下的计划内物理备机升主对接。receiver 在线接收、保存和 prewarm； 真正升主由后续物理备机项目的 HA 流程触发。

本文覆盖

  • source phase2 对业务命令的处理。
  • 4020 的代理挂起合同。
  • 文本协议和二进制 prepared statement。
  • HA 升主后 Tx→Ty attach 与请求重放。
  • RESET DRAIN 后在原 source 上继续。
  • FINAL_ACK 后 source 与 receiver 的责任边界。

本文不覆盖

  • 本地 preserve → shutdown → startup resume。
  • receiver crash 后恢复 transfer epoch。
  • 真实物理 redo apply、authority 或 write-enable 实现。
  • 由 source 触发 target promotion。
  • 把代理 PS catalog、请求队列或 peerid 数据存入 mysqld。
  • 分布式两阶段提交或 source/target 双向回滚协议。
receiver 是在线、进程内候选 receiver 重启后 transfer epoch 失效，残留临时文件应清理；它不是本地 startup carrier。 因而代理续作也只针对当前 target mysqld 进程和当前 HA promotion attempt。

5. Phase 2 命令边界

source 对 phase2 周围命令的处理不是“所有命令直接报错”，而是按命令被内核看到的时间点分成三类。

命令时点source 行为代理行为
命令包已被 get_command() 读取，并在关闭边界前成为 inflight 允许该命令完成，返回正常 OK、结果集或业务错误；之后会话再进入 quiesce。 按普通结果处理，不得重放。
命令在 WARMCOPY_CLOSING/BATCH_DRAINING 中尝试创建事务或锁，但事务尚未 preserve 可能返回 ER_PRESERVE_TRX_UNSUPPORTED (4013)。 4013 不是事务续作信号，不得作为挂起重放触发器。
事务已 preserve，会话已是 PRESERVED_DRAINED 读取命令包，但不执行命令，返回 4020。 隐藏 4020，挂起原请求，停止向 source 继续发送。 
source Tx command boundary

packet read before closing gate
    -> mark inflight
    -> command executes
    -> normal response
    -> Tx reaches idle boundary and quiesces

packet read after Tx == PRESERVED_DRAINED
    -> reject before dispatch
    -> ER_PRESERVE_TRX_SESSION_DRAINED (4020)
    -> command body is not executed

mysql-test/suite/preserve_trx/t/batch_drain_packet_before_dispatch.test 覆盖第一类边界；batch_drain_target_command_blocked.test 覆盖命令在 quiesce 期间等待、随后以 4020 返回的行为。

6. 4020 精确定义

错误名
ER_PRESERVE_TRX_SESSION_DRAINED
错误号
4020
SQLSTATE
HY000
服务端消息
This session's transaction has been preserved by DRAIN TRANSACTIONS PRESERVE
代理可依赖的语义 对产生该 4020 的命令包，mysqld 已经消费协议请求，但没有执行该命令的 SQL/协议主体； 原事务已经从 Tx 分离并由 Preserve 路径持有。因此该请求可以在终局节点上重放一次。
4020 不等于 target 已接受 PRESERVED_DRAINED 也可能用于 unresolved detach/cleanup failure 的可见隔离。 因此 4020 只建立“source 上未执行”的请求边界，不表达 FINAL_ACK、READY、promotion authority 或 attach 成功。 代理必须等待 HA 的 promotion、RESET 或 continuation-abandoned 终局。
错误/事件是否挂起是否允许自动重放说明
4020 是 HA 给出终局后是 唯一的 Preserve 事务续作挂起触发器。
4013 ER_PRESERVE_TRX_UNSUPPORTED 否 否 用途广泛，可能表示资格、上下文或 drain gate 不支持，不能推导“请求未执行且事务已转移”。
4014 ER_PRESERVE_TRX_DRAIN_TIMEOUT 否 否 主要是 drain owner/control-plane 失败。
4015 ER_PRESERVE_TRX_BATCH_CLEANUP_FAILED 否 否 需要 HA 检查 source 状态，不能由业务代理自行续作。
网络断开、2013、EOF，未收到完整响应 等待 HA 判定 不得盲目重放 请求可能未执行、已执行但响应丢失，或只写入部分结果。

错误文本定义在 share/messages_to_clients.txt:9475； 当前 debug/release 生成头均确认 ER_PRESERVE_TRX_SESSION_DRAINED = 4020。

7. 代理状态机

每条用户逻辑连接维护一个很小的状态机即可。进入挂起态不需要 HA 预先通知，只由 source 返回 4020 触发。

ACTIVE_SOURCE → REQUEST_IN_FLIGHT → SUSPENDED_4020 → WAIT_HA_TERMINAL → REPLAYING | TERMINAL_FAILED
代理状态可向 source 发送可向 target 发送客户端可见行为
ACTIVE_SOURCE 是 否 正常转发。
REQUEST_IN_FLIGHT 同一后端不得再发第二个 response-bearing 请求 否 等待完整响应；long-data 分片只能作为紧随 execute 的 compound request 组成部分。
SUSPENDED_4020 否 否 不返回 4020；保存触发请求，后续前端请求排队。
WAIT_HA_TERMINAL 否 否 等待 promotion attach 成功或 RESET 成功。
REPLAYING_SOURCE 仅重放队列 否 RESET 分支；先重放 4020 请求，再按序释放队列。
REPLAYING_TARGET 否 仅在 attach 成功后 promotion 分支；先重放 4020 请求，再按序释放队列。
AMBIGUOUS_DISCONNECT 否 否 没有 4020 证据，不自动执行；由 HA/上层异常策略处理。
TERMINAL_FAILED 否 否 HA 已放弃 Preserve 续作；结束逻辑事务/连接，不阻塞普通升主。

7.1 必须保持的顺序规则

  1. 每个 source backend connection 同时最多一个 response-bearing 请求在途。
  2. COM_STMT_SEND_LONG_DATA... 与紧随其后的 COM_STMT_EXECUTE 视为一个 compound request，不允许夹入其他命令。
  3. 收到 4020 后立即停止向该 source connection 发送任何新协议命令。
  4. 原始 4020 请求排在队首；promotion 或 RESET 后必须先重放它。
  5. 只有队首请求获得完整结果后，才释放后续排队请求。
  6. 不得把同一请求同时发往 Tx 和 Ty。
“完全依赖 4020”的准确含义 4020 是进入挂起态的唯一触发器，不要求 HA 在 phase2 前通知每条代理连接。 但挂起后的终局仍必须由 HA 告知：target attach 成功、source RESET 成功，或 Preserve continuation 已放弃。

9. 二进制 Prepared Statement 续作

当前 MTR 已证明：事务 preserve 后，已有 prepared statement 的 COM_STMT_EXECUTE 返回错误码 4020，随后 COM_PING 也返回 4020。测试位于 mysql-test/suite/preserve_trx/t/batch_drain_drained_session_binary_ps_blocked.test。

backend statement id 不能跨 mysqld 使用 source 上的 statement id 只在 Tx 所属 mysqld 进程内有效。升主后不能把原 COM_STMT_EXECUTE(stmt_id=source_id) 原样发给 Ty。 PS 迁移必须由代理维护虚拟 statement catalog。

9.1 代理必须保存的 PS 信息

  • 客户端可见 statement id 与 source/target backend statement id 的映射。
  • 原始 SQL 文本和 prepare 时的数据库、字符集等必要会话上下文。
  • execute 参数类型、NULL bitmap、值和游标标志。
  • COM_STMT_SEND_LONG_DATA 的全部分片内容，直到对应 execute 得到确定结果。
  • statement close/reset 状态，防止已关闭语句被重建。

9.2 Existing PS execute 的 promotion 重放

1. Tx 上 COM_STMT_EXECUTE(source_stmt_id) -> ERR 4020
2. Proxy 挂起 execute，保存参数和 long-data
3. HA 完成 token Tx -> Ty attach
4. Proxy 在 Ty 上 COM_STMT_PREPARE(original_sql)
5. Proxy 记录 target_stmt_id
6. Proxy 按原顺序重发 COM_STMT_SEND_LONG_DATA(target_stmt_id, ...)
7. Proxy 发送 COM_STMT_EXECUTE(target_stmt_id, original_params)
8. Proxy 将结果转回客户端，并切换 stmt-id 映射

9.3 各 PS 命令处理

协议命令4020/迁移处理对接要求
COM_STMT_PREPARE 若收到 4020，挂起 prepare；终局节点上重新 prepare。 客户端 stmt id 必须由代理虚拟化，不能暴露 backend id 的迁移。
COM_STMT_EXECUTE 收到 4020 后挂起；attach 后 reprepare + execute。 保存参数类型和值；只重放一次。
COM_STMT_SEND_LONG_DATA 协议本身不返回响应，不能把每个分片当成独立的 4020 请求。 代理必须缓存每个分片，并与 execute 组成连续 compound request；最终 execute 确定前不能丢弃。
COM_STMT_CLOSE 协议本身无响应，不作为挂起业务请求。 更新代理 catalog；终局节点不重建已关闭语句。drained gate 不应向该命令发送违背协议的 ERR packet。
COM_STMT_RESET 按有响应命令处理；必要时在终局 backend 映射上执行。 同时清理代理缓存的 long-data。
COM_STMT_FETCH 当前不支持跨节点 cursor 续作。 Preserve 资格检查已拒绝 open server-side cursor，见 sql/preserve_trx.cc:5083。
mysqld 只恢复事务，不迁移代理协议对象 binlog cache、MDL、InnoDB trx、锁、会话事务属性等由 Preserve 内核恢复； prepared statement catalog、backend stmt id 和客户端请求队列仍属于代理。

9.4 当前无响应命令缺口

当前 do_command() 在 get_command() 后对所有 server command 统一调用 preserved_trx_reject_if_batch_session_drained()。 该早期路径会直接 send_statement_status()。但正常 dispatch 对 COM_STMT_SEND_LONG_DATA 和 COM_STMT_CLOSE 会调用 Diagnostics_area::disable_status()，明确保持无响应协议语义， 见 sql/sql_parse.cc:1751-1759 和 1782-1787。

因此 binary PS 目前只证明了 execute/ping 被 4020 拦截，尚未证明完整协议闭环 后续最小修正应按 command 类型处理：response-bearing command 返回 4020； COM_STMT_SEND_LONG_DATA 在 drained 后不再写入 backend PS buffer、不发送 ERR， 只标记一个有 deadline 的 drained_ps_compound_pending； 代理必须紧接着发送 COM_STMT_EXECUTE，由 execute 获得 4020 并关闭该 compound； COM_STMT_CLOSE 可继续执行其无响应 close 语义，COM_QUIT 保持关闭语义。 不应向无响应命令注入一个客户端不会读取的 ERR packet。

9.5 Long-data 的 RESET 重放

部分 long-data 分片可能在 Tx 进入 PRESERVED_DRAINED 前已经写入 source 的 prepared statement buffer， 其余分片则可能在 drained 后被丢弃。代理无法仅凭 4020 判断 source 已接收了多少分片。 因此 RESET 分支不能直接追加式重发。 mysqld_stmt_reset() 会关闭 cursor 并调用 reset_stmt_params() 清除 mysqld_stmt_send_long_data() 写入的参数，见 sql/sql_prepare.cc:1984-2016。 

RESET success, replay a hung long-data execute on original Tx:
  1. COM_STMT_RESET(source_stmt_id)   // clear any partially accepted long-data
  2. resend every cached COM_STMT_SEND_LONG_DATA chunk in original order
  3. COM_STMT_EXECUTE(source_stmt_id, original_params)

promotion success on Ty:
  1. COM_STMT_PREPARE(original_sql)   // clean target statement
  2. resend every cached long-data chunk
  3. COM_STMT_EXECUTE(target_stmt_id, original_params)

10. HA 升主与 Tx→Ty 接管

当前仓库没有真实物理备机 HA 流程，但已经预埋了一部分“受保护 Ty + promotion attach/resume”内核能力。 后续物理备机项目应从 HA 内部入口调用，而不是由 source classic session 触发。

1. HA 选主target 获得 promotion authority，满足 apply/fence 条件
2. 准备 Ty建立或定位空闲、无事务、受保护的 target THD
3. peerid 解析用 token Tx 找到 peerid(Tx, Ty) 中的 Ty
4. 内核 attach将 ADOPTED_LOCKED 事务挂载到 Ty
5. 代理重放HA 返回 attach OK 后，代理发送挂起命令

  • 真实 peerid(Tx, Ty) provider，把 source token Tx 映射到 target connection id Ty。
  • HA 调用统一 promotion 接口并取得每个 token 的 attach 结果。
  • attach 全部成功后向代理发布“可在 Ty 重放”的终局事件。
  • preserve 不可用、过期或 attach 失败时走普通升主策略，而不是阻塞升主。
当前默认 resolver 不是生产 peerid provider preserved_trx_resolve_peer_thd() 当前按传入的 source_connection_id 在本进程执行 Find_thd_with_id， 适合本地预埋/测试语义；跨节点生产对接必须由 HA/代理先完成 Tx→Ty 映射。 推荐的最小接口不是让 provider 返回裸 THD*，而是让 HA 传入 Ty， 再由现有 handle 逻辑按 Ty 查找、pin 并保护 THD。token 仍只有 Tx，Ty 只是 promotion 调用参数， 不进入 transfer artifact。
普通升主不能被 Preserve 阻塞 若 receiver candidate 不存在、已过期、未 READY 或 attach 失败，HA 应放弃该 Preserve epoch， 清理 target 进程内对象并继续普通形态升主。只有 preserve-aware 接管成功，代理才重放挂起事务请求。

11. RESET DRAIN 分支

HA 放弃切换时，在 source 上执行 RESET DRAIN。成功定义是原主业务已经重新开放； 后台 artifact、transfer participant 或缓存清理可以继续。详细设计见 RESET DRAIN 与 Receiver 自动失效设计 。

  1. HA 调用 source RESET DRAIN。
  2. source 停止新的 phase2/transfer 推进，恢复原 Tx 上的事务和会话状态。
  3. source 发布“业务可继续”并返回 RESET 成功。
  4. HA 通知代理该逻辑连接走 REPLAYING_SOURCE。
  5. 代理在原 Tx 上先重放触发 4020 的请求，再按序释放后续请求。
RESET 不等于重新执行已成功的命令 只有明确收到 4020 的命令才进入重放队列。phase2 前已经获得正常响应的命令仍然只执行一次。

12. FINAL_ACK 责任边界

source drain/build/send
        |
        v
target 完整接收并保存当前进程内 epoch
        |
        v
target 返回 FINAL_ACK
        |
        v
source 收到 FINAL_ACK
======== transfer ownership boundary ========
source: 结束 sender/session/epoch 上下文，进入自身后续流程
target: 独立 prewarm，等待 HA promotion 或 TTL 自动销毁

FINAL_ACK 表达

  • target 当前 mysqld 进程已完整接收 epoch。
  • 格式、完整性和当前进程内保存已成功。
  • transfer ownership 已交给 target。

FINAL_ACK 不表达

  • target 已 READY 或已完成 prewarm。
  • 事务已经 attach 到 Ty。
  • HA authority/write-enable 已满足。
  • receiver crash 后仍可恢复 epoch。

source 收到 FINAL_ACK 后不再查询 READY、不触发 promotion、不等待 target 清理，也不接收 target 后续状态。 target 的 prewarm、promotion、abandon 和 TTL 全部由 target 本地状态与 HA 管控。

4020 响应 cutoff/fence 必须位于 FINAL_ACK 之前 source 在所有目标 Tx 已进入 PRESERVED_DRAINED 后，先关闭新的命令读取准入， 等待已经由自己读取的业务命令完成正常响应或 4020 响应，然后才发送 COMMIT_EPOCH 并等待 FINAL_ACK。这样 response fence 失败时 receiver epoch 尚未提交， source 仍可走现有 abort/restore；FINAL_ACK 一旦生效，两端继续彻底解耦。

13. 请求结果安全

对接目标不是实现通用的分布式 exactly-once，而是利用 source 的明确结果边界，避免 Preserve 场景下的重复执行。

代理观察请求执行状态处理
完整正常 OK/结果集/业务错误 source 已完成该命令 把结果返回客户端，不重放。
完整 ERR 4020 该协议命令未执行；事务已 preserve 挂起；终局节点上重放一次。
其他完整 MySQL 错误 按错误本身定义 正常返回或交由 HA 控制面处理，不进入 4020 重放路径。
无完整响应即断开 不确定 进入 AMBIGUOUS_DISCONNECT，不得自动重放。

13.1 为什么 4020 可以重放

早期 gate 位于 get_command() 成功之后、dispatch_command() 之前。 preserved_trx_reject_if_batch_session_drained() 设置错误后， do_command() 直接调用 send_statement_status() 并返回； SQL parser、handler 和 InnoDB 执行路径都没有被调用。

13.2 无法消除的网络事实

mysqld 能确认完整错误包已交给本地网络层，却不能在不增加代理应用级 ACK 的情况下证明代理业务线程已经消费该包。 本设计不增加新的代理 ACK 协议。计划内切换中，代理以自己实际读取到的完整 MySQL packet 为准； 网络断开仍按结果不确定处理。

14. 当前响应屏障缺口

当前代码已经能返回 4020，但尚不能严格证明“DRAIN 完成时，所有已被 source 读取的业务命令都已经完成协议响应”。

14.1 已有的单事务 token delivery 机制不能直接复用

preserved_trx_note_statement_response() 位于 sql/preserve_trx.cc:8418，当前服务的是单会话 pending token delivery 与延迟 shutdown signal。 通用 dispatch 尾部在 sql/sql_parse.cc:2227-2228 调用它。

但 drained session 的最早 4020 路径位于 sql/sql_parse.cc:1266-1325。它在读取命令后直接 send_statement_status()，没有经过 preserved_trx_note_statement_response()。 该机制也没有按 batch generation 统计每个 Tx 的 accepted/completed command。

14.2 当前竞态

Tx 已 PRESERVED_DRAINED
Proxy 写入一个新命令
        |
        +-- source 已 get_command()
        |      -> 应返回 4020
        |
drain owner 直接发送 COMMIT_EPOCH
        |
        +-- FINAL_ACK -> teardown -> finish_with_shutdown()
                               |
                               +-- close_connections / socket close

缺少条件：
    在 COMMIT_EPOCH 前关闭新的命令读取准入，
    并确认该已读取命令的 4020 packet 已完成本地发送。
影响 代理可能没有收到 4020，只看到连接断开，于是不能安全判断该请求是否执行。 这不破坏事务 preserve 正确性，但会破坏“完全依赖 4020 挂起命令”的稳定对接合同。 把 fence 放在 FINAL_ACK 后只能发现问题，无法再安全 abort 未提交 epoch，因此不是推荐落点。

14.3 必须精确定义“已接受命令”

本文将“source 已接受命令”定义为 get_command() 成功读取了一个完整 classic-protocol command packet。 仅停留在 TCP receive buffer、尚未被 mysqld 读取的字节不属于内核可观测的 accepted command。

因此 response fence 能保证 source 已读取请求的响应完成；它不能证明网络中尚未读取的请求一定得到 4020。 代理必须遵守每 backend connection 只有一个 response-bearing outstanding request； long-data 只能与 execute 组成连续 compound request。收到 4020 后停止发送， 才能把不可观测窗口限制为正常的网络断开歧义，而不是制造协议流水线竞态。

15. 最小内核补强

补强只解决 source 已读取命令的响应完成问题，不改 transfer wire、不改 receiver、不改 InnoDB，也不新增 HA 通知协议。

15.1 每个 Tx、每个 batch generation 的两个序号和一个 cutoff

accepted_seq
get_command() 成功后递增，表示 source 已读取完整命令包。
response_seq
该命令的完整 OK/result/error 已完成本地协议发送后推进到对应序号。
read_cutoff_closed
drain owner 捕获 fence 时置位；此后 Tx 不再从 socket 读取新的 command packet，直到 RESET 重新开放或连接关闭。
ps_compound_pending
drained 后已经消费 long-data 分片、但紧随的 execute 尚未读取；cutoff 必须等待其闭合或按 phase2 deadline 失败。

字段只在 preserve_trx_enable=ON 且 THD 属于当前 batch generation 时使用。 普通 MySQL 路径仅保留一个极薄的条件分支。

15.2 Fence 流程

  1. Tx 每次成功读取 response-bearing command 后记录本 generation 的 accepted_seq。
  2. 正常 dispatch 响应和早期 4020 响应都记录 response_seq。
  3. 所有目标事务 preserve 完成后，drain owner 在每个 Tx 上原子置位 read_cutoff_closed，并捕获当前 accepted_seq 作为 fence。
  4. 若存在 ps_compound_pending，先允许该连接读取紧随的 execute 并返回 4020；不得接受其他 response-bearing command。
  5. cutoff 关闭后，命令线程停在读包前，不发送 unsolicited error，也不接受新的 command packet。
  6. drain owner 等待每个 Tx 的 response_seq >= fence_seq。
  7. 等待受 phase2 剩余 deadline 约束，不允许无限等待。
  8. 满足后才调用 commit_epoch()；失败时 abort 尚未提交的 receiver epoch，并复用现有 source restore 路径。
  9. RESET 赢时清除 cutoff，socket 中尚未读取的命令可在原 Tx 恢复后正常执行。

15.3 线性化与锁

  • 序号和 generation 在 THD::LOCK_thd_data 下读写，或使用同等强度的原子合同。
  • 等待时不得持有 LOCK_thd_data、manager mutex、transfer session 锁或 InnoDB 锁。
  • 旧 generation 的迟到 response 不能推进新 generation 的 fence。
  • 普通无响应协议命令不占 response sequence；COM_STMT_SEND_LONG_DATA 仅建立一个 deadline-bounded compound obligation。
  • drained 状态下的 long-data 不进入 backend PS buffer，也不发送 ERR；代理保留的分片由紧随的 execute 统一获得 4020 边界。
  • compound 在 deadline 内没有 execute、连接断开或插入了其他命令时，response fence 失败并在 COMMIT_EPOCH 前 abort。
  • 正常响应发送失败时，把 fence 标记为 transport failure，而不是假装 response complete。

15.4 为什么不需要更复杂的方案

候选设计裁定原因
Proxy 给每个 4020 再发应用级 ACK 不采用 需要新协议、双向状态和更多故障语义；当前计划内切换不需要。
source 等每个连接至少收到一次新命令并返回 4020 不采用 空闲连接可能永远不发命令，会阻塞 DRAIN。
把 proxy 请求队列写入 transfer artifact 不采用 代理协议状态不属于事务内核对象。
accepted/response sequence fence 采用 只覆盖 source 已读取请求，修改面小，语义可测试。
该补强不改变 FINAL_ACK 后两端解耦 fence 在 COMMIT_EPOCH 前只观察 source 自己的 Tx 命令响应，不等待 READY，不发送 target 控制命令。 FINAL_ACK 后 source 不再执行任何 response-fence 协商。

16. 三方接口合同

16.1 mysqld → Proxy：MySQL 错误包

ERR packet:
  error_code = 4020
  sqlstate   = HY000

meaning:
  this exact command packet was consumed but not executed
  source transaction has entered preserved/drained ownership

proxy action:
  suppress client-visible error
  store exact request
  stop source forwarding
  wait for HA terminal event

16.2 HA → Proxy：三个终局结果

事件必要字段代理动作
PRESERVE_PROMOTION_ATTACHED logical connection id、Tx、Ty、promotion attempt/generation、target endpoint 校验当前挂起 generation，切到 Ty，重放 4020 请求。
PRESERVE_RESET_SUCCEEDED logical connection id、Tx、drain attempt/generation、source endpoint 校验当前挂起 generation，回到 Tx，重放 4020 请求。
PRESERVE_CONTINUATION_ABORTED logical connection id、Tx、attempt/generation、稳定 reason code 不重放，结束该逻辑事务/连接；HA 可继续普通升主。

事件名可按 HA 项目现有接口命名调整，关键是携带 attempt/generation，防止旧 promotion/reset 结果唤醒新一轮挂起。 不需要 READY 进度事件驱动代理；代理只关心最终能在哪个 backend 上继续。

16.3 HA → mysqld：目标端内部 promotion 调用

promotion attempt
  -> validate candidate/process generation
  -> validate READY/apply/fence
  -> adopt preserved token Tx
  -> resolve peerid(Tx, Ty)
  -> pass Ty to kernel and protect pristine target THD
  -> resume adopted transaction on Ty
  -> return per-token attach result
  -> HA publishes terminal event to Proxy

16.4 Proxy 的伪代码

on_source_response(request, response):
  if response.is_complete_mysql_error(4020):
    assert no_other_backend_request_inflight()
    suspended_request = request
    state = WAIT_HA_TERMINAL
    return  // do not expose 4020 to client

  if response.is_complete():
    deliver_to_client(response)
    state = ACTIVE_SOURCE
    return

  state = AMBIGUOUS_DISCONNECT
  notify_ha_transport_ambiguity()

on_ha_promotion_attached(event):
  require state == WAIT_HA_TERMINAL
  require event.tx == source_connection_id
  require event.generation == suspended_generation
  bind_target_backend(event.ty, event.endpoint)
  replay_on_target(suspended_request)
  drain_queued_requests_in_order()

on_ha_reset_succeeded(event):
  require state == WAIT_HA_TERMINAL
  require event.tx == source_connection_id
  require event.generation == suspended_generation
  replay_on_source(suspended_request)
  drain_queued_requests_in_order()

on_ha_continuation_aborted(event):
  require state == WAIT_HA_TERMINAL
  require event.tx == source_connection_id
  require event.generation == suspended_generation
  state = TERMINAL_FAILED
  fail_logical_transaction_without_replay(event.reason)

17.2 response fence 必加 MTR

  • 在 Tx 读取命令后、早期 4020 send_statement_status() 前暂停；证明 COMMIT_EPOCH 尚未发送。
  • 释放发送后，证明代理收到完整 4020，随后 source 才发送 COMMIT_EPOCH。
  • 正常 inflight 命令响应前暂停；证明 fence 同样等待正常结果。
  • 多 Tx 并行：一个响应慢时，全 batch fence 不提前完成；其余 Tx 不被串行执行。
  • 旧 generation 迟到 response 不满足新 generation fence。
  • 发送失败：DRAIN 不宣称成功完成 response contract。
  • cutoff 关闭后不再读取新命令；RESET 清除 cutoff 后，socket 中未读取命令可正常继续。
  • COM_STMT_SEND_LONG_DATA/CLOSE drained 路径不产生错位 ERR packet；long-data compound 的下一条 execute 返回 4020。
  • long-data 在 preserve 边界前后各接收一部分；RESET 后先 STMT_RESET，再完整重发，最终参数内容无重复。
  • preserve_trx_enable=OFF 时命令路径和 THD 行为不变。

17.3 代理与 HA 联调场景

  1. 文本 UPDATE 收到 4020，promotion attach 后在 Ty 执行一次，最终只产生一次业务效果。
  2. 文本 UPDATE 收到 4020，RESET 后在 Tx 执行一次。
  3. 已 prepare 的 binary execute 收到 4020，Ty 上 reprepare/remap 后成功。
  4. 带 long-data 的 execute 收到 4020，Ty 上按原分片顺序重发。
  5. 收到 4013 时不进入挂起。
  6. 网络断开但无 4020 时不自动重放。
  7. 旧 HA attempt 的 attach/reset 回调不能唤醒新 generation。
  8. Preserve promotion 失败时 HA 继续普通升主，代理按既定异常策略结束挂起，不阻塞集群开写。
  9. continuation-aborted 终局不重放触发 4020 的请求，也不让连接永久停留在 WAIT_HA_TERMINAL。

17.4 验收断言

0 收到 4020 的请求在 source 上实际执行次数
1 终局 backend 上该挂起请求的成功重放次数
0 无 4020 证据时的自动盲重放次数

18.3 代理项目对接检查表

  • 按数值 4020 识别，不按错误文本。
  • 每 backend connection 同时只允许一个 response-bearing outstanding request。
  • long-data 与 execute 作为一个连续 compound request，代理全量缓存分片。
  • 收到 4020 后停止 source 转发，保存原请求并保持队列顺序。
  • 正常响应永不重放；无完整响应永不盲目重放。
  • 维护 client stmt id 与 Tx/Ty backend stmt id 双映射。
  • 缓存 long-data 直到 execute 结果确定。
  • RESET 重放 long-data execute 前，先对 source statement 执行 COM_STMT_RESET。
  • HA 终局事件携带 Tx 和 generation；promotion-attached 额外携带 Ty。
  • HA 必须为每个挂起连接给出 attached、reset-succeeded 或 continuation-aborted 三选一终局。
  • Ty attach 成功前不得发送挂起业务请求。
  • RESET 成功后先重放 4020 请求，再开放后续请求。
  • Preserve 失败不阻塞普通升主。
最终裁定 这套对接不需要把系统复杂化。mysqld 提供事务 preserve/attach 和明确的 4020 未执行边界； Proxy 保存协议请求并负责重放；HA 只发布 promotion attach 成功或 RESET 成功的终局。 当前 source 侧需要补齐两个相邻合同：在 COMMIT_EPOCH 前关闭命令读取并等待已接受命令的正常响应或 4020； 对 COM_STMT_SEND_LONG_DATA/CLOSE 保持 classic protocol 的无响应语义。
