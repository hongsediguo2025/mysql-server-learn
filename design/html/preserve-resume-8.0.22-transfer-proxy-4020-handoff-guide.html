Transfer Phase 2、4020 挂起与 Tx→Ty 事务续作对接指南

本文说明代理节点如何处理两种“尚未执行”边界：source 在线时收到 ER_PRESERVE_TRX_SESSION_DRAINED (4020)，以及 promotion/shutdown 终态中的计划内连接断开。 两种路径都必须等 HA 完成终态节点的事务 RESUME 后，才把队首请求准确重放到 Ty 或重启后的连接；RESET 保留原连接，单独处理。

1. 对接结论

代理、HA 与 mysqld 的职责可以压缩成三个简单合同，不需要把 HA 状态机或代理协议状态放进 Preserve 内核。

mysqld

Source 发布 CLOSING 后，普通业务连接的新 command 一律不进入执行主体；已读完整 packet 时返回 4020， 终态连接先关闭时则由断连结束； 该连接当时可能尚无事务、正在等待 Preserve，或最终被排除，不能从 4020 推导 token 已经 Preserve。

Proxy

收到 4020 后不向客户端返回错误；计划内终态断连时也保存唯一在途请求。 两者都停止向 source 继续下发，后续客户端请求按连接顺序排队。

HA

HA 决定最终走升主还是 RESET。升主成功后提供 Tx→Ty 接管结果； RESET 成功后通知代理原 source 已恢复；Preserve 接管放弃时明确结束续作。

核心流程 source 正常执行的旧请求必须先完成并返回正常结果；CLOSING 后完整 4020 明确证明该请求未执行。 若 promotion/shutdown 终态先关闭连接，只有当前 HA attempt 明确完成且事务 RESUME 成功，代理才重放唯一在途、未得到完整结果的请求。 HA 升主成功则在 Ty 上重放，local startup 在重连并 RESUME 后重放，RESET 成功只重放明确收到 4020 的请求。
本文是三方接口权威面 HA 身份、4020 唯一承诺、DRAIN survivor/excluded 结果、RESET/promotion 终局和计划内断连重放条件以本文为准。 CLOSING 编排细节见 WARMCOPY_CLOSING 逐 token 设计； RESET 内部恢复和 TTL 见 RESET DRAIN 与 Receiver 自动失效设计。
只能识别计划内终态断连，不能泛化任意断连 代理必须先消费断连前收到的完整 MySQL packet。只有连接关闭与当前 drain/promotion 或 local shutdown generation 匹配， HA 已确认 source 终态，且事务随后 RESUME 成功时，才允许重放没有完整结果的唯一在途请求。 网络故障、mysqld crash、旧 generation 回调或无法证明旧 command 已收敛的断连仍是结果不确定，禁止盲重放。

2. 场景与边界

本文以 transfer 模式下的计划内物理备机升主为主，同时解释本地 shutdown/startup 与 RESET DRAIN 为什么采用不同的连接处理。三类场景共享 CLOSING 命令门禁，但连接是否终止、由谁授权重发并不相同。

场景旧 source 连接未进入执行主体的在途请求允许重发的时点
物理备机计划内升主 source 交权后关闭；代理在新主建立 Ty。 若 source 在线时已完整返回 4020，则按 4020 挂起；若终态先关闭连接，则保存唯一在途请求并等待 HA 判定。 HA 确认本 generation 的 promotion 成功，且 token 已在 Ty 上 RESUME/attach 成功之后。
本地 preserve → shutdown → startup 旧连接随 mysqld shutdown 断开；startup 后重新连接。 处理方式与计划内升主相同：完整 4020 可直接证明未执行；计划内 shutdown 断连由本次 generation 的恢复结果裁决。 startup recovery 完成、对应事务在新连接上 RESUME 成功之后。
RESET DRAIN mysqld 不退出，原 Tx 保留并恢复可运行。 完整收到 4020 的请求由代理保存；尚未被 mysqld 读取的 packet 仍留在 socket 中，不应由代理再发一份。 HA 收到 RESET OK 后：仅重发明确收到 4020 的请求；未读 packet 由原连接自然读取执行。
本文的“计划内断连可重发”不是通用网络重试 代理必须维持 classic protocol 半双工约束：每个 backend 同时最多一个需要响应的请求，并先消费断连前已经收到的完整 packet。 只有旧 command 已按 drain completion boundary 收敛、连接按当前 generation 正常终态关闭、transfer DRAIN 结果确认 Tx 是 survivor （或本地 startup recovery 确认 token 可恢复）、且终态 RESUME 成功时， 才允许重发该唯一在途请求。RST、socket send failure、网络故障、mysqld crash、旧 generation 回调或已执行但响应不明的请求仍按结果不确定处理。

receiver 是在线、进程内候选 receiver 重启后 transfer epoch 失效，残留临时文件应清理；它不是本地 startup carrier。 因而代理续作也只针对当前 target mysqld 进程和当前 HA promotion attempt。

5. Phase 2 命令边界

source 对 phase2 周围命令的处理不是“所有命令都必须收到 4020”，而是先保证所有新 command 零执行， 再根据 source 是否来得及读取并完整回复 packet，表现为 4020 或计划内断连。

命令时点source 行为代理行为
命令包已被 get_command() 读取，并在关闭边界前成为 inflight 允许该命令完成，返回正常 OK、结果集或业务错误；之后会话再进入 quiesce。 按普通结果处理，不得重放。
CLOSING 发布后，普通业务连接读取新 response-bearing command 无论是否有事务、是否已经 Preserve，均在执行主体前返回 4020。 隐藏 4020，挂起原请求，停止向 source 继续发送；等待 HA 终局。
CLOSING 发布后，packet 尚未被 mysqld 读取，终态先关闭连接 该 command 没有进入 dispatch；连接随 promotion handoff 或 shutdown 关闭，不要求补发 4020。 保存唯一在途请求；只有匹配本 generation 的终态 RESUME 成功后才重发。
CLOSING 中的 HA 专用控制连接 固定账号 + SHUTDOWN_ACL 绕过 CLOSING gate，随后按命令原生权限和语义执行。 只用于 HA 控制，不承载业务请求，也不因绕过门禁获得额外 SQL 权限。 
source Tx command boundary

packet read before closing gate
    -> mark inflight
    -> command executes
    -> normal response
    -> Tx reaches idle boundary and quiesces

packet read after CLOSING publication on ordinary connection
    -> reject before dispatch
    -> ER_PRESERVE_TRX_SESSION_DRAINED (4020)
    -> command body is not executed

packet not read before planned terminal connection close
    -> no dispatch and no 4020 requirement
    -> proxy waits for matching HA terminal + successful RESUME
    -> replay once on the resumed connection

mysql-test/suite/preserve_trx/t/batch_drain_packet_before_dispatch.test 覆盖第一类边界；batch_drain_target_command_blocked.test 覆盖命令在 quiesce 期间等待、随后以 4020 返回的行为。

6. 4020 精确定义

错误名
ER_PRESERVE_TRX_SESSION_DRAINED
错误号
4020
SQLSTATE
HY000
服务端消息
Preserve drain is active; this command was not executed
代理可依赖的语义 对产生该 4020 的命令包，mysqld 已经消费协议请求，但没有执行该命令的 SQL/协议主体。 这是 4020 的唯一内核承诺；事务是否成为 survivor 只能由 DRAIN result 和 HA 终局决定。
4020 不等于事务已 Preserve，也不等于 target 已接受 CLOSING gate 可在 token Preserve 前、无事务会话上或最终 timeout exclusion 的会话上返回 4020。 因此 4020 只建立“source 上未执行”的请求边界，不表达 survivor、FINAL_ACK、READY、promotion authority 或 attach 成功。 代理必须等待 HA 的 promotion、RESET 或 continuation-abandoned 终局。
错误/事件是否挂起是否允许自动重放说明
4020 是 HA 给出终局后是 显式证明该 command 已被读取但未执行；不是终态场景唯一的挂起触发器。
4013 ER_PRESERVE_TRX_UNSUPPORTED 否 否 用途广泛，可能表示资格、上下文或 drain gate 不支持，不能推导“请求未执行且事务已转移”。
4014 ER_PRESERVE_TRX_DRAIN_TIMEOUT 否 否 主要是 drain owner/control-plane 失败。
4015 ER_PRESERVE_TRX_BATCH_CLEANUP_FAILED 否 否 需要 HA 检查 source 状态，不能由业务代理自行续作。
匹配当前 generation、旧 command 已收敛的 promotion 或 local shutdown 正常终态断连 是 RESUME 成功后是 代理先消费完整 packet；对没有完整结果的唯一在途请求，HA 终态与 survivor/RESUME 结果共同授权重发。
普通网络断开、2013、EOF 或无法匹配 generation 进入歧义态 不得盲目重放 请求可能未执行、已执行但响应丢失，或只写入部分结果。

错误文本定义在 share/messages_to_clients.txt:9475； 当前 debug/release 生成头均确认 ER_PRESERVE_TRX_SESSION_DRAINED = 4020。

7. 代理状态机

每条用户逻辑连接只需要一个很小的状态机。完整 4020 与可归属到当前 drain generation 的计划内终态断连 都可以进入等待态；真正重发仍只能由 HA 的 RESUME 成功终局授权。

ACTIVE_SOURCE → REQUEST_IN_FLIGHT → WAIT_HA_TERMINAL → REPLAYING | TERMINAL_FAILED
代理状态可向 source 发送可向 target 发送客户端可见行为
ACTIVE_SOURCE 是 否 正常转发。
REQUEST_IN_FLIGHT 同一后端不得再发第二个 response-bearing 请求 否 等待完整响应；long-data 分片只能作为紧随 execute 的 compound request 组成部分。
WAIT_HA_TERMINAL 否 否 隐藏完整 4020 或接收匹配 generation 的计划内断连，保存唯一在途请求并排队后续请求；等待 promotion/startup RESUME 成功或 RESET 成功。
REPLAYING 只向 HA 终局指定且已满足继续条件的 backend 发送：RESET 为原 Tx，promotion 为已 attach 的 Ty，startup 为已 RESUME 的新连接。 先重放唯一在途请求；得到完整结果后再按序释放队列。
AMBIGUOUS_DISCONNECT 否 否 断连无法绑定当前计划内 generation，或请求结果无法裁定；不自动执行。
TERMINAL_FAILED 否 否 HA 已放弃 Preserve 续作；结束逻辑事务/连接，不阻塞普通升主。

7.1 必须保持的顺序规则

  1. 每个 source backend connection 同时最多一个 response-bearing 请求在途。
  2. COM_STMT_SEND_LONG_DATA... 与紧随其后的 COM_STMT_EXECUTE 视为一个 compound request，不允许夹入其他命令。
  3. 收到 4020 后立即停止向该 source connection 发送任何新协议命令。
  4. 发生计划内终态断连时，先消费断连前已经收到的完整 packet，再保存没有完整结果的唯一在途请求。
  5. 挂起请求排在队首；promotion/startup RESUME 或 RESET 后必须先处理它。
  6. 只有队首请求获得完整结果后，才释放后续排队请求。
  7. 不得把同一请求同时发往 Tx 和 Ty。
不再要求“每条晚到 command 必须收到 4020” 4020 是 source 在线时最清晰的未执行证据；promotion/shutdown 已进入终态时，关闭旧连接比继续维护逐连接响应屏障更简单。 代理仍必须等待 HA 告知：target attach/RESUME 成功、local startup RESUME 成功、source RESET 成功，或 Preserve continuation 已放弃。

这里不复用 transfer receiver 或 HA promotion。共同点只有请求边界：旧连接必然消失，代理必须先完成 startup 后的事务 RESUME， 再重发 CLOSING 后未执行且未获得完整结果的请求。本地 preserve token 继续使用既有生成语义，不等于本节 transfer 场景的 Tx token。

重放的是原始协议请求，不是“重放事务历史” 已经 preserve 的事务状态由内核转移和 attach/RESUME 恢复；代理只重放触发 4020、或在计划内终态断连时尚未执行的那一条命令， 再继续发送其后排队的新命令。之前已经成功执行的 SQL 绝不能重放。

9. 二进制 Prepared Statement 续作

当前 MTR 已证明：事务 preserve 后，已有 prepared statement 的 COM_STMT_EXECUTE 返回错误码 4020，随后 COM_PING 也返回 4020。测试位于 mysql-test/suite/preserve_trx/t/batch_drain_drained_session_binary_ps_blocked.test。

backend statement id 不能跨 mysqld 使用 source 上的 statement id 只在 Tx 所属 mysqld 进程内有效。升主后不能把原 COM_STMT_EXECUTE(stmt_id=source_id) 原样发给 Ty。 PS 迁移必须由代理维护虚拟 statement catalog。

9.1 代理必须保存的 PS 信息

  • 客户端可见 statement id 与 source/target backend statement id 的映射。
  • 原始 SQL 文本和 prepare 时的数据库、字符集等必要会话上下文。
  • execute 参数类型、NULL bitmap、值和游标标志。
  • COM_STMT_SEND_LONG_DATA 的全部分片内容，直到对应 execute 得到确定结果。
  • statement close/reset 状态，防止已关闭语句被重建。

9.2 Existing PS execute 的 promotion 重放

1. Tx 上 COM_STMT_EXECUTE(source_stmt_id) -> ERR 4020
2. Proxy 挂起 execute，保存参数和 long-data
3. HA 完成 token Tx -> Ty attach
4. Proxy 在 Ty 上 COM_STMT_PREPARE(original_sql)
5. Proxy 记录 target_stmt_id
6. Proxy 按原顺序重发 COM_STMT_SEND_LONG_DATA(target_stmt_id, ...)
7. Proxy 发送 COM_STMT_EXECUTE(target_stmt_id, original_params)
8. Proxy 将结果转回客户端，并切换 stmt-id 映射

9.3 各 PS 命令处理

协议命令4020/迁移处理对接要求
COM_STMT_PREPARE 若收到 4020，挂起 prepare；终局节点上重新 prepare。 客户端 stmt id 必须由代理虚拟化，不能暴露 backend id 的迁移。
COM_STMT_EXECUTE 收到 4020 后挂起；attach 后 reprepare + execute。 保存参数类型和值；只重放一次。
COM_STMT_SEND_LONG_DATA 协议本身不返回响应，不能把每个分片当成独立的 4020 请求。 代理必须缓存每个分片，并与 execute 组成连续 compound request；最终 execute 确定前不能丢弃。
COM_STMT_CLOSE 协议本身无响应，不作为挂起业务请求。 更新代理 catalog；终局节点不重建已关闭语句。drained gate 不应向该命令发送违背协议的 ERR packet。
COM_STMT_RESET 按有响应命令处理；必要时在终局 backend 映射上执行。 同时清理代理缓存的 long-data。
COM_STMT_FETCH 当前不支持跨节点 cursor 续作。 Preserve 资格检查已拒绝 open server-side cursor，见 sql/preserve_trx.cc:5083。
mysqld 只恢复事务，不迁移代理协议对象 binlog cache、MDL、InnoDB trx、锁、会话事务属性等由 Preserve 内核恢复； prepared statement catalog、backend stmt id 和客户端请求队列仍属于代理。

9.4 无响应命令与终态断连合同

当前 protocol gate 已对 BLOCK_CLOSING_DRAINED 单独处理 COM_STMT_SEND_LONG_DATA：不写入 backend PS buffer，也不发送 ERR； COM_STMT_CLOSE 和 COM_QUIT 继续作为无响应清理命令放行。 该行为位于 sql/sql_parse.cc:1605-1637。

promotion/shutdown 不需要在 mysqld 中记录 compound fence 旧 backend 连接在终态必然关闭，source PS buffer 也不会迁移。代理已经缓存全部 long-data 分片； 只有 HA 或 startup 完成事务 RESUME 后，代理才在新 backend 上重新 PREPARE、重发全部分片并 EXECUTE。 因而无需增加 ps_compound_pending、accepted/response sequence 或 long-data ACK，也不能向无响应命令注入 ERR packet。

9.5 Long-data 的 RESET 重放

部分 long-data 分片可能在 Tx 进入 PRESERVED_DRAINED 前已经写入 source 的 prepared statement buffer， 其余分片则可能在 drained 后被丢弃。代理无法仅凭 4020 判断 source 已接收了多少分片。 因此 RESET 分支不能直接追加式重发。 mysqld_stmt_reset() 会关闭 cursor 并调用 reset_stmt_params() 清除 mysqld_stmt_send_long_data() 写入的参数，见 sql/sql_prepare.cc:1984-2016。 

RESET success, replay a hung long-data execute on original Tx:
  1. COM_STMT_RESET(source_stmt_id)   // clear any partially accepted long-data
  2. resend every cached COM_STMT_SEND_LONG_DATA chunk in original order
  3. COM_STMT_EXECUTE(source_stmt_id, original_params)

promotion success on Ty:
  1. COM_STMT_PREPARE(original_sql)   // clean target statement
  2. resend every cached long-data chunk
  3. COM_STMT_EXECUTE(target_stmt_id, original_params)

10. HA 升主与 Tx→Ty 接管

当前仓库没有真实物理备机 HA 流程，但已经预埋了一部分“受保护 Ty + promotion attach/resume”内核能力。 后续物理备机项目应从 HA 内部入口调用，而不是由 source classic session 触发。

1. HA 选主target 获得 promotion authority，满足 apply/fence 条件
2. 准备 Ty建立或定位空闲、无事务、受保护的 target THD
3. peerid 解析用 token Tx 找到 peerid(Tx, Ty) 中的 Ty
4. 内核 attach将 ADOPTED_LOCKED 事务挂载到 Ty
5. 代理重放HA 返回 attach OK 后，代理发送挂起命令

11. RESET DRAIN 分支

HA 放弃切换时，在 source 上执行 RESET DRAIN。成功定义是原主业务已经重新开放； 后台 artifact、transfer participant 或缓存清理可以继续。详细设计见 RESET DRAIN 与 Receiver 自动失效设计 。

  1. HA 调用 source RESET DRAIN。
  2. source 停止新的 phase2/transfer 推进，恢复原 Tx 上的事务和会话状态。
  3. source 发布“业务可继续”并返回 RESET 成功。
  4. HA 通知代理该逻辑连接进入 REPLAYING，backend 仍为原 Tx。
  5. 代理在原 Tx 上先重放触发 4020 的请求，再按序释放后续请求。
RESET 不等待 target ABORT ACK source 可 best-effort 发送 epoch ABORT 或断开 transport，但 RESET OK 只等待原 Tx 恢复可运行和 4020 gate 解除； target orphan 由 receiver TTL 销毁。只有 A=OFF 后仍要提交 survivor epoch 的 timeout exclusion，才要求 excluded token 先取得确定 ABORT ACK。
RESET 不等于重新执行已成功的命令 只有明确收到 4020 的命令才进入重放队列。phase2 前已经获得正常响应的命令仍然只执行一次。

12. FINAL_ACK 责任边界

source drain/build/send
        |
        v
target 完整接收并保存当前进程内 epoch
        |
        v
target 返回 FINAL_ACK
        |
        v
source 收到 FINAL_ACK
======== transfer ownership boundary ========
source: 结束 sender/session/epoch 上下文，进入自身后续流程
target: 独立 prewarm，等待 HA promotion 或 TTL 自动销毁

FINAL_ACK 表达

  • target 当前 mysqld 进程已完整接收 epoch。
  • 格式、完整性和当前进程内保存已成功。
  • transfer ownership 已交给 target。

FINAL_ACK 不表达

  • target 已 READY 或已完成 prewarm。
  • 事务已经 attach 到 Ty。
  • HA authority/write-enable 已满足。
  • receiver crash 后仍可恢复 epoch。

source 收到 FINAL_ACK 后不再查询 READY、不触发 promotion、不等待 target 清理，也不接收 target 后续状态。 target 的 prewarm、promotion、abandon 和 TTL 全部由 target 本地状态与 HA 管控。

FINAL_ACK 前不再增加逐 THD response fence source 只需保证：CLOSING 前已经 dispatch 的旧 command 先到既有 completion boundary；CLOSING 后普通新 command 不进入执行主体； survivor epoch 完整提交后才接受 FINAL_ACK。source 在线时可返回 4020，终态先到则关闭旧连接。 FINAL_ACK 一旦生效，两端彻底解耦，后续重连、RESUME 和重发由 HA/Proxy 终局驱动。

13. 请求结果安全

对接目标不是实现通用的分布式 exactly-once，而是在计划内 drain generation 内区分“已有完整结果”“明确未执行”与“结果不确定”， 避免 Preserve 续作时重复执行。计划内断连只有满足本节完整证据链时，才能等价于“该晚到请求未执行”。

代理观察请求执行状态处理
完整正常 OK/结果集/业务错误 source 已完成该命令 把结果返回客户端，不重放。
完整 ERR 4020 该协议命令未执行；事务 Preserve 结果尚未由该错误确定 挂起；终局节点上重放一次。
其他完整 MySQL 错误 按错误本身定义 正常返回或交由 HA 控制面处理，不进入 4020 重放路径。
匹配当前 generation 的计划内终态断连，且 Tx 是 survivor CLOSING 后的唯一在途请求未进入执行主体；旧连接已终止 继续挂起；promotion/startup RESUME 成功后在终局连接上重放一次。
无法匹配 generation 的断连，或旧请求是否已 dispatch 无法裁定 不确定 进入 AMBIGUOUS_DISCONNECT，不得自动重放。

13.1 为什么 4020 可以重放

mysqld 在读取完整 command packet 后，先经过 protocol CLOSING gate；文本/PS 执行还有 SQL gate 兜底。 BLOCK_CLOSING_DRAINED 在 parser/handler/InnoDB 执行主体之前设置 4020 并结束本 command， 所以代理实际读取到完整 4020 时，能证明该 command 主体没有执行。

13.2 为什么计划内终态断连也可重放

  1. 代理遵守半双工：每个 backend 同时最多一个需要响应的请求。
  2. CLOSING 前已 dispatch 的旧 command 继续执行，只有完成后才在既有 command-read boundary 发布 QUIESCED。
  3. CLOSING 后普通新 command 不能进入执行主体；source 来得及读取时返回 4020，否则旧连接随终态关闭。
  4. transfer 由 HA 用 drain generation 和 DRAIN result 确认 Tx 是 survivor；本地 startup 则以 recovery 找到 token 且 RESUME 成功为准。
  5. 代理先消费断连前的完整 packet，并只保留那个没有完整结果的唯一在途请求。
  6. 只有事务在 Ty 或 startup 后的新连接上 RESUME 成功，HA 才授权重发。
缺少任一条证据就不能使用该简化合同 尤其是普通网络故障、mysqld crash、旧 generation 回调、Tx 不在 survivor 结果中，或旧 command 已执行但响应不明， 都不能仅凭 EOF 推导“未执行”。这些情况进入普通异常处理，不得盲目重放。

13.3 无法消除的网络事实

mysqld 能确认完整错误包已交给本地网络层，却不能在不增加代理应用级 ACK 的情况下证明代理业务线程已经消费该包。 本设计不增加新的代理 ACK 协议。代理以自己实际读取到的完整 MySQL packet 为准，并由 HA generation 区分计划内终态断连与普通网络故障。

14. 场景化请求边界

三类场景必须分开理解。promotion 与 shutdown/startup 是终态连接切换；RESET 是原进程、原连接继续运行。 把它们混成同一套 response fence 会增加状态和竞态，却不能替代 HA 对终局的裁决。

场景内核边界Proxy/HA 边界不需要做
物理备机 promotion 旧 command 完成；CLOSING 后新 command 零执行；FINAL_ACK 后 source 关闭。 HA 确认 survivor 和 Ty RESUME；Proxy 重发唯一在途请求。 不等待每个 Tx 都收到一次 4020；不保留旧连接。
本地 shutdown/startup 旧 command 完成；CLOSING 后新 command 零执行；旧连接随 shutdown 消失。 startup recovery 完成后重连；事务 RESUME 成功后重发。 不把 transfer receiver、FINAL_ACK 或 peerid 引入本地路径。
RESET DRAIN 撤销 CLOSING，恢复原 Tx；mysqld 和 socket 不因 RESET 终止。 完整 4020 请求在 RESET OK 后重发；未读 packet 留在原 socket 自然执行。 不按终态断连重建连接；不重复发送未读 packet。
终态期间不得重新开放普通 command promotion 或 shutdown 已选择成功终局后，CLOSING gate 一直保持到旧普通连接关闭。 FINAL_ACK 与 teardown 之间不能出现短暂 reopen，否则新 command 可能在旧主重新进入执行主体，计划内断连重发合同随即失效。
RESET 是唯一的 reopen 分支 RESET 成功屏障要求原事务恢复、batch state 清除、CLOSING gate 解除。收到完整 4020 的请求由 Proxy 重发； mysqld 尚未读取的 packet 本来就在 socket 中，解除 gate 后只会执行一份，Proxy 不应再复制发送。

15. 最小内核职责

按上述场景边界，终态路径不需要新增逐 THD request/response 状态机。内核只做好命令执行门禁、旧 command 收敛、 survivor 结果和终态连接关闭；请求保存与重发属于 Proxy，终局授权属于 HA。

15.1 内核必须保证的四件事

  1. 发布 CLOSING 后，普通连接的所有新 command 在 parser/handler/存储引擎执行主体之前被截断。
  2. CLOSING 前已 dispatch 的旧 command 继续执行；只有到达既有 command-read completion boundary 后才发布 QUIESCED。
  3. DRAIN 结果明确给出 generation、survivor 和 excluded；终态只能续作 survivor。
  4. promotion/shutdown 成功分支保持 CLOSING 到普通连接关闭；RESET 分支在恢复原事务后才解除 gate。

15.2 明确不新增的状态

  • 不增加 accepted_seq、response_seq 或 read_cutoff_closed。
  • 不增加 ps_compound_pending；终态连接关闭后由 Proxy 在新 backend 重建完整 PS compound request。
  • 不在 get_command() 前 park 普通连接；source 在线时继续使用现有 gate 返回 4020。
  • 不增加 Proxy 对 4020 的应用级 ACK，不把请求队列或 backend stmt-id 写入 Preserve artifact。
  • 不修改 transfer wire、receiver、InnoDB、carrier 或 startup recovery。

15.3 为什么该方案足够

候选设计裁定原因
Proxy 给每个 4020 再发应用级 ACK 不采用 需要新协议、双向状态和更多故障语义；当前计划内切换不需要。
source 等每个连接至少收到一次新命令并返回 4020 不采用 空闲连接可能永远不发命令，会阻塞 DRAIN。
把 proxy 请求队列写入 transfer artifact 不采用 代理协议状态不属于事务内核对象。
accepted/response sequence fence 不采用 终态路径最终关闭旧连接；已有执行门禁与 RESUME 后重发合同足够，新增字段只会扩大共享命令热路径。
CLOSING + old-command boundary + terminal reconnect 采用 复用现有内核状态；明确区分 promotion/startup 与 RESET，修改面最小。
FINAL_ACK 后两端仍彻底解耦 source 不等待 READY、不发送 target 控制命令，也不参与 target 的 prewarm、promotion 或 TTL。 HA 在 target 本地完成 RESUME 后通知 Proxy；请求重发不回到 transfer 协议。

16. 三方接口合同

HA → source 控制连接身份 发起 DRAIN、RESET 或 CLOSING 期间诊断的连接必须使用认证用户名精确为 preserve_trx_ha_admin、且有效持有 SHUTDOWN_ACL 的专用账号。身份判断发生在 SQL 解析前；执行具体命令时仍按原权限检查。 普通 root、仅持 SHUTDOWN 的其他账号或 transfer data session 都不是 HA 控制连接。

16.1 mysqld → Proxy：MySQL 错误包

ERR packet:
  error_code = 4020
  sqlstate   = HY000

meaning:
  this exact command packet was consumed but not executed
  no statement is made about survivor, FINAL_ACK, READY or attach

proxy action:
  suppress client-visible error

promotion/shutdown 的另一条合法入口是旧连接的计划内关闭：若请求没有完整结果，Proxy 保存唯一在途请求， 但只有 HA 后续把该连接、Tx 和 generation 对账为 survivor，并报告 RESUME 成功，才能重发。

16.2 HA → Proxy：DRAIN 结构化结果

result row:
  generation
  outcome = SUCCESS | SUCCESS_WITH_EXCLUSIONS | NO_PRESERVABLE_TOKENS
  source_connection_id | NULL
  token_role = SURVIVOR | EXCLUDED | SUMMARY
  reason = NONE | CLOSING_COMMAND_TIMEOUT
  closing_started_us
  closing_deadline_us

4020 只决定“请求挂起”，DRAIN result 才决定 Tx 是否属于 survivor。HA 必须完整读取结果集并按 (generation, source_connection_id) 对账；不能把所有收到 4020 的连接都当作可在新主 Resume。 SUCCESS_WITH_EXCLUSIONS 当前只用于 standalone/simulator；未来生产物理升主准入固定要求 A=ON。

结果集范围与升级顺序 该结构化结果集只由 strict standby-transfer streaming 的成功路径返回；本地 durable preserve→shutdown→startup 成功路径继续使用原响应合同。失败由 MySQL ERR packet 表达，不发送 outcome=FAILED 结果行。部署必须先升级 HA/Proxy，使其能够完整消费结果集并容忍结果结束后 source 进入计划内 shutdown，再升级返回该结果集的 mysqld；首版不增加 OK/result 双模式、capability 协商或 wire version。

16.3 HA → Proxy：终局结果

事件必要字段代理动作
PRESERVE_PROMOTION_ATTACHED logical connection id、Tx、Ty、promotion attempt/generation、target endpoint 校验当前挂起 generation 和 survivor，切到已 RESUME 的 Ty，重放挂起请求。
PRESERVE_STARTUP_RESUMED logical connection id、本地 preserved token、startup/drain generation、新 source endpoint/connection 校验 startup recovery 与 RESUME 已成功，在新连接重放挂起请求。

PRESERVE_CONTINUATION_ABORTED logical connection id、Tx、attempt/generation、稳定 reason code 不重放，结束该逻辑事务/连接；HA 可继续普通升主。

事件名可按 HA 项目现有接口命名调整，关键是携带 attempt/generation，防止旧 promotion/reset 结果唤醒新一轮挂起。 不需要 READY 进度事件驱动代理；代理只关心事务是否已在某个 backend 上成功 RESUME，以及是否允许重发挂起请求。

16.4 HA → mysqld：目标端内部 promotion 调用

promotion attempt
  -> validate candidate/process generation
  -> validate READY/apply/fence
  -> adopt preserved token Tx
  -> resolve peerid(Tx, Ty)
  -> pass Ty to kernel and protect pristine target THD
  -> resume adopted transaction on Ty
  -> return per-token attach result
  -> HA publishes terminal event to Proxy

on_source_response(request, response):
  if response.is_complete_mysql_error(4020):
    assert no_other_backend_request_inflight()
    suspended_request = request
    suspension_evidence = EXPLICIT_4020
    state = WAIT_HA_TERMINAL
    return  // do not expose 4020 to client

  if response.is_complete():
    deliver_to_client(response)
    state = ACTIVE_SOURCE
    return

on_source_connection_closed(request, connection):
  consume_complete_packet_before_eof_if_any()
  if clean_terminal_close(connection) and
     ha_matches_current_planned_terminal(connection, drain_generation) and
     old_commands_converged(drain_generation):
    assert no_other_backend_request_inflight()
    suspended_request = request
    suspension_evidence = PLANNED_TERMINAL_DISCONNECT
    state = WAIT_HA_TERMINAL
    return

  state = AMBIGUOUS_DISCONNECT
  notify_ha_transport_ambiguity()

on_ha_promotion_attached(event):
  require state == WAIT_HA_TERMINAL
  require event.tx == source_connection_id
  require event.generation == suspended_generation
  require event.tx_role == SURVIVOR
  require event.resume_succeeded
  bind_target_backend(event.ty, event.endpoint)
  replay_on_target(suspended_request)
  drain_queued_requests_in_order()

on_ha_startup_resumed(event):
  require state == WAIT_HA_TERMINAL
  require event.token == suspended_local_preserve_token
  require event.generation == suspended_generation
  require event.recovered_token == suspended_local_preserve_token
  require event.resume_succeeded
  bind_restarted_source(event.connection, event.endpoint)
  replay_on_restarted_source(suspended_request)
  drain_queued_requests_in_order()

on_ha_reset_succeeded(event):
  require state == WAIT_HA_TERMINAL
  require suspension_evidence == EXPLICIT_4020
  require event.tx == source_connection_id
  require event.generation == suspended_generation
  replay_on_source(suspended_request)
  drain_queued_requests_in_order()

on_ha_continuation_aborted(event):
  require state == WAIT_HA_TERMINAL
  require event.tx == source_connection_id
  require event.generation == suspended_generation
  state = TERMINAL_FAILED
  fail_logical_transaction_without_replay(event.reason)

17.2 命令边界与终态连接测试

  • CLOSING 前已 dispatch 的旧 command 正常完成，随后才发布对应 Tx 的 QUIESCED。
  • CLOSING 后普通文本、binary PS 和无响应 command 均不进入执行主体；可响应命令在 source 在线时得到完整 4020。
  • promotion/shutdown 终态先关闭连接时，不要求补发 4020；旧连接不能在 FINAL_ACK 与 teardown 之间重新执行普通 command。
  • 本地 startup：计划内断连后必须先重连并 RESUME，再重发请求；RESUME 前执行次数为 0。
  • promotion：计划内断连后必须先在 Ty attach/RESUME，再重发请求；旧 generation 终局不得唤醒。
  • RESET：完整 4020 请求在 RESET OK 后重发；未读 packet 留在 socket 中自然执行，代理不得复制一份。
  • COM_STMT_SEND_LONG_DATA/CLOSE drained 路径不产生错位 ERR packet；终态重连后 reprepare 并重发完整 long-data。
  • long-data 在 preserve 边界前后各接收一部分；RESET 后先 STMT_RESET，再完整重发，最终参数内容无重复。
  • 普通网络断开、mysqld crash、Tx 非 survivor 和 generation 不匹配均进入歧义/失败路径，不自动重放。
  • preserve_trx_enable=OFF 时命令路径和 THD 行为不变。

17.3 代理与 HA 联调场景

  1. 文本 UPDATE 收到 4020，promotion attach 后在 Ty 执行一次，最终只产生一次业务效果。
  2. 文本 UPDATE 收到 4020，RESET 后在 Tx 执行一次。
  3. 已 prepare 的 binary execute 收到 4020，Ty 上 reprepare/remap 后成功。
  4. 带 long-data 的 execute 收到 4020，Ty 上按原分片顺序重发。
  5. 收到 4013 时不进入挂起。
  6. 匹配 generation 的计划内终态断连，在 RESUME 后重放一次。
  7. 普通网络断开或无法匹配 generation 时不自动重放。
  8. 本地 shutdown/startup 断连后，重连、RESUME、重发的业务效果恰好一次。
  9. 旧 HA attempt 的 attach/reset 回调不能唤醒新 generation。
  10. Preserve promotion 失败时 HA 继续普通升主，代理按既定异常策略结束挂起，不阻塞集群开写。
  11. continuation-aborted 终局不重放触发 4020 的请求，也不让连接永久停留在 WAIT_HA_TERMINAL。

17.4 验收断言

0 收到 4020 的请求在 source 上实际执行次数
1 终局 backend 上该挂起请求的成功重放次数
0 无 4020 或计划内终态证据时的自动盲重放次数

18.2 最小实现与联调面

  • sql/preserve_trx.cc：只验证/保持现有不变量：旧 command 完成后才 QUIESCED，终态关闭前 CLOSING 不 reopen。
  • sql/sql_parse.cc 与 sql/sql_class.h：本方案不要求新增字段或 hook；复用已交付 gate/batch state。
  • Proxy：增加 planned terminal generation 归属、唯一在途请求保存、startup/promotion RESUME 后重发。
  • HA：把 DRAIN survivor 结果、terminal attempt 和 RESUME 结果绑定到同一 logical connection/Tx/generation。
  • MTR/E2E：补计划内断连与普通断连分流、startup/promotion RESUME 前不得重发、RESET 未读 packet 不重复发送。
明确不需要修改 不修改 InnoDB trx/undo/lock 热路径，不修改 bundle、carrier、transfer wire、receiver artifact， 不新增错误码，不增加 accepted/response/cutoff/compound 状态，不把 peerid 或代理 PS catalog 存入 mysqld，也不实现真实 HA。

18.3 代理项目对接检查表

  • 按数值 4020 识别，不按错误文本。
  • 每 backend connection 同时只允许一个 response-bearing outstanding request。
  • long-data 与 execute 作为一个连续 compound request，代理全量缓存分片。
  • 收到 4020 后停止 source 转发，保存原请求并保持队列顺序。
  • 计划内终态断连前先消费已完成 packet；只保存没有完整结果的唯一在途请求。
  • 正常响应永不重放；无 4020 或匹配 generation 的计划内终态证据时永不盲目重放。
  • 维护 client stmt id 与 Tx/Ty backend stmt id 双映射。
  • 缓存 long-data 直到 execute 结果确定。
  • RESET 重放 long-data execute 前，先对 source statement 执行 COM_STMT_RESET。
  • HA 终局事件携带 Tx 和 generation；promotion-attached 额外携带 Ty。
  • HA 必须为每个挂起连接给出 promotion-attached、startup-resumed、reset-succeeded 或 continuation-aborted 终局。
  • Ty attach 成功前不得发送挂起业务请求。
  • RESET 成功后先重放 4020 请求，再开放后续请求。
  • Preserve 失败不阻塞普通升主。
最终裁定 这套对接不需要把系统复杂化。mysqld 提供事务 preserve/attach、CLOSING 零执行门禁和明确的 4020 未执行边界； promotion 与 shutdown/startup 终态直接关闭旧连接；Proxy 保存唯一在途请求并负责重放；HA 只在事务 RESUME 成功后授权重放。 RESET 保持原连接，完整 4020 请求由 Proxy 重发，未读 packet 由原 socket 自然执行。 不引入 generation-scoped response fence，也不把 long-data+execute 状态塞进内核。
