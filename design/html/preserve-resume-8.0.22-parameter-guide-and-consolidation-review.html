1. 结论摘要

参数数量多不是唯一问题。更关键的是有些参数在运行时互相取最小值、二次缩放或跨语义复用，导致“配置值”不等于“实际生效值”。

总体判断：核心配额、artifact 上限、两类 warmcopy、source/receiver/promotion 的大部分参数都对应不同资源或阶段，不能因为名称相似就合并。最值得处理的是并发双旋钮、profile 二次缩放和 commit timeout 多重语义。

高置信度可合并

transfer_data_sessions 与 transfer_sender_workers 的有效并发恒为两者最小值，且默认值、范围相同。建议对外只保留一个 source 并发参数。

高置信度需重定义

transfer_runtime_profile 会再次乘显式 IO、prewarm 和 commit batch 参数。建议 profile 只负责一次性 preset，或完全由显式值取代。

高置信度需拆语义

transfer_commit_timeout_ms 同时参与网络默认超时、receiver artifact 生命周期和 strict prepared 窗口，不应继续使用一个名字承载三种合同。

产品边界：当前仓库完成的是 Preserve/Resume 和 standby promotion-ready 准备栈，不包含真实物理备机 redo apply coordinator 与 HA role transition。promotion 参数只能解释为 targeted readiness / simulator 合同，不能据此声明真实物理升主已完成。

2. 参数如何沿生命周期联动

0. 启动与角色enable、OFF artifact policy、receiver enable、artifact mode、endpoint identity
1. 准入与配额instance/user/batch 数量、timeout、snapshot/binlog/temp/lock 上限、memory lease
2. Drain Phase 1binlog warmcopy、lock warmcopy、temp capture、transfer batching、IO budget
3. Closing / Phase 2drain deadline、warmcopy close、final catch-up、phase2 transfer timeout
4. Receiversource authentication、inflight、receiver workers、saved artifacts、prewarm backlog
5. Promotion Readyprewarm workers/IO/round bytes、ready cache、gate token/worker/deadline
6. Recovery / Resumestartup workers、recovery pass/grace、lock page prefetch、materialize limits

2.1 主开关不是所有子参数的替代品

preserve_trx_enable 是 startup-only 总开关。OFF 时，新 preserve/drain/resume/transfer 必须被隔离；历史 artifact 的处理由 preserve_trx_off_artifact_policy 单独决定。子特性参数不会绕过总开关，但总开关 ON 也不会自动使 standby transfer 可用。

2.2 进入两阶段 drain 的条件

two_phase_enabled = standby_transfer_streaming || preserve_trx_temp_table_enable || lock_warmcopy_requires_two_phase(binlog_warmcopy_enabled)

因此，两阶段 drain 不只由 preserve_trx_warmcopy_enable 决定。启用 temp-table preserve 或 standby transfer 也会进入 phase1/closing/phase2 编排。

2.3 Source 与 receiver 是两套独立角色开关

source 需要 artifact_mode=STANDBY_TRANSFER_SAVE，并满足 target UUID、用户、credential 和“TCP 或 Unix socket 二选一”的 endpoint 完整性检查。receiver 则需要 startup-only 的 transfer_receiver_enable=ON 和 allowed_source_uuid。二者不能合并成一个 enable，因为同一实例可能只承担 source 或 receiver 角色。

3. 最容易误解的有效值公式

数量准入

本次可保存数量同时受： instance max_total per-account max_pending_per_user one-command batch_max_transactions 约束

三者是不同维度，不应合并。即使 batch 上限很高，也不能突破实例或账号上限。

事务存活 timeout

要求：min_timeout <= default_timeout <= max_timeout 显式 WITH TIMEOUT 也必须落在 [min, max] 否则命令拒绝

当前三者都是 SESSION 变量。这使“策略上下限”也可被会话改变，语义上应重新审视。

Preserve heap lease

单次申请必须同时满足： global current + bytes <= memory_budget token current + bytes <= memory_per_token kind current + bytes <= kind_cap lock-plan kind cap = global * 60% native-binlog kind cap = global * 30%

这是 server heap，不是 InnoDB Buffer Pool。lock warmcopy、promotion ready cache 仍有独立上限，当前并非全部纳入同一 root budget。

Source final payload 并发

effective_source_parallelism = min(sender_workers, data_sessions, final_token_count)

这就是两个 public 并发参数高度冗余的直接代码事实。

Runtime profile 二次缩放

BUSINESS_FIRST multiplier = 1 BALANCED multiplier = 2 PROMOTION_PREPARE multiplier = 4 被乘参数：transfer IO、prewarm IO、prewarm max bytes、commit batch tokens prewarm worker floor：1 / 2 / 3

例如配置 prewarm IO=32MiB/s 且 profile=PROMOTION_PREPARE，实际预算是 128MiB/s，而不是 32MiB/s。

Receiver prewarm 并发

effective_prewarm_workers = min(receiver_workers, max(promotion_prewarm_workers, profile_floor))

receiver_workers 是池上限，promotion_prewarm_workers 是 active subset；两者有明确层级，不能直接合并。

Phase1 micro-batch

flush when： encoded_bytes >= phase1_batch_bytes OR oldest_wait >= phase1_batch_linger_ms OR phase1 flush/abort bytes=0 或 linger=0 => 立即发送

大小与等待时间是两个正交触发条件，不能合并成一个参数。

Phase2 与 commit timeout

phase2 source connection timeout = phase2_timeout_ms commit_timeout_ms 还被用于： - connection 未显式指定时的默认超时 - receiver publish/token timeout 秒数 - strict prepared window

默认 phase2=3s、commit=30s。phase2 连接会切到 3s，因此 30s 并不是 phase2 source ACK 的唯一有效上限。

4. 场景化配置与联动

场景 A：本机 shutdown 后恢复

  • preserve_trx_enable=ON
  • artifact_mode=LOCAL_CARRIER
  • transfer_receiver_enable=OFF
  • binlog 与 lock warmcopy 按事务负载启用
  • startup 由 recovery count/grace/threads/prefetch 控制

standby endpoint、receiver 与 promotion 参数在此场景不应影响本地普通路径。

场景 B：Source 在线 transfer

  • preserve_trx_enable=ON
  • artifact_mode=STANDBY_TRANSFER_SAVE
  • target UUID、user、credential 必须完整
  • TCP host+port 或 socket 必须二选一
  • phase1 batching/IO/inflight/source parallelism 生效

该模式只允许 batch manager delivery；单事务 preserve 不进入 standby transfer save。

场景 C：Receiver 实时 prewarm

  • transfer_receiver_enable=ON（startup-only）
  • allowed_source_uuid 匹配 source
  • receiver_workers 决定池容量
  • profile、prewarm workers/IO/max bytes 决定 active budget
  • ready cache cap 决定可保留 READY bundle 数量

暂停 prewarm 只积压 backlog，不应停止 receiver 保存 artifact。

场景 D：未来 promotion gate

  • batch tokens 限制一次 gate 的 token 数
  • gate workers 限制 bounded worker pool
  • gate timeout 是 adopt deadline
  • ready cache miss/cold path 必须 fail closed

当前没有真实 HA provider 时，只能作为 targeted readiness/simulator 证据。

场景 E：总开关 OFF

  • preserve_trx_enable=OFF
  • 无 artifact：普通 MySQL 路径应保持原生等价
  • 有 artifact：由 OFF policy 决定拒绝、忽略、恢复或 abandon
  • 其它动态子参数不能重新开启 Preserve/Resume

场景 F：容量规划

  • 先定 root memory budget 和 per-token 上限
  • 再核对 lock warmcopy epoch cap、prewarm round cap、ready cache cap
  • 外部 blob 还受 snapshot/binlog/temp 文件上限约束
  • native binlog 还受 FD 与 tmpdir headroom 约束

这些上限目前不是一个封闭的总和公式，不能把 256MiB 误解为本特性的绝对进程内存上限。

6.1 名字相似但不应合并

三类 chunk

spill_chunk、warmcopy_chunk、transfer_chunk 分别服务本地 spill、binlog mirror 和网络 frame，生命周期与上限不同。

三类线程

seal、parallel preserve、startup recovery 分别属于 phase2 seal、per-target preserve 和启动恢复，瓶颈与锁域不同。

两个 warmcopy enable

binlog cache 与 lock metadata 可独立失败和回退；合成枚举反而使组合与诊断更复杂。

两个 pending 限制

range count 防元数据放大，byte limit 防 payload 放大，必须同时约束。

gate batch 与 workers

前者限制一次操作的 token 基数，后者限制并发执行；数值相同只是默认策略，不是同一资源。

prewarm max 与 ready cache max

前者限制一次 round 的读取量，后者限制跨 token 持有的缓存量，时间范围不同。

7. 推荐收敛顺序

  1. 先补 effective status，不改行为。暴露 effective source parallelism、profile 后的 IO/worker/batch、完整 memory hierarchy 和各层 deadline。
  2. 合并 source 并发双旋钮。新增单一参数，旧参数进入兼容期；冲突值 fail closed，不继续静默取最小值。
  3. 停止 profile 乘法。让 profile 只产生 preset；一旦用户显式设置参数，该值就是最终生效值。
  4. 拆清 commit timeout 语义。source phase2/ACK、receiver artifact lifetime、strict prepare window分别命名或内部化。
  5. 内部化 scheduler 微参数。在 scaled/full-pressure 回归稳定后，隐藏 commit batch/yield。
  6. 最后处理 memory hierarchy 与 endpoint URI。这两项触及容量合同和配置兼容，必须单独设计和迁移。
不建议一次性删参数。先让“配置值、effective value、状态指标”一致，再逐项废弃。任何收敛都必须保持 preserve_trx_enable=OFF 的原生路径隔离，并对 local preserve、standby source、receiver、promotion 四类场景分别回归。
