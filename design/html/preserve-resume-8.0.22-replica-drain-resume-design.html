Preserve/Resume 物理复制集群接入方案

读者对象：集群系统开发、HA 控制器开发、DBA 平台和 Preserve/Resume 维护者。

适用版本：当前 MySQL 8.0.22 preserve-port worktree；本文描述集群接入目标方案，非当前代码已完整具备的跨机功能。

目标：设计“主机 drain + preserve，备机升主过程中 recovery + resume”的接入方案。

事实源：当前本机 preserve/recovery/resume 能力来自 sql/preserve_trx.cc、sql/preserve_trx_drain.cc、sql/preserve_trx_bundle.*、sql/preserve_trx_carrier*、sql/binlog_warmcopy.*、sql/preserve_trx_lock_warmcopy.* 和 InnoDB preserve/temp table/lock 相关源码。跨机器 manifest、传输协议、升主编排是本文提出的目标方案。

当前边界：当前 MySQL 8.0.22 preserve-port 代码支持本机 preserve/resume/recovery；跨机器 artifact 同步、集群控制器编排和备机自动 resume 尚未实现，本文是后续接入方案。

文档套件导航： 全面详细设计 · 用户手册 · 新同事交接 · 物理复制集群接入方案 · 代码详解

1. 总体模型

目标集成方式是：旧主在受控切换前执行 DRAIN TRANSACTIONS PRESERVE，把 eligible 事务保存为 token 和 snapshot/sidecar；这些 artifact 通过物理复制系统或集群控制器同步到备机；备机在升主前或升主过程中执行 preserve recovery，然后按策略 resume token。对业务来说，未提交事务不在旧主提交，而是在新主恢复后由业务或控制器继续完成。

本方案复用当前 MySQL 的用户命令边界：单连接仍可使用 PREPARE SHUTDOWN PRESERVE TRANSACTION，批量切换使用 DRAIN TRANSACTIONS PRESERVE，升主后通过 RESUME PRESERVED TRANSACTION 恢复 token，运维查询通过 SHOW PRESERVED TRANSACTIONS 或 P_S 表完成。

1.1 与当前本机 Preserve/Resume 的差异

当前本机流程还会处理 record locks、table locks、MDL tickets、read view、savepoint、temporary table sidecar、binlog cache/GTID 等内核对象。集群接入方案不能丢失这些对象，也不能只复制 token 文本。

维度当前本机能力集群接入新增要求
snapshot 位置本机 preserve_trx_dir必须可复制到备机，并保证文件集合原子可见。
prepared trx重启后在同一实例 recovery claim备机需要拥有等价数据页状态，并能根据 token/XID 恢复对应事务语义。

2. 主备切换流程

推荐分为 prepare-drain、artifact seal、standby verify、promotion、resume 五个阶段。控制器必须把每个阶段的成功条件写入切换日志，避免发生旧主已释放、新主未能恢复的灰区。

2.1 推荐阶段定义

阶段主机动作备机/控制器动作成功条件
Prepare Drain阻止新写入，执行 batch drain preserve。记录切换 epoch、旧主身份、预期 token 集。drain 返回成功，token manifest 完整。
Artifact Seal保证 snapshot、sidecar、warm blob 均 fsync 并生成 manifest。开始传输 artifact set。每个 token 的 snapshot 与 sidecar digest 可校验。
Standby Verify保持 fenced，不再接受业务写。确认数据页 checkpoint、binlog/GTID、artifact manifest 一致。备机具备恢复 token 的全部输入。
Promotion旧主保持只读或隔离。备机升主，执行 startup recovery 或显式 recovery step。preserved records 可见，失败 token 可审计。
Resume不再持有事务所有权。控制器或业务执行 resume，并按策略 commit/rollback。每个 token 有明确结果。

3. Artifact 与一致性协议

跨机接入的关键不是简单复制目录，而是定义一个可验证的 artifact set。每个切换 epoch 应有 manifest，列出 token、snapshot、binlog sidecar、temp sidecar、lock artifact、digest、size、source instance id、数据 checkpoint 和 binlog/GTID 边界。

3.1 原子可见规则

  • 备机只处理带完整 commit marker 的 artifact set。
  • manifest 中列出的每个文件必须大小、digest、权限和常规文件属性一致。
  • snapshot 内部 HMAC/CRC 校验仍由 MySQL carrier 执行；集群 manifest 是跨机传输层校验，不替代 MySQL 内部校验。
  • 如果 artifact set 缺文件、digest mismatch 或 commit marker 缺失，备机不得 resume；控制器必须回滚切换或进入人工处理。
  • artifact set 与数据页 checkpoint 必须绑定，不能把旧主某一时刻的 preserved snapshot 套到另一个不一致的数据目录状态。

4. 备机升主 Resume 流程

备机升主时，推荐先完成 artifact 校验和 preserve recovery，再决定由控制器自动 resume 还是把 token 返回给业务。自动 resume 的策略必须按业务定义：有些事务应该继续提交，有些事务应让业务重新连接后显式决定。

4.1 自动 Resume 的准入条件

  • 备机已完成升主 fencing，旧主不可写。
  • artifact set 完整，snapshot 内部校验通过。
  • 新主 binlog/GTID/read_only/super_read_only 状态满足 resume 约束。
  • 执行 resume 的账号具备 token owner 或跨账号恢复权限，并通过对象权限复检。
  • 业务已声明该 token 可由控制器自动 commit、rollback 或只 resume 不提交。

5. 失败矩阵

失败点风险处理策略
旧主 drain 失败未形成完整 token 集。取消切换或按普通停机处理；不能让备机 resume 不完整事务。
snapshot 已写但 sidecar 未同步备机看到 token 但无法恢复语义。manifest 无 commit marker，备机不得导入；旧主保留 token 或回滚。
artifact digest mismatch跨机传输损坏或版本不一致。拒绝该 artifact set；保持旧主 fenced 状态，进入人工修复或回滚切换。
备机 recovery 失败token 无法注册或事务语义无法导入。按 fail-closed，记录错误；根据策略 rollback、taint 或停止升主。
resume 权限失败控制器账号不能恢复 token 或对象权限不足。保留 token，交由具备权限账号处理；不能绕过对象权限。
GTID 或 binlog 状态冲突提交后复制历史不一致。拒绝 resume 或停止升主，必须人工确认位点和 GTID 语义。
旧主回归写入同一事务可能在两侧继续。旧主必须 fenced；新主成功前不释放旧主隔离。
双主风险业务分裂写。集群层必须先完成 fencing，再允许备机写入或自动 resume。

6. 安全、权限和观测

6.1 安全边界

  • Token 是恢复事务的 bearer credential，跨机传递必须加密或限制在可信控制平面。
  • Snapshot/sidecar 文件已有 HMAC/CRC 和文件权限要求；跨机传输层还必须增加通道认证和 manifest digest。
  • 备机 resume 不能绕过对象权限复检。控制器账号应最小化授权，只授予必要的 resume 权限和对象权限。
  • 旧主 fencing 是强制条件。没有 fencing，就不能让备机自动 resume。

6.2 观测与审计

观测项来源用途
token manifest集群控制器记录切换 epoch、token 数、文件 digest 和决策。
P_S preserved transactions新主 MySQL确认 token 状态、owner、错误原因和可见性。
server error log旧主/新主恢复失败、rollback、taint、cleanup 证据。
GTID/position report复制系统证明 artifact 与数据状态属于同一切换边界。
resume result report控制器或业务每个 token 的最终 commit、rollback、保留或失败结果。

6.3 接入实施顺序

控制参数应继承当前本机参数语义，例如 preserve_trx_enable 控制功能总开关，preserve_trx_warmcopy_max_total_bytes 影响 warm external blob 总预算，preserve_trx_lock_warmcopy_enable 控制锁 warmcopy，preserve_trx_parallel_preserve_threads 影响 batch phase 2 target preserve 并行度。集群层不得绕过这些本机约束。

  1. 先实现 artifact set manifest 和只读校验工具，不改变 MySQL 内核。
  2. 实现旧主 drain 成功后的 artifact export hook，记录完整 token set 和文件集合。
  3. 实现备机 import 到 preserve_trx_dir 的原子发布协议。
  4. 实现升主前 recovery 校验步骤，只做 token 可见性和完整性验证。
  5. 再实现可配置 auto resume 策略，默认只暴露 token，不自动 commit。
  6. 最后做强杀、网络中断、旧主回归、双主防护和 full E2E 演练。
